# Setup: MemVane onboarding

Users can ask “이 프로젝트 MemVane 온보딩해줘”, “MemVane 색인 준비 상태 보여줘”, “인덱스 활성화해줘”, or “MemVane 인덱스 전환을 되돌려줘”. Always name the project root and show the result of each phase.

Install this host plugin through its marketplace before using this skill. Plugin registration and hook trust are separate host actions; this skill never changes them. Resolve `ROOT` from a verified host plugin-root variable (`CLAUDE_PLUGIN_ROOT` or `PLUGIN_ROOT`), or from the absolute path of this `SKILL.md` by ascending two directories, and verify `ROOT/core/setup_entry.py` exists. Never infer the plugin root from the target project git root. Run every action through `python3 "$ROOT/core/setup_entry.py" <action> --project "$PROJECT_ROOT" ...` (it disables bytecode); importing plugin modules from the installed tree with plain `python3` writes `__pycache__` and fails the exact installed-tree check (`installed_file_set_not_exact_commit`, listed in `detail.unexpected`).

A project without a selected MemVane route gets no recall, indexing, compile or learning work. Its SessionStart shows one notice line when it has `.auto-context/settings.json`; this skill is the onboarding path the notice names.

## Minimal settings

Onboarding reads only minimal settings: `.auto-context/settings.json` with `{name, skipPaths}`. Any other shape refuses as `minimal_settings_required`; report that and ask the user to write the minimal file (the `name` slug derives the raw collection `<slug>` at the project root and the wiki collection `<slug>-wiki` at `.auto-context/wiki`). Never rewrite settings.json on the user's behalf. A selected route binds the resolved settings identity, so editing `skipPaths` keeps it selected; changing `name` changes the identity and blocks the route as `route_settings_changed`.

## Embedding runtime

The provider is the MemVane embedding runtime under `~/.local/state/memvane/embed-runtime`; check it with `index-runtime-status`. When it is missing on a new machine, `provision-index-runtime --approve-index-runtime-download` builds it: Node comes from `PATH` first, then mise/fnm/nvm/volta/asdf/Homebrew installs, accepted only for a supported major (22, 24 or 26); the pinned lock `locks/laya-embed-runtime` installs node-llama-cpp 3.18.1 and its prebuilt native package with `npm ci --ignore-scripts`; the GGUF is downloaded from its pinned URL and accepted only with the pinned sha256. Pass `--provider-model-file` to use an existing local copy of that exact GGUF instead of downloading. State the network scope (npm registry, model host) before asking for approval. `gc-index-runtime` lists generations; with `--approve-index-runtime-gc` it removes those that are neither active, previous, nor named by an install attestation.

## Onboarding

When asked to onboard a project, keep this as a separate reviewed setup operation. The project needs minimal settings and its wiki under `.auto-context/wiki`; the raw collection is the project root. First identify the exact commit that the host actually loaded and its source checkout, a short owner-private installer state directory and the embedding dimension. A new state directory must be `~/.local/state/memvane/<install id>` with a fresh 32-hex install ID; review and prepare refuse any other new path (`unsupported_state_root_creation`), and the provider digest depends on that path. Use the read-only `plan-fresh-wiki-origin` and `review-index-provider --provider-dimension <n>` actions as internal maintenance steps; the user-facing flow remains a natural-language request to this skill. `--provider-model-file` is optional and must name the runtime's own model (`provider_review_model_not_laya_runtime`). A missing or changed runtime refuses (`provider_review_laya_embed_runtime_missing` / `_corrupt`); report it and offer the runtime step above.

Show the user both exact proposal digests, collection roots, installed commit, model/native identity and the resource admission for local embedding. Apply existing user authorization when it covers this exact scope; seek a new decision only if the source, artifacts or execution scope changes beyond that authorization. Use `prepare-fresh-wiki-origin` with the current digests, same commit, private state directory and dimension. Preparation registers an inactive durable build and returns without selecting a route. Use `index-build-status` or `index-origin-status` to report progress and any explicit deferral; a registered or partially built candidate is not ready for activation. When the worker reports a sealed build, use `finalize-index-origin` to request a fresh source scan. If it reports `freshness_pending`, wait for the worker and repeat finalization only after the new seal is complete. Finalization verifies the current plan, journal, attestation and sealed evidence, then binds the sealed candidate to the recoverable `fresh-wiki-cutover.json` ledger and the project selection marker. Use `index-build-rescan` if freshness cannot be established. To abandon a bound build that was never selected, use `retire-index-origin` with `--approve-index-origin-retire`; it keeps the stores and journal and releases only its own project marker and build pointer, and the next install needs a new state directory and install ID. A mismatch outside these paths requires `recover-index-origin` or a fresh review; never remove a marker or pointer by hand, and never overwrite or delete the model, wiki, manuscript, settings or learning state.

Only after candidate verification and the user's installation/activation authorization, use `activate-index-origin` with its explicit activation flag. Activation also requires the build record to be bound to exactly the ledger's freshly sealed generation (`activation_requires_fresh_generation` / `initial_build_bind_unsettled` otherwise). On success it queues one selected MemVane sync and reports it as `syncWake`. That sync catches up edits made after the sealed snapshot; report it as queued, not as completed. Then verify the host loads that same exact commit and route, performs selected search and off-hook sync through the owned worker, and records L1 QA.

When the user asks to undo or withdraw memvane-db selection, name the project root and state directory. Then, on that explicit request, run `restore-index-origin --project "$PROJECT_ROOT" --state-root "$STATE_ROOT" --approve-index-origin-restore`. It first checks that the ledger, the private install journal and the reviewed route agree. It restores only while no selected MemVane write has been seen, and it settles an interrupted activation or restore through recovery. `legacy_restored` and `legacy_selected` (nothing to withdraw) mean the route is no longer selected. `blocked` with `rollback_forward_only` means memvane-db already took a new write and stays selected. `recovery_required` reports the observed phase after one bounded attempt. Show it as is and do not retry in a loop. Restore removes only the exact route file this selection published; the candidate stores, the ledger and the marker are kept. A state root that still holds a QMD-origin ledger (`qmd-cutover.json`) is refused everywhere as `qmd_origin_detach_required`; report it and stop.

After a host plugin update, the plugin moves each memvane-db install to the newly installed bundle by itself; do not run the `upgrade-*` actions for that. A SessionStart worker uses the host marketplace clone only when its HEAD is the installed commit and its tracked files are clean, re-runs the provider review, and accepts it only when nothing but the bundle file paths changed. Until it finishes, a selected project serves its last published index read-only and the SessionStart notice names the reason; sync, compile and index wakes wait for the upgrade. When the notice reports `provider_changed_rebuild_required`, `older_host_bundle` or a marketplace source refusal, explain it to the user: the index keeps its old bundle, search stays read-only, and a changed provider needs a reviewed rebuild or the explicit upgrade actions with a fresh provider review.

## Explicit local learning profile

For an explicitly requested profile, run `plan-learning-profile --project "$PROJECT_ROOT" --learning-namespace "$APPROVED_NAMESPACE" --learning-choice local-auto-apply --learning-migration new --learning-expires-at-unix-ms "$REVIEWED_EXPIRY"`. Explain the choices in natural language: local learning plus validated candidate application, staged local learning only (`local-staged`), or disabled (`off`). A profile requires an already prepared private namespace, local runtime/model and inference identity, and a separate current train/evaluate execution grant. Missing preparation or corpus authorization remains review-required; do not create a grant, import data, download weights or call a teacher to satisfy it. Use `preserve` migration for an existing learning configuration; never switch to `new` to escape existing false choices. Show the proposal's actual settings changes, project/source/cohort and runtime/model scope, resource/batch/disk limits, expiry and application authority.

Only on acceptance of that exact proposal, use `activate-learning-profile` with identical options plus `--accepted-learning-profile` equal to its `proposalSha256`. Never infer acceptance from the recommendation, onboarding approval, a prior train/evaluate grant or live selection. An interrupted profile activation resumes with the identical accepted options; changed scope/expiry/settings require review. Report selected, waiting, deferred, blocked, staged and applied states separately. A selected profile is not evidence that real training, model replacement or host-hook operation passed.

## Retired QMD backend cleanup (owner, once)

Run this only after both host caches (Claude and Codex) load a release without the QMD backend and every install has moved to it: an install still bound to an older bundle would recreate `~/.cache/qmd` and `~/.config/qmd`, so the action refuses with `older_host_bundle_bound`. Every install must also be re-attested onto the MemVane embedding runtime. `plan-legacy-cleanup` is read only: it lists the plugin's QMD daemon pid files and whether each names a verified live daemon, the `managed-by: qmd-auto-context` LaunchAgents, every target tree with its size, and any install attestation that still names a file inside a target (which blocks the cleanup). `apply-legacy-cleanup --approve-legacy-cleanup` stops only verified daemons (exact command line under the plugin QMD runtime, re-read immediately before `SIGTERM`), unloads and removes marked LaunchAgents, and removes the plugin QMD runtime, shared QMD store and QMD backend state. `~/.cache/qmd` and `~/.config/qmd` also hold the user's own QMD index, configuration and model cache; they are removed only with the additional `--include-user-qmd-data`. Show the plan and get the owner's explicit approval for exactly that scope first.

`update` refreshes an already selected index; it does not replace this setup flow. Never activate a teacher, private checkpoint, or operating plugin hook as a side effect of preparing a runtime.
