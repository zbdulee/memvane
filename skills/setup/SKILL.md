# Setup and preserving upgrade

Users can ask “이 프로젝트 auto-context 설치 상태 보여줘”, “설치 준비해줘”, “검증된 준비를 적용해줘”, or “직전 적용을 되돌려줘”. Always name the project root and show the result of each phase.

1. Install this host plugin through its marketplace before using this skill. Plugin registration and hook trust are separate host actions; this skill never changes them. Resolve `ROOT` from a verified host plugin-root variable (`CLAUDE_PLUGIN_ROOT` or `PLUGIN_ROOT`), or from the absolute path of this `SKILL.md` by ascending two directories. Verify `ROOT/core/install_update.py` exists. Never infer the plugin root from the target project git root; keep it distinct from `PROJECT_ROOT`. Do not use a global install script.
2. Plugin installation has no documented Codex or Claude install callback that runs a long migration. On the first SessionStart for a project that needs setup, the plugin gives one short local notice. New hook and worker code keeps that project inactive until explicit setup succeeds; existing settings, QMD DB, wiki, and model files stay in place. This does not disable the plugin in the host or revoke hook trust. Ask the user once to run this setup skill after host marketplace install and official hook trust review. On a later plugin update, run the read-only `python3 "$ROOT/core/setup_entry.py" check-update --project "$PROJECT_ROOT"`; report the detected reasons and obtain approval before preparing or applying. SessionStart maintains an already configured project but is not an installation permission grant. A running host session that loaded an older plugin may continue using that older code until the host reloads it.
3. Run `python3 "$ROOT/core/setup_entry.py" inspect --project "$PROJECT_ROOT"`, then use the ordinary `plan-install --project "$PROJECT_ROOT"` route in step4. Use the older `plan` route only for separately requested, reviewed topical-card/shadow migration or runtime preparation. The CLI discovers modern/legacy settings, project QMD paths, selected DB, wiki and available Node/npm. It builds the strict request itself; never author request JSON. `--qmd-mode auto` uses a verified active runtime or probes the selected existing package. If needed, supply the reviewed absolute `--qmd-entry` and `--node`; choose `--qmd-mode install` with `--npm` only after explaining package/download/native lifecycle scope, and pass both `--approve-package-execution` and `--approve-lifecycle-scripts` only with explicit authorization. Managed QMD accepts Node 22/24 LTS and Node 26 Current; guide Node 20 users to a supported version. On unsupported macOS architecture or Linux, report that v2 routing remains `setup_required`; preserve existing global QMD binaries, settings and data, and do not promise a global-CLI fallback. Laya defaults to `--laya-mode defer`. Select `--laya-mode reuse` only with a reviewed `--laya-executable` and local `--laya-model-dir`; use `--laya-adapter` if the bundled adapter is unsuitable. Select `--laya-mode install` only after reviewing `--uv`, `--laya-lock`, and the local model directory; `--approve-laya-install` is a separate execution gate. An installed Laya runtime is not a reason to activate learning or select a private checkpoint.
   - On a new machine, `inspect` reports `sharedStoreStatus: not_prepared` instead of rejecting inventory. Production routing still refuses that missing store. `inspect` reports `pythonExecutable` and `sqliteExtensionLoading`; physical vector audits in `prepare-store`, `prepare-replacement-store`, and `install` require that capability. If the latter is false, stop before preparation. Find an **already installed** Python interpreter with both SQLite `enable_load_extension` and `load_extension` APIs (the macOS Command Line Tools Python 3.9 may lack them; an existing Python 3.12 can qualify). Run `inspect` again through that interpreter's reviewed absolute executable path, verify the reported capability is true, and use that same explicit path for subsequent `setup_entry.py` plan/prepare/install/status commands that operate on this store. Do not change the global `python3` or PATH, download an interpreter, or mistake the hook's Python 3.9 floor for this one-time physical vector audit requirement. If none exists, report `python_sqlite_extension_loading_unavailable`. Before project migration, use `plan-store` with reviewed existing `--qmd-entry`, `--node`, `--embedding-model-file` (absolute local GGUF), positive `--expected-dimension`, and an explicit `--qmd-backend auto|cpu` (`--qmd-cpu` remains a CPU alias). This initializer never installs packages or Laya. Auto creates a hash-attested generation-local Node entry that forces QMD 2.5.3's existing `ensureLlama(false)` contract: native `build:never` and `skipDownload:true` for automatic GPU selection and CPU fallback. CLI and LLM module hashes, wrapper, and entry are checked again on selection; daemon and CLI use that same entry. It does not add a hook, change OS permissions, use a test injection API or a Node environment preload. After already-granted synthetic index execution approval, `prepare-store ... --approve-index-execution` proves a single local embedding and typed vector search without generation/rerank, records actual native backend/no-build receipts, removes all probe rows, and reports `prepared_inactive`. Failed native lookup/context/search leaves pointers unchanged. Identical preparation resumes; changed inputs/proof fail closed. `--replace-inactive-store-preparation` explicitly archives a valid inactive prior journal and retains every old generation before preparing a new backend; it refuses an active pointer or an unproved/interrupted preparation. CPU is optional, never a permanent requirement for auto.
   - Activation is an owner-approved cutover, not an assertion that every host session ended. For live-session coexistence, prepare with explicit `--store-scope <approved project>` and apply with `activate-store --approve-store-activation --allow-live-host-sessions`. It reserves normal writer/embed locks with bounded wait, preserves live/unknown holders, checks latest settings/proof and reservation ownership, and atomically publishes pointers. Project writers stay closed until the bootstrap journal commits; unapproved project roots stay `setup_required`. No session termination or scheduler pause is required or performed. A previously loaded v1 session retains its separate global DB/queue until normal reload; it is not silently redirected. A fresh scoped v2 store and private queue preserve those late legacy writes. The older restart flag remains available for callers that actually confirmed restart; never fabricate it. Own daemon quiescence/identity remains required, with port conflicts handled separately by actual bind retries. Failure removes only its exact new runtime pointer before shared selection; an already selected/interrupted store remains for recovery. Empty initialization does not migrate history or prepare generation/reranker/Laya models. Additional project scope enrollment needs its own explicit migration flow.
4. For ordinary preserving v1 file/wiki installation, use `plan-install --project "$PROJECT_ROOT"` with the reviewed existing QMD/Node path, local GGUF/dimension and backend options. This plan does not need published topical-v2 cards. State the collection roots, input hashes and local indexing impact. On explicit installation approval, run `install` with those same options and `--approve-project-enrollment --approve-index-execution`; a missing common store also requires `--approve-store-activation` and the already reviewed live-session or actual restart choice. The formal entry copies legacy settings exclusively, preserves the original settings/wiki/DB/cache/history, reuses or prepares the common tuple, enrolls the approved roots and runs normal index maintenance. Actual shared routing, scoped search, owned daemon health and queue ACK prove QMD readiness. The response separately reports `qmdReady`, `layaReady`, `overallReady` and `componentReadiness`. A successful QMD operation with missing/incompatible required Laya returns `qmd_ready`, `completionScope:qmd`, exit0; report QMD usable and full setup incomplete. Only both components ready produce `completed` with `completionScope:overall`. The journal phase `completed` records QMD maintenance for compatible resume, not overall installation readiness. Identical invocation resumes; `deferred` exits75 and preserves an in-flight writer; unsafe inputs stay closed for review. The Laya execution choice defaults to deferred with no learning. This execution choice and disabled capture/training preferences do not exempt required local Laya/reranker preparation. Explicit `check-update` revalidates pinned Python/package versions, existing compatibility attestation, current adapter and local multilingual edit-model bundle without running a new smoke, downloading or installing. The SessionStart notice uses cheap local metadata preflight only and never proves full readiness or blocks an already ready QMD route. Missing/incompatible QMD or model files require separate reviewed runtime/model preparation; never silently use another global DB, download weights or start a native build. Plugin auto-update only updates code: missing Laya/runtime/model and different v1 QMD paths remain setup-required with one local setup notice; it is not installation permission. Completed installs allow ordinary query preference edits, while changed collection ownership requires review.
   For separately requested topical-card migration, the older shadow CLI requires an opted-in, published v2 wiki and reviewed v1→v2 card mappings. Its project shadow alone is not production readiness. Do not invent wiki text/mappings or use empty bootstrap to relabel existing data as new. Preparation and activation remain separate explicit operations. The original shadow/reviewed mapping and empty-new-project modes retain their existing gates; they are not the ordinary preserving file-index install route.
5. Only for that separately requested topical-card/shadow migration or runtime preparation, on an explicit prepare request, rerun the same options with `python3 "$ROOT/core/setup_entry.py" prepare --project "$PROJECT_ROOT" ...`. It creates a private deterministic request file, the coordinator journal and inactive generations. Repeating identical options resumes; a changed request follows the coordinator's archive/review rules. On a separate explicit apply request, run `activate --project "$PROJECT_ROOT"` only after `prepared` and source/proof checks. Return selected QMD/index/Laya modes and daemon identity. Report `rolled_back_after_activation_failure` or `recovery_required` exactly if handoff fails.
6. To connect another explicitly approved modern project to the selected common store, run `enroll-store --project "$PROJECT_ROOT" --approve-project-enrollment --approve-index-execution`. State the root, collection paths and local embedding impact first. Reuse existing wiki files, model and DB; do not require bulk wiki regeneration or published v2 replacement cards for this file-reindex path. This grants only that root and enqueues normal maintenance, preserving existing store vectors and original/global state. Repetition is idempotent. `queued:false` retains approved intent after interruption; rerunning resumes queueing. Use the normal backend manager/index worker to finish indexing and report search proof separately from enrollment. Never treat indexing:true alone as a migration grant. Sessions and schedulers may stay open.
7. On an explicit rollback request, run `rollback --project "$PROJECT_ROOT"`. Confirm pointer/settings restoration and report concurrent changes that block safe rollback. Shared enrollment is a preserving forward operation; do not automatically select an old operating DB to undo indexed writes.

## Laya Index QMD-origin transition

When asked to move an already indexed project to Laya Index, keep this as a separate reviewed setup operation. First identify the exact commit that the host actually loaded and its source checkout, a short owner-private installer state directory, and every separate user QMD root to preserve. Use the setup entry's read-only `plan-index-origin` and `review-index-provider` actions as internal maintenance steps; the user-facing flow remains a natural-language request to this skill. These actions generate the two-collection source/QMD proposal and the local Node, GGUF, module and packaged native-file proposal without hand-written JSON or model execution. If the selected QMD/model proof or exact local artifact inventory is unavailable, report the missing file or proof and stop. Do not download a replacement or infer approval from an old smoke test.

Show the user both exact proposal digests, collection roots, settings/QMD digests, installed commit, model/native identity, planned backup destination and the resource admission for local embedding. Apply existing user authorization when it covers this exact scope; seek a new decision only if the source, artifacts or execution scope changes beyond that authorization. Use `prepare-index-origin` with the current digests, same commit, private state directory, reviewed existing GGUF/dimension if needed, and separately identified user QMD roots. Preparation registers an inactive durable build and returns while QMD remains selected. Use `index-build-status` or `index-origin-status` to report progress and any explicit deferral; a registered or partially built candidate is not ready for activation. When the worker reports a sealed build, use `finalize-index-origin` to request a fresh source scan. If it reports `freshness_pending`, wait for the worker and repeat finalization only after the new seal is complete. Finalization verifies the current source, makes and checks the plugin-owned QMD backup, then binds the sealed candidate to a recoverable cutover ledger. Use `index-build-rescan` if freshness cannot be established. QMD stays selected and keeps indexing until activation. If QMD indexed anything after finalization, repeated finalization and activation both refuse with `cutover_source_drift_requires_fresh_generation`: the bound generation predates that change and is never rebound to the new QMD digest. Report this to the user as "the prepared Laya index is older than the current QMD index; QMD stays in use and nothing was removed". Do not retry activation. On the user's request to continue this reviewed transition, use `retire-index-origin` with `--approve-index-origin-retire` for the old state directory. It confirms the old binding is unselected and drifted, marks it retired, preserves its source, backup, stores, journal and evidence, and releases only its own project marker and build pointer. Then create a new state directory and install ID, run a fresh plan and provider review, and prepare a new inactive build with the newly reviewed digests. Reusing the retired state directory or its route is refused. A changed plan, journal, file identity, or uncertain route blocks retirement for investigation; never remove a marker or pointer by hand. An interruption resumes through the same retirement action. A mismatch outside this explicit drift path requires `recover-index-origin` or a fresh review; never overwrite or delete the source DB, model, wiki, manuscript, settings or learning state.

Only after candidate verification and the user's installation/activation authorization, use `activate-index-origin` with its explicit activation flag. Activation also requires the build record to be bound to exactly the ledger's freshly sealed generation (`activation_requires_fresh_generation` / `initial_build_bind_unsettled` otherwise). On success it queues one selected Laya sync and reports it as `syncWake`. That sync catches up edits made after the sealed snapshot; report it as queued, not as completed. Then verify the host loads that same exact commit and route, performs selected search and off-hook sync through the owned worker, and records L1 QA.

When the user asks to go back to QMD, undo or withdraw the Laya Index transition (for example “Laya 인덱스 전환을 되돌려줘” or “QMD로 복원해줘”), name the project root and state directory. Then, on that explicit request, run `restore-index-origin --project "$PROJECT_ROOT" --state-root "$STATE_ROOT" --approve-index-origin-restore`. It first checks that the cutover ledger, the private install journal and the reviewed route agree. It restores only while no selected Laya write has been seen, and it settles an interrupted activation or restore through recovery. It accepts the result only when the ledger phase, journal state and selector agree. `qmd_restored` and `qmd_selected` (nothing to withdraw) mean QMD is in use. `blocked` with `rollback_forward_only` means Laya already took a new write and stays selected. `recovery_required` reports the observed phase after one bounded attempt. Show it as is and do not retry in a loop. Restore removes only the exact route file this cutover published. The QMD database, every backup, the candidate stores, the ledger and the marker are kept. A private bundle copy or successful preparation alone is not host installation evidence. Do not expose the lower-level installer `stage` JSON interface as a setup procedure, and do not start learning as a side effect of this transition.

## Explicit local learning profile

Ordinary `plan-install` offers a recommended `local-auto-apply` profile; omission of `--learning-choice` preserves existing behavior and accepts nothing. Explain the choices in natural language: local learning plus validated candidate application, staged local learning only (`local-staged`), or disabled (`off`). A profile requires an already prepared private namespace, local runtime/model and inference identity, and a separate current train/evaluate execution grant. Missing preparation or corpus authorization remains review-required; do not create a grant, import data, download weights or call a teacher to satisfy it.

For an explicitly selected profile, run `plan-learning-profile --project "$PROJECT_ROOT" --learning-namespace "$APPROVED_NAMESPACE" --learning-choice local-auto-apply --learning-migration new --learning-expires-at-unix-ms "$REVIEWED_EXPIRY"` through the same verified `python3 "$ROOT/core/setup_entry.py"` entry. Use `preserve` migration for an existing learning configuration; never switch to `new` to escape existing false choices. Show the proposal's actual settings changes, project/source/cohort and runtime/model scope, resource/batch/disk limits, expiry and application authority. Existing explicit false capture/autoCycle/live selection/shared learning/application choices stay false. New capture defaults false. Application requires at least the existing quality-sized fresh batch within the approved batch cap; an insufficient cap needs separate budget review. No profile expands external transmission or source scope.

Only on acceptance of that exact proposal, use `activate-learning-profile` with identical options plus `--accepted-learning-profile` equal to its `proposalSha256`. Never infer acceptance from the recommendation, installation approval, a prior train/evaluate grant or live selection. `install` also accepts these explicit learning options, but requires that same exact digest before execution. If installation changes settings and returns `qmd_ready_learning_profile_review_required`, report QMD ready and learning pending review. Generate a fresh proposal from current settings and obtain exact acceptance; do not reuse or retime the old acceptance. An interrupted profile activation resumes with the identical accepted options; changed scope/expiry/settings require review.

Report selected, waiting, deferred, blocked, staged and applied states separately. A selected profile is not evidence that real training, model replacement or host-hook operation passed. Service registration/login startup and actual hardware/host validation remain separate rollout work. Keep installed packages, operating flags, grants and checkpoints unchanged unless that specific deployment is authorized.

The `update` skill refreshes an already configured index; it does not replace this setup flow. Never activate a teacher, private checkpoint, or operating plugin hook as a side effect of preparing a runtime. Private model quality/learning activation requires its separate policy and review.
