# 설치 증명과 번들 업그레이드

- `laya_ledger_common.py` — 선택 ledger 공용 primitive(비공개 JSON 읽기·쓰기, ledger lock, 프로젝트 단위 operation lock `laya-qmd-cutover-operation.lock`, multi settings preflight). fresh-wiki ledger·`_select_route`·active/bound/inactive 업그레이드가 이 모듈을 import한다. state root에 QMD-origin ledger(`qmd-cutover.json`)가 남아 있으면 `refuse_qmd_origin`이 `qmd_origin_detach_required`로 거절하고, `_select_route`는 QMD-origin marker를 같은 사유의 `blocked`로 분류한다. lock 파일 이름은 구버전 호스트 사본과의 상호 배제 계약이라 바꾸지 않는다.
- `laya_bundle_upgrade.py` — 호스트 플러그인 업데이트 뒤 memvane-db 설치를 실행 중인 번들로 옮기는 자동 업그레이드. 선택 프로젝트의 SessionStart(`laya_host_response`)가 `request`로 상태 파일(`<state>/bundle-auto-upgrade.json`)을 읽고 필요할 때만 detached worker(`run`)를 띄운다. worker는 프로젝트의 route·build pointer가 가리키는 state root만 다룬다: inactive(sealed는 freshness 요청 후)→`laya_inactive_upgrade`, bound→`laya_bound_upgrade`, 선택(fresh-wiki)→`laya_active_upgrade` 후 sync wake. QMD-origin ledger가 남은 state root는 `qmd_origin_detach_required`로 거절한다(재시도로 풀리지 않는 `REFUSALS`). 소스는 호스트 marketplace clone(Claude `~/.claude/plugins/marketplaces/<mkt>`, Codex `~/.codex/.tmp/marketplaces/<mkt>`)뿐이며 HEAD가 호스트 기록(Claude `installed_plugins.json` `gitCommitSha`, Codex 캐시 clone HEAD)의 설치 커밋과 같고 추적 파일이 깨끗할 때만 쓴다. provider review는 다시 돌리고 이전 attestation과 번들 파일 경로(`providerPath`·`workerPath`)만 다를 때 자동 수락한다. 모델·런타임·closure·provider 바이트가 바뀌면 `provider_changed_rebuild_required`로 거절하고 안내만 남긴다. 설치 커밋이 바인딩 커밋의 조상이면 `older_host_bundle`로 거절한다(호스트 간 왕복 방지). 같은 커밋의 다른 호스트 캐시는 route를 바꾸지 않고 `seal_companion_host_copy`로 봉인한다. worker가 Codex 캐시에 실제 seal을 쓰면 `bundle.upgrade`에 `codexSealWritten`을 기록한다. Claude SessionStart는 해당 설치의 최근 24시간 이벤트를 최대 1 MiB 읽어 seal 이후 안내가 없으면 Codex hook 재승인이 필요할 수 있음을 알리고 같은 이벤트 종류에 안내를 기록한다. 로그 회전·유실로 안내가 빠지거나 중복될 수 있다.
- `laya_bound_upgrade.py` — bound 빌드(`prepared` fresh-wiki 선택 ledger)의 번들 교체. route·attestation·journal pending과 이를 가리키는 ledger·marker·build record 다이제스트만 바꾸고 세대·벡터 프로필·저장소는 그대로 둔다. 전환 중에는 selector가 `blocked`로 읽고, 중단되면 intent로 같은 동작이 이어서 끝낸다. 아무 파일도 바꾸기 전에 멈춘 intent(`_unswitched`)의 번들이 요청 번들과 다르거나 사라졌으면 요청 번들로 다시 증명해 intent를 교체하고, store counts가 같고 그 backup의 저장소 핀이 낡지 않았으면(`_pins_stale`) backup을 재사용한다. 완료 receipt가 durable해지면 그 backup을 지운다.
- `laya_active_upgrade.py` — 선택된 memvane-db의 번들 교체. fresh-wiki(`fresh-wiki-cutover.json`) ledger를 intent·fence(`upgrading`)·backup 경로로 처리한다. `origin: qmd` intent는 `qmd_origin_detach_required`로 거절한다. 이전 번들 캐시가 이미 지워졌으면 전진만 허용하고 이전 번들 복원은 거절한다. fence 전 intent 봉인(`_seal_reader_intent`)은 선택된 reader record(v6·schema3)를 새 번들 attestation으로 함께 봉인한다. fence 전에 멈춘 intent(`_prefence_intent`: ledger가 intent의 old row 그대로, journal이 old route를 선택하고 pending 없음)는 receipt가 아니다. 다른 번들(또는 다시 풀린 같은 root)이 요청하면 그 대상으로 다시 증명해 intent를 교체하고 새 intent로 reader를 봉인한다. store counts와 journal snapshot이 그대로고 저장소 핀이 낡지 않았으면 backup을 재사용하고, 그 사이 선택 route가 sync했으면 backup을 새로 뜬다(교체된 intent의 이전 backup은 지우지 않는다). settle된 intent는 다음 업그레이드나 state move가 archive할 때 receipt만 확인하고(`_backup_proof(..., archive=True)`) 같은 단계에서 그 backup을 지운다. 선택 record가 이전 state base(`~/.local/state/laya`)를 가리키는 v6 record로 남은 설치는, settled state move intent·attestation 재배치·inode·incarnation·settings·roots가 모두 일치할 때만 같은 이미지 트랜잭션에서 재봉인하고 아니면 `reader_relocation_unproved`로 거절한다. pending 뒤 대상이 바뀌면 v2 intent의 유계 descriptor로 route만 정규화하고 새 대상을 정상 재증명한다. 원래 snapshot·counts를 유지하고 매 metadata 쓰기 전에 journal의 project dev/ino를 확인한다. v2 복구는 forward-only이며 계약은 `docs/development-active-upgrade-recovery.md`에 있다.
- `laya_inactive_upgrade.py`의 업그레이드 백업(`inactive-upgrade-backup-*`, receipt `laya-inactive-upgrade-backup-v2`) — inactive·bound·active 업그레이드가 공유한다. 업그레이드는 메타데이터만 다시 묶고 어떤 restore도 백업에서 저장소 바이트를 읽지 않으므로, journal만 SQLite 온라인 백업으로 복사하고 다섯 저장소(candidateDb·queueDb·catalogDb·bindingStore·incrementalDocs)는 핀만 남긴다. 핀은 inode와 한 읽기 스냅숏의 논리 증거(application_id·user_version·page_size·DDL SHA, 작은 식별 테이블의 행 SHA, rowid 테이블별 최대 rowid SHA)다. `dev`·크기·mtime·page/freelist 수는 기록만 하고 비교하지 않는다(APFS `st_dev`는 부팅마다 바뀌고, 읽기-쓰기 close의 WAL checkpoint와 v6 recall의 `pins` 읽기 lease 행은 내용 변화 없이 이 값을 바꾼다). catalogDb·queueDb는 inode와 schema만 대조한다. settle 뒤 sync pass는 첫 새 쓰기를 journal에 표시(`before_publish`)하기 전에 카탈로그를 스캔하고 claim을 남기며, 두 저장소의 binding은 `_store_counts`가 다시 확인한다. `_verify_backup`은 백업 디렉터리 자체(receipt·journal 복사본 SHA)만 증명한다. settle된 intent의 저장소는 계속 sync되기 때문이다. 핀과 라이브 저장소의 대조는 restore가 메타데이터를 되돌리기 전에 하고, 다르면 아무것도 되돌리지 않고 `inactive_upgrade_backup_changed`로 fence를 유지한다. 메타데이터를 되돌린 뒤 fence가 남아 있는 동안 한 번 더 확인한다. 저장소 검사(`_store_counts`)는 page scan·전체 COUNT 없이 schema·binding 행과 최대 rowid만 읽는다(`countsSchema: laya-store-tails-v1`). 0.44.15 이하 번들이 남긴 v1 receipt(전체 복사본)와 정확한 행 수를 담은 intent는 그대로 검증·복원되며, 그런 미완료 intent를 재개할 때만 이전 방식(quick_check·COUNT·복사본 SHA-256)으로 대조한다. settle된 intent를 archive할 때는 같은 단계에서 백업을 지우므로 receipt와 복사본 파일 상태만 확인하고 복사본을 다시 해시하지 않는다(`_verify_backup_receipt`). 업그레이드 receipt가 durable해지면(inactive `_retire_intent`, bound complete rename, active `_archive_finished_intent`) 그 업그레이드 자신의 백업을 지운다. 살아 있는 intent가 가리키는 백업과 다른 오래된 백업은 지우지 않는다. 단계는 install 이벤트 로그에 `bundle.upgrade` 행(outcome `backup.start`·`backup.done`·`verify.start`·`verify.done`·`activate.done`·`store_check.done`·`backup.deleted`·`backup.kept`, 30초 이상 걸리는 복사·해시는 `*.progress`의 `bytesDone`/`bytesTotal`)으로 남고 worker의 `operation`·`kind`가 붙는다.
- `laya_product_install.py`의 fresh prepare(`prepare_fresh_wiki_origin`)는 review digest를 확인한 뒤 두 state base 아래 모든 설치 디렉터리(중단 뒤 재실행에 대비해 자기 설치 포함)의 소유자 전용 attestation을 donor 후보로 읽고 `reattest`로 내용 동등성을 증명한다. 동등한 donor가 있으면 새 설치는 기존 설치들의 벡터 프로필로 합류하고 attestation에 `profileDependencyClosure`를 싣는다(결과의 `profileDonor`). 봉인된 번들은 자기 봉인 프로필의 donor만 받는다. 미봉인 번들에서 서로 다른 동등 프로필(review 자신의 프로필을 가진 설치도 센다)이 둘 이상이면 `fresh_profile_donor_ambiguous`로 거절하고, 다른 동등 프로필이 없으면 review 프로필을 그대로 쓴다. 봉인 메타데이터가 검증되지 않는 번들은 미봉인으로 보고 adopt가 다시 봉인한다. review 경로의 프로필은 런타임 절대 경로에서 파생되므로, 이 합류가 없으면 옮겨진 런타임에서 새 설치가 봉인 번들에 `installed_candidate_already_owned`로 거절되거나 미봉인 번들을 기존 설치가 업그레이드할 수 없는 프로필로 봉인한다.
- 번들 불일치 중 읽기 — 전체 증명이 번들 정체성(`laya_install_journal.BUNDLE_DRIFT_CODES`)에서만 실패하면 `verify_selected_route_read_only`가 route·journal·저장소 incarnation·봉인된 attestation만 다시 증명하고, recall은 마지막 게시 세대를 읽기 전용으로 제공한다(warm owner가 없으면 lexical만. schema3 endpoint는 이 읽기 전용 증명에서 query vector를 요청하지 않고 lexical로 답한다. 번들 증명이 서는 연결 워크트리 읽기는 vector를 쓴다). sync·compile·index wake는 기록하지 않고, SessionStart는 실제 사유를 담은 한 줄 안내를 낸다. hook stderr는 `JournalEvidenceError` 코드를 그대로 보고한다.
