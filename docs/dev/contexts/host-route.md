# Host 응답과 route

선택 프로젝트 레지스트리(`core/memvane_registry.py`, `~/.local/state/memvane/auto-context/registry/projects.sqlite`)는 선택된 main checkout과 연결 worktree 경로의 조회 색인이다. 행은 후보일 뿐이고 소비자는 기존 route 증명을 다시 한다. 활성화 성공 뒤 setup이 등록하고, restore·retire·abandon 성공 뒤 재관측으로 해제가 증명될 때만 `detached`로 바꾸며, 선택 route의 SessionStart와 `snapshot()`이 유계 reconcile을 한다. journal·route·ledger·store·intent를 쓰지 않고 새 lock·wake kind·hook action이 없다. resident service는 레지스트리를 다루지 않는다. 외부 편집 대상 탐색이 이 색인을 쓴다. 상태 규칙·예산·실패 방향은 `docs/project-registry.md`에 있다.

프로젝트 밖 원문 편집은 `core/laya_external_edits.py`가 소유 설치의 journal·route·번들 메타데이터만 증명해 private blob 알림과 `laya-sync` wake를 전달한다. 외부 색인·claim DB는 훅에서 열지 않는다. 소유 sync 워커가 전체 write 증명·현재 blob·설정·compile 동의를 다시 확인한 뒤 기존 source 큐와 삭제 수명 주기로 넘긴다. recall과 로컬 compile 범위는 세션 프로젝트를 따른다. 범위·상한은 `docs/out-of-project-edit-routing.md`에 있다.

host route: `hooks/run-hook`은 등록된 모든 action을 먼저 `core/laya_index_host_route.py classify-hook`으로 분류한다(`legacy|candidate|preview|worktree|blocked`). 선택된 Laya route(candidate/preview)는 `core/laya_host_response.py serve-stdin`이 응답하고, 그 검색은 위키 전용이며 질의 시점에 원문을 다시 읽지 않는다. `worktree`는 선택된 main checkout의 연결 git 워크트리(같은 common git dir, 같은 settings 유도 정체성, 워크트리 안에 route 기록 없음)다. 검색 대상은 main checkout journal이 선택한 reader 형식이 정한다. v6 reader가 선택돼 있으면 main checkout의 게시 세대를 읽기 전용으로 검색하고 결과 앞에 그 사실을 적으며, sync·compile·index wake·학습·setup 안내는 하지 않는다. schema3 reader가 선택돼 있으면 같은 view store 안의 그 워크트리 자기 view만 읽고(`laya_journal_reader._schema3_pin(linked=…)`) 결과 앞에 자기 view라는 사실을 적는다. 게시된 head가 없으면(처음 보는 워크트리·브랜치) `view_preparing`, 읽는 동안 checkout이 두 번 바뀌면 `checkout_changed`로 컨텍스트 없이 exit 0이며 main view나 다른 view로 폴백하지 않는다. 이때 SessionStart·성공한 편집(`index`)·성공한 Bash(`file-change-event`)는 main checkout의 `laya-sync` wake를 기록하고, main의 sync owner가 main view를 게시한 뒤 `git worktree list` 순서로 연결 워크트리 view를 pass당 최대 16개 등록·게시한다. recall은 wake를 남기지 않으므로 `git switch` 직후에는 다음 SessionStart나 편집이 wake를 남길 때까지 `view_preparing`이다. 두 형식 모두 wiki compile·수명 주기·학습은 main checkout에서만 돈다. blocked는 QMD로 폴백하지 않고 exit 3으로 끝난다. 예외는 번들 업그레이드 fence(fresh-wiki ledger `upgrading`)에 걸린 recall이다. `laya_fresh_wiki_origin.settle_decision`이 최대 1.5초 route를 다시 읽고, 그래도 fence 중이면 classify-hook이 `upgrading`을 내 run-hook이 컨텍스트 없이 exit 0으로 끝낸다. recall 도중 fence에 걸린 실패, 그리고 worker status `running`·`complete` 뒤 30초 안의 route·proof 전환 오류(`selected_route_changed` 등)도 core는 exit 0이다. 그 밖의 오류는 그대로 exit 3이다. fence를 만난 recall과 SessionStart는 업그레이드 worker에 마무리를 요청하고, 요청은 설치당 60초에 한 번이다(호스트 사본과 무관). ledger mtime 기준 10분이 지났거나 미래인 fence는 멈춘 업그레이드다. recall은 기다리지 않고 컨텍스트 없이 exit 0으로 끝나고, SessionStart가 멈춤을 한 줄로 알린다. worker는 journal 활성화 뒤 fence 해제 전에 멈춘 업그레이드(`laya_active_upgrade.finish_activated`)도 끝낸다. `legacy`(선택된 route 없음, 즉 미온보딩)는 인덱스·recall·compile·학습 작업을 하지 않는다. SessionStart(`update-queued`)에서만 프로젝트 폴더에 `settings.json`이 있는 프로젝트에 setup skill 온보딩을 안내하는 한 줄을 낸다(`laya_index_host_route.py onboarding-notice`, Codex는 SessionStart JSON으로 감싼다). 안내는 경로 없는 사용자용 한 줄과 거절 명령(argv·shell)을 담은 `[memvane] onboarding-answer <JSON>` 한 줄로 나간다. 사용자의 거절은 `setup_entry.py onboarding-skip`(payload session id 한정, 30일 보존)·`onboarding-never`(프로젝트 영속)로 `~/.local/state/memvane/onboarding/<sha256(canonical project root)>.json`에 기록되고 그 안내만 숨긴다. canonical root는 resolve 후 파일시스템 표기(macOS `F_GETPATH`)라 대소문자 별칭이 한 기록을 쓴다. `onboarding-resume`이 기록을 지운다(`core/onboarding_choice.py`). 수동 query/update skill과 wiki-compile wrapper도 선택된 route에서만 동작한다.
- `laya_host_response.py` — 선택된 Laya route의 hook 응답(`recall`·`update`·`update-queued`·`gate`·`posttool`·`index`·`compile` 등). 설치 journal이 설치된 플러그인 전체를 증명한 뒤에만 runtime을 열고, 증명이 바뀌면 실패한다(fail-closed). `wiki_card.py`는 선택 경로와 위키 worker가 공유하는 카드 읽기 헬퍼(frontmatter 파싱·source 해석·본문 추출)다. `event_log.py`는 설치 이벤트 로그(`<state root>/events.jsonl`) writer·reader이고, recall 진단은 `laya_host_response._event_scope`가 hook 호출당 한 줄로 남긴다.
- `posttool.py` — 편집 hook payload helper(편집 경로·apply_patch 추가 텍스트 추출, `is_story_path`는 config의 `collectionPaths`로 판별). hook entrypoint가 아니고 `wiki_compile_enqueue`가 import한다.
- `hook_main.py` — **모든 Python hook entrypoint의 단일 fail-safe 경계.** hook은 항상 exit 0이어야 하고(deny는 stdout JSON, non-zero exit이 아님), main() 콜트리에서 새는 어떤 예외든 host가 "hook (failed): exited with code 1"로 표면화한다. Python hook entrypoint(`wiki_compile_enqueue`)의 `__main__`은 `sys.exit(hook_main.run(main))` 형태로 이 wrapper를 거친다. run()은 예외를 삼켜 0을 반환하고, entry point가 `event_log.bind`로 묶은 설치가 있으면 `hook.error` 이벤트(예외 클래스와 file:line, 메시지 제외)를 남긴다(stdout 오염 없음). **새 Python hook entrypoint를 추가하거나 `__main__`을 만질 때 반드시 이 wrapper를 거치게 한다** — per-site try/except는 다음 편집에서 빠뜨리기 쉬워 이 클래스 버그가 반복됐다(exit 127/1 계열).
### hooks (`hooks/`) — 유일한 훅 진입점
> Claude/Codex/Gemini의 훅 진입점은 `hooks/run-hook` 단일 디스패처다. Hermes Agent는 별도 host protocol이므로 Python plugin adapter(`plugin.yaml`, `__init__.py`, `hermes_adapter/`)가 같은 core 스크립트를 호출한다. **도메인 로직은 여전히 core/가 SSOT**다.

- `run-hook` — 공통 디스패처(bash). 호출: `run-hook <action> <engine>` (engine: claude|codex|gemini). `hooks.json`·`hooks-codex.json`이 등록한 action은 `update-queued`(SessionStart), `recall`(UserPromptSubmit), `gate`(PreToolUse), `posttool`·`index`·`compile`(PostToolUse 편집 도구), Claude 전용 `file-change-event`(PostToolUse Bash)다. 처리 순서: sandbox/headless 가드 → 모든 action을 `core/laya_index_host_route.py classify-hook`으로 분류 → `candidate|preview|worktree`면 `core/laya_host_response.py serve-stdin`으로 exec, `blocked`(또는 분류 실패)면 "request refused"로 exit 3, recall의 `upgrading`(번들 업그레이드 fence)은 컨텍스트 없이 exit 0, `legacy`면 무작업 exit 0. `legacy`의 `update-queued`만 `core/context_learning_host_ack.py`를 돌리고 온보딩 안내 한 줄(`onboarding-notice`)을 출력한다. 플러그인 루트는 env `CLAUDE_PLUGIN_ROOT`/`PLUGIN_ROOT`가 우선이고 없으면 `dirname "$0"`이다. **도메인 로직은 core/가 SSOT.**
- `hooks.json` — Claude hooks (`${CLAUDE_PLUGIN_ROOT}`). `hooks-codex.json` — Codex hooks도 **`${CLAUDE_PLUGIN_ROOT}`**를 쓴다(형태: `"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook" <action> codex`). Codex가 신뢰성 있게 주입하는 plugin-root 변수가 CLAUDE_PLUGIN_ROOT이고, 로컬 캐시의 OpenAI codex·zax·superpowers 등 **모든 codex 플러그인이 codex hooks에서 이 형태를 쓴다**(shell 확장이든 텍스트 템플릿 치환이든 양쪽 메커니즘에서 입증된 유일한 형태). `${PLUGIN_ROOT}`(codex 바이너리가 인식하는 alias지만 간헐적으로만 주입)를 단독으로 쓰면 비었을 때 command가 `/hooks/run-hook`으로 해석돼 **exit 127**(command not found)이 난다 — 실패 지점이 command 확장 단계라 run-hook 내부 dirname fallback으로는 못 막는다. **novel한 `${VAR:-fallback}` 파라미터 확장이나 `;`/`&&` 제어 연산자는 쓰지 않는다**: 어떤 codex 플러그인도 안 쓰는 문법이라, codex가 shell이 아니라 템플릿 치환을 하면 매칭/해석에 실패할 수 있다. run-hook 내부는 여전히 `CLAUDE_PLUGIN_ROOT→PLUGIN_ROOT→dirname` 순서로 방어한다(도달만 하면). CLAUDE_PLUGIN_ROOT 자체가 비면 여전히 127인데, 이는 codex-level 상태로 OpenAI 공식 포함 모든 codex 플러그인에 동일하게 영향한다(우리만의 문제 아님). PreToolUse `gate`도 이 경우 127로 죽어 deny를 못 내므로 pending 편집 차단이 fail-open된다(수용 가능한 트레이드오프). Codex 공식 문서상 same-event command hooks는 동시 실행될 수 있으므로 posttool/index/compile은 서로 순서 의존하면 안 된다.
- Antigravity(agy)는 공식 PostToolUse payload에 edited file path/tool input이 문서화되어 있지 않고 stdout contract도 `{}`라서, AGY 자동 hook은 설치하지 않는다. AGY 자동 posttool/index/compile은 전용 payload adapter가 생긴 뒤 재활성화한다.
- `hooks.json`은 **표준 구조** `{hooks:[{type:"command",command}]}`를 따라야 한다. 비표준 구조면 호스트(Claude/Codex)가 훅을 인식 못 함.
- 매니페스트: `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`(+`interface`, `hooks` 경로 명시).

### Hermes Agent plugin (`plugin.yaml`, `__init__.py`, `hermes_adapter/`)
- Hermes는 Claude/Codex hook JSON을 읽지 않고 Python plugin system을 쓴다. root `plugin.yaml` + `__init__.py`가 `hermes_adapter.plugin.register(ctx)`를 노출한다.
- Hook mapping: `pre_llm_call`→`recall`, `on_session_start`→`update-queued`, `pre_tool_call`→`gate`, `post_tool_call`→`posttool`+`index`. `hermes_adapter/core_bridge.py`가 route를 분류해 선택된 route에서만 `laya_index_host_route.select_route` → `laya_host_response.serve_selected`로 넘긴다. `legacy`는 무작업이고, 그 밖의 상태는 경고만 남기며 QMD로 폴백하지 않는다(gate는 block).
- Hermes `post_tool_call` 반환값은 observer-only라 같은 턴 모델 컨텍스트에 posttool 힌트를 주입하지 않는다. 따라서 Hermes 경로의 편집 후 동작은 자동 인덱싱 중심이며, Claude/Codex posttool 컨텍스트 주입과 동일하다고 문서화하면 안 된다.
- reader 전환(`laya_shadow_migration`)의 loaded receipt는 Claude·Codex recall hook만 남긴다. 현재·이전 플러그인 id의 Hermes 사본이 설치된 계정에서는 전환 게이트가 `switch_hosts_unsupported`로 멈추고 그 설치는 v6 reader를 계속 읽는다.
- Hermes `on_session_start`도 context 주입 채널이 없어(반환값 미사용) SessionStart 안내가 표면화되지 않는다. 미온보딩 프로젝트의 온보딩 안내도 Hermes에는 나가지 않는다.
