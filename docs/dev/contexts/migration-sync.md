# Migration과 sync 게시

- schema3 sync 게시(`laya_product_sync_worker._run_schema3`) — schema3 reader가 선택된 설치의 `laya-sync` pass는 v6 runtime을 열지 않는다. sync owner와 worker writer scope 아래 main view를 먼저, 그다음 연결 워크트리 view를 게시한다. 연결 워크트리 view의 collection root는 그 워크트리의 활성 프로젝트 폴더를 가리킨다(main이 `.memvane`이고 그 브랜치가 `.auto-context`이거나 그 반대여도 된다). store가 그 view의 decision을 거절하면(`attestation_decision_mismatch`) 그 view만 held로 남고 pass와 main 게시·reader 재봉인은 이어진다. 바뀐 카드만 `ingest_attested_card`로 넣고(pass당 64장·45초) 같은 바이트의 member는 trust를 유지하며, 카드의 `sourceRevisions`가 한 원문 경로를 서로 다른 (sha256, 크기)로 두 번 이상 인용하면 같은 pass의 raw 관측이 완료된 경우에만 현재 바이트와 맞는 revision 하나를 attestation에 남기고 맞는 것이 없으면 카드를 untrusted로 넣는다(`laya_blob_store.current_revision_evidence`, 관측 상한 초과나 관측 밖 경로는 판정하지 않고 재생성은 `wiki_lifecycle`이 맡는다), 다른 worktree·branch view의 trust는 빌리지 않는다. 게시 head가 없는 cold view는 완료 전까지 게시하지 않는다. view binding은 settings 정체성(v6 route의 `settings_identity_digest`와 같은 범위)과 wiki root dev/ino이고, `skipPaths`는 binding 밖이라 pass마다 현재 settings에서 읽는다. 대량 삭제는 `schema3_mass_removal_held`로 보류한다. manifest의 `sources`는 같은 pass의 유계 raw 관측(4,096 파일·64 MB, 넘으면 빈 목록)이고 wiki discovery가 그 관측을 재사용한다. vector는 lexical 세대를 먼저 게시한 뒤 설치 provider spec으로 fill하고(cursor 재개), 완료되면 vector 세대를 게시한다. pass의 첫 cold target(chunk set 없음)은 chunk set이 있는 target처럼 resume 예산(`SCHEMA3_RESUME_SECONDS`)을 한 번 받고, 앞 작업이 pass 예산을 다 써도 그 target은 시도한다. main view에 ingest할 카드·원문 변경이 없는 pass는 vector fill과 그 뒤 vector 세대 게시에 240초 창(`SCHEMA3_VECTOR_SECONDS`, publish reserve 포함)을 쓰고, 창 안에서 자기 deadline에 걸린 fill 호출이 embedding set을 남겼으면 다음 호출로 이어 간다(아무것도 남기지 못한 호출은 pass를 끝낸다). 카드를 ingest한 pass와 연결 view는 pass 예산 그대로다. 첫 미완 target 앞 cache hit 구간이 `MAX_FILES`를 넘으면 한 호출로 넘기고, provider 호출마다 그 앞에서 owner를 기다리는 다른 프로젝트의 초기 빌드(`_initial_build_waiting`, v6 capacity 경로와 같은 판정)에 양보하고(`laya_sync_yield_priority`), main view vector가 그 pass에 embedding set을 늘리고 끝나지 않으면(이 양보·provider 실패로 멈춘 경우 포함) 결과를 ACK하고 같은 `laya-sync` wake를 30초 뒤로 다시 offer한다(진척이 없으면 pending으로 남아 backoff하고, 연속 144회면 wake 정책의 `retry_cap`으로 지워져 다음 편집·SessionStart wake를 기다린다). main이 진척했거나 vector 세대를 게시한 pass에서 pass 예산으로만 남은 연결 view(`schema3_pass_budget`)는 결과를 pending으로 만들지 않고 같은 30초 재offer를 받는다. 마지막 fill 호출이 pass deadline을 넘기면 그 pass의 세대 게시는 새 publish reserve를 받는다. `wake.sync` detail은 main view vector 상태(`vec_<state>_<사유>`·`rem`·`ord`·`pms`·`pub`·`res_`)를 담는다. main view의 첫 vector 세대 뒤 owner가 `resettle_selection`으로 endpoint에 vector spec을 봉인해야 recall이 query vector를 요청한다. provider가 token window로 다시 쪼개는 카드가 하나라도 있으면 그 view는 그 카드가 바뀔 때까지 lexical 세대로 남고(`chunk_text_unreconstructable`), recall은 `laya_vector_selected_view_vectors_pending`을 남긴다. provider 정체성을 증명할 수 없으면 wake가 `blocked`(`provider_blocked`)로 끝나고 일시적 거절은 `deferred`다. 같은 설치의 외부 편집 drain·wiki discovery·dedup retrieval·학습 corpus는 view head를 읽고, retroactive dedup scan은 view vector가 없으면 고정 사유로 건너뛴다.
- 모든 선택 sync와 초기 빌드는 사용자당 하나인 sync owner 잠금을 함께 쓴다. 초기 빌드(`_build_rounds`)는 선택 sync처럼 그 잠금을 짧게(`SYNC_OWNER_WAIT_SECONDS`) 기다려 잡고 그 owner로 `sync_step`을 돈다. 선택 sync(`_sync_capacity`)는 라운드 사이에 다른 프로젝트의 초기 빌드가 owner에 막혀 있는지 (`_initial_build_waiting`: pending `laya-sync` row, 빌드 phase `registered`/`building`, 마지막 시도가 `INITIAL_BUILD_YIELD_RECENT_SECONDS` 안에 정상 deferred `owner_busy`로 끝남) 확인하고, 그렇다면 그 기존 wake를 `WakeQueue.pull_first`로 due 0에 당긴 뒤(row를 새로 만들지 않음) `laya_sync_yield_priority`로 양보한다. 초기 빌드끼리는 서로 양보하지 않는다. 예외로 끝난 시도(이전 reason에 `lastAttemptReason`을 더한 기록), 다른 이유로 실패하는 빌드, 재시도되지 않는 오래된 기록은 긴 sync를 붙잡지 않는다.
