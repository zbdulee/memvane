# 설치·정리와 내부 명명

임베딩 모델과 학습 추론은 사용자당 하나인 `core/laya_resident_service.py` 프로세스가 호스팅한다. 이 서비스가 각 설치의 `runtime/laya-embed.sock`과 owner lease를 넘겨받아 단일 worker로 응답하고, 더 새 버전 번들이 요청하면 drain 후 교체된다. 같은 릴리스의 설치가 두 host 사본(owner와 봉인된 companion)에 나뉘어 묶여도, 서비스는 자기 사본이 아닌 쪽 v5 설치를 자기 사본과 같은 v5 queue owner·lifetime·physical window 안에서 hook과 같은 full selected proof(`laya_embed_resident._companion_selected`)로 증명해 worker를 붙인다. v5 writer plan의 정확한 root 요구는 writer에만 남는다. worker가 없고 full proof가 로딩 또는 재시도 중이면 `read_only_no_worker` drift 설치의 재증명은 최대 30초 미루고 worker가 준비되면 깨운다. full proof는 기존 owner lock 대기를 사용하며 drift 증명은 worker를 시작하지 않는다. 계약과 자원 조율은 `docs/runtime-resource-coordination.md`를 따른다.
### 설치 / cleanup
Claude·Codex는 marketplace plugin install이 제품 경로다. 제품용 `install.sh`/`uninstall.sh`는 없다. AGY는 공식 PostToolUse payload adapter 전까지 자동 hook을 설치하지 않는다.

새 머신의 Laya embed runtime은 `setup_entry.py provision-index-runtime --approve-index-runtime-download`가 만든다(`core/laya_embed_runtime.py`). Node는 `PATH`를 먼저 보고 mise/fnm/nvm/volta/asdf/Homebrew/system 설치 순으로 찾되 메이저 22/24/26의 실제 바이너리만 받는다(버전 매니저 shim은 거절). `locks/laya-embed-runtime`(node-llama-cpp 3.18.1 + prebuilt `@node-llama-cpp/mac-arm64-metal`)를 `npm ci --ignore-scripts`로 설치하고, GGUF는 `https://huggingface.co/ggml-org/embeddinggemma-300M-GGUF/resolve/main/embeddinggemma-300M-Q8_0.gguf`에서 받아 sha256 `f470220f84b6235197541352d22f10bf00098a8242c18eaacea9c8a4add557bc`과 일치할 때만 채택한다(`--provider-model-file`로 같은 GGUF의 로컬 사본 지정). 결과는 `~/.local/state/memvane/embed-runtime`의 세대 디렉터리와 `active.json`·`previous.json`이다. 기존 설치의 자동 번들 업그레이드는 attestation의 `runtimeFilesSha256` 또는 소유 Laya generation에서 유도한 전체 파일 digest가 있어야 ensure를 호출한다. 외부 경로를 가리키는 attestation도 이 digest를 명시하면 해당 바이트를 Laya runtime으로 복사하고 재검증할 수 있다. 전체 digest가 없으면 ensure 전에 `provider_changed_rebuild_required`로 거절한다. `gc-index-runtime`은 active·previous·`~/.local/state/memvane/*/production-provider-attestation.json`이 가리키지 않는 세대를 나열하고 `--approve-index-runtime-gc`가 있을 때만 지운다(attestation의 과거 `profileDependencyClosure` 행은 보지 않는다).

은퇴한 QMD 백엔드 정리는 owner가 한 번 수동으로 하는 작업이고 hook·worker·플러그인 업데이트에서는 돌지 않는다(`core/legacy_cleanup.py`). Claude·Codex 호스트 캐시가 모두 이 릴리스를 로드하고, 모든 설치가 SessionStart 번들 업그레이드로 이 번들에 옮겨지고, 모든 설치가 Laya embed runtime으로 재증명된 뒤에 실행한다. `plan-legacy-cleanup`(read-only)은 `~/Library/Application Support/qmd-auto-context/backend/daemon-*.pid`(포트 없는 구 `daemon.pid` 포함)와 각 pid가 검증된 살아 있는 데몬인지, `managed-by: qmd-auto-context` 마커가 있는 LaunchAgent(`com.qmd-mcp-daemon`·`com.qmd-keepalive`·`com.qmd-logrotate`·`com.qmd-index-worker`, `.bak` 사본은 건드리지 않음), 대상 트리와 크기, 차단 사유를 보여 준다. 차단 사유는 대상 안 파일을 가리키는 install attestation(`attestation_references_legacy_path`), `~/.local/state/memvane/*/reviewed-route.json`의 `pluginRoot`가 아직 `core/backend_manager.sh`가 있는 구 번들을 가리키는 경우(`older_host_bundle_bound` — 구 번들은 `~/.cache/qmd`·`~/.config/qmd`를 다시 만든다), 심볼릭 링크 대상(`legacy_cleanup_target_symlink`), HOME에서 대상까지 사이 디렉터리가 링크이거나 남의 소유인 경우(`legacy_cleanup_target_unsafe`), pid 파일이나 read-only 프로세스 표에서 실행 파일·스크립트가 plugin 대상 안에 있는데 정확한 데몬 identity가 아닌 살아 있는 node 프로세스(`qmd_daemon_unverified`, 경로를 언급만 하는 편집기·`backend-backup` 복사는 제외)이고 하나라도 있으면 plan·apply 모두 거절한다. `--include-user-qmd-data` 없이는 사용자 QMD 데이터를 `preserved`로 두고 검사하지 않는다(사용자가 관리하는 `~/.config` 링크가 정리를 막지 않는다). 대상 안에 mount point(장치 변경·mount 표)가 있으면 아무것도 지우기 전에 그 대상을 거절하고, 실패한 대상은 `failed`·`status: partial`(exit 1)로, 이미 지운 대상은 `completed`로 보고한다. 이 검사들은 사고(dotfile 링크·mount·pid 재사용)를 막는 장치이고 같은 UID 공격자의 rename 경합이나 macOS(pidfd 없음)에서 SIGTERM 직전 pid 재사용은 막지 못한다. `apply-legacy-cleanup --approve-legacy-cleanup`은 명령줄이 정확히 `<node> <plugin QMD runtime>/generations/g-<id>/qmd-native.mjs mcp --http --port <그 pid 파일의 port>`(`daemon.pid`는 그 프로세스의 port)인 데몬에만 SIGTERM을 보내고(신호 직전에 다시 읽는다. SIGKILL·패턴 kill은 쓰지 않는다), 마커가 있는 LaunchAgent만 `launchctl bootout` 후 plist를 지운 뒤 `~/Library/Application Support/qmd-auto-context/{runtimes/qmd,shared-qmd,backend}`를 HOME에서 연 디렉터리 fd를 따라 링크를 따라가지 않고 지운다. `~/.cache/qmd`·`~/.config/qmd`는 사용자 자신의 QMD 인덱스·설정·모델 캐시도 담으므로 `--include-user-qmd-data`가 있을 때만 지운다. 같은 디렉터리의 `learning`·`laya-inference`·`live-selection`·`runtimes/laya`는 남긴다.

### 이름과 내부 명명
- 제품 이름은 MemVane, 플러그인 id는 `memvane`, marketplace는 `memvane-marketplace`, 저장소는 `zbdulee/memvane`이다. skill id는 `memvane:<skill>`, 색인 DB의 사용자용 이름은 memvane-db, hook·안내 메시지 태그는 `[memvane]`이다.
- 사용자별 루트는 `core/memvane_paths.py`가 정한다: 상태 `~/.local/state/memvane`(설치별 state root, `embed-runtime`, `service`, `initial-builds`, `auto-context` 로그·scan state: 프로젝트 폴더와 별개인 사용자별 디렉터리라 이름이 그대로다), 지원 디렉터리 `~/Library/Application Support/memvane`(그 밖의 OS는 `~/.local/share/memvane`), 설정 `~/.config/memvane`, 캐시 `~/Library/Caches/memvane`·`~/.cache/memvane`. 새 설치·온보딩은 이 루트에만 쓴다.
- 내부 명명은 그대로다: `core/laya_*.py` 모듈, Laya 엔진 용어, `laya-*` 스키마 id, 프로젝트 폴더 안 `laya-index-route.json`·`laya-index-selection.json`, `configFormat` 값 `auto-context-dir`, `QMD_*` 환경 변수. 사용자에게 보이지 않고, 바꾸면 봉인된 기록과 테스트만 흔들린다.
- 프로젝트 폴더는 `.memvane/`다(settings, `wiki/`, route·selection·lock·`compile/` 런타임 파일, `core/project_dir.py`). 아직 옮기지 않은 프로젝트의 `.auto-context/`는 파일마다 `.memvane/` 다음으로 읽는다. 쓰기는 활성 폴더 하나에만 한다: `.memvane/`가 있으면 그것, 없고 `.auto-context/`가 있으면 그것, 둘 다 없으면 `.memvane/`(`project_dir.active_name`).
- SessionStart 번들 업그레이드 worker가 선택된 프로젝트마다 폴더를 한 번 옮긴다: `.auto-context`를 `rename(2)` 한 번으로 `.memvane`으로 바꾸거나(`rename`), git이 `.memvane/settings.json`·`.memvane/wiki`를 이미 가져왔으면 `.auto-context/`에 남은 항목(런타임 파일, git이 옮기지 않은 추적되지 않는 카드와 숨은 pending 교체본)을 항목 단위로 합쳐 옮긴다(`adopt`, 바이트가 다른 충돌은 아무것도 옮기기 전에 `project_dir_conflict`로 거절). 큐에 남은 `.auto-context/wiki/...` 경로는 읽을 때 활성 폴더로 옮겨 읽는다(`rebase_rel`). 옮기는 동안 recall은 최대 1.5초 기다린 뒤 한 번 재시도하고, 검색은 계속 응답한다.
- 두 폴더가 함께 있으면 `.memvane/`가 이긴다(`project_dir.layout`: none/legacy/current/adopt/split/conflict). `split`(이동한 프로젝트 위에 이전 브랜치를 체크아웃해 settings가 `.auto-context/`에만 있음)은 색인·위키 writer를 `project_dir_split`로 멈추고(writer의 route 증명 `verify_selected_route_for_write`가 publish·카드 쓰기 직전에도 split을 거절한다) 두 번째 색인을 만들지 않으며 SessionStart가 안내한다. recall·편집 gate는 계속된다. 이동 뒤 `.auto-context/`에 파일 관리자 메타데이터(`.DS_Store` 등)와 빈 디렉터리만 남으면 `current`로 보고 worker가 그 경우에만 지운다(`tidy`). Hermes는 SessionStart 출력 통로가 없어 이동·conflict 안내를 다음 recall 턴 앞에 한 번 붙인다. 이동이 만드는 추적되지 않는 `.memvane/wiki/.memvane-root`가 체크아웃 동안 wiki 디렉터리(같은 inode)를 남겨 검색이 마지막 게시본을 계속 쓴다. `conflict`(이전 브랜치 병합으로 두 폴더 모두 settings나 카드가 있음)는 `.auto-context/`를 무시하고 남은 카드를 `git mv`하라고 안내한다. 어느 폴더 이름의 연결 워크트리든 main checkout의 색인을 공유한다.
- 이동이 끝나면 SessionStart 안내가 owner 커밋 명령 `git add -A .memvane .auto-context`과 프로젝트 `.gitignore`의 `.auto-context` 줄에 대응하는 `.memvane/...` 줄을 보여 준다. 플러그인은 사용자 파일을 고치지 않는다.
- resident service는 `~/.local/state/memvane/service`에서 돈다. 기본 루트로 시작하기 전에 이전 루트(`~/.local/state/laya/service`)에서 도는 서비스가 있으면 drain을 요청하고 그 lease가 풀릴 때까지 새 서비스를 띄우지 않는다(`drain_legacy_service`). MemVane 서비스는 살아 있는 동안 이전 루트의 `service.lock`을 잡고 있다(디렉터리가 나중에 생기면 tick에서 잡는다). 그래서 이전 id 클라이언트는 서비스를 새로 띄우지 못하고 기존의 lexical 폴백으로 간다. 한 사용자에게 서비스가 둘(provider worker 둘) 생기지 않는다. worker 회수는 서비스 공통 규칙(`_reclaim`: 바인딩도 진행 중 요청도 없는 worker를 `RECLAIM_SECONDS` 뒤 정지)을 따르고, 로딩 중 마지막 route가 사라진 worker도 여기에 포함된다. 바인딩 소유 재증명은 바인딩마다 `OWNER_RECHECK_SECONDS`(5초, active upgrade가 fence 뒤 release를 기다리는 15초보다 짧다) 간격이고 worker가 죽었으면 다음 tick에 한다. 증명이 사용자당 sync owner lock 경합으로 `ResourceDeferred`(`owner_busy`)가 되면 바인딩과 socket을 그대로 둔다. route 철회·fence·identity 변경·worker 사망만 바인딩을 푼다. 이 재증명이 사용자당 sync owner lock을 잡는 동안 off-hook sync worker와 shadow driver의 잠금 단계(parity seal, `reader_ready`·`switched`)는 owner·queue lock을 `laya_index_sync.SYNC_OWNER_WAIT_SECONDS`(3초, step deadline 안)까지 기다린 뒤에만 busy로 보고한다. hook 경로는 기다리지 않는다. 서비스 상태 파일(`service.lock`, `control.sock`, `successor.lock`, `forced-exit.json`)은 서비스 디렉터리 안 내부 이름 그대로이고, 위치만 `~/.local/state/memvane/service`다. `LAYA_SERVICE_TIME_SCALE`은 fixture 전용 내부 환경 변수다.
- 이전 id의 Hermes 사본(`~/.hermes/plugins`나 `$HERMES_HOME/plugins`에 있는, 디렉터리 이름이나 `plugin.yaml` 이름이 이전 id인 사본, `laya_journal_v4.legacy_hermes_present`)이 있으면 프로젝트 route를 v3로 바꾸는 동작을 하지 않는다. 그 사본은 v3를 읽지 못해 편집 gate가 `block`을 낸다. 해당 동작은 active 업그레이드(새 intent)와 activation이다. bundle worker는 `legacy_hermes_copy_present`로 미루고(in-process 대기 없이 `DEFER_RETRY_SECONDS` 뒤 재시도), activation은 거절한다. 그동안 route는 v2 그대로 두 번들이 모두 읽는다. 판독할 수 없는 Hermes 플러그인 디렉터리도 있는 것으로 본다. Claude·Codex의 이전 훅은 v3 route에서 exit 3(비차단 오류)만 낸다.
- resident service 인계: MemVane 클라이언트는 이전 루트 서비스가 돌고 있으면 먼저 이전 루트 `successor.lock`(0.40.3 클라이언트가 successor를 고르는 lock)을 잡는다. 그 lock을 물려받은 MemVane successor를 띄운 다음 drain을 요청한다. 그래서 drain 중에 0.40.3 클라이언트가 와도 자기 successor를 세우지 못하고, MemVane successor가 이전 lease를 잡는다. 이미 0.40.3 successor가 기다리고 있었다면 MemVane successor가 그 lock을 이어받아 한 번 더 drain한 뒤 수렴한다.
- 이전 base embed runtime generation(`~/.local/state/laya/embed-runtime/generations/<g>`)에 봉인된 설치를 넘겨받으면, 그 generation 전체를 manifest로 재해시해 검증한 뒤 파일 단위로 같은 이름의 MemVane generation에 복사하고, 복사본이 같은 manifest를 재현할 때만 활성화한다(`_adopt_legacy`).
- wiki-dedup resolver의 프로젝트별 run-lock은 `~/.local/state/memvane/auto-context/dedup-resolve-lock/<project_key>`다. 이전 id 번들의 resolver는 이 릴리스가 쓴 route를 읽지 못해 그 프로젝트에서 돌지 않으므로 경로가 갈라져도 겹치지 않는다.
- 버전 간 상호 배제 lock 이름은 바꾸지 않는다: 프로젝트 단위 `laya-qmd-cutover-operation.lock`, `.topical-publish.lock`. 이전 플러그인 id의 번들도 같은 이름을 잡으므로, 모든 보유자를 옮기지 않고 이름만 바꾸면 상호 배제가 깨진다.
- 이전 이름과의 호환 shim(이 목록 밖의 사용자용 `qmd-auto-context`·`[laya-index]`·`Laya Index`·`laya-db` 문자열은 `test/memvane-naming-guard.test.mjs`가 막는다):
  - pre-rename state base `~/.local/state/laya`: 번들 업그레이드 worker가 그 아래 설치를 같은 볼륨 rename으로 `~/.local/state/memvane/<install id>`에 옮긴다(`laya_state_move`: intent 선계산, 프로젝트 폴더의 `memvane-state-move.json` 포인터로 재개, journal은 `cas_relocate_state_root`). 남은 legacy 설치가 없으면 참조 없는 `embed-runtime`·`service`·`auto-context`·`initial-builds`와 빈 base를 정리한다. 옮기기 전까지(다른 볼륨이면 계속) 읽는 쪽은 그 자리를 받는다: `initial-builds` pointer는 새 디렉터리를 먼저, 없으면 이전 디렉터리를 읽고, `auto-context` 로그·scan state는 새 디렉터리에 scan state가 없고 이전 디렉터리에 있으면 이전 디렉터리를 쓰고, embed runtime GC·legacy cleanup은 두 base의 attestation을 모두 본다. 이전 base에 새 설치를 만들지 않는다. 옮기는 트랜잭션은 journal의 reader record도 새 state root로 재봉인한다(`laya_journal_reader.relocate_selection`).
  - 프로젝트 폴더 `.auto-context/` → `.memvane/`: `laya_project_dir_move`가 옮긴다. intent `project-dir-move-intent.json`(state root)이 모든 기록을 미리 계산하고, 포인터 `memvane-project-move.json`(프로젝트 폴더)으로 재개하며, ledger를 `upgrading`으로 fence한 뒤 옮긴다. 색인은 명시적으로 다시 묶는다: published head의 clone generation을 `.memvane/wiki`에 묶은 새 binding store와 다시 쓴 catalog 메타데이터(binding·roots)로 바꾸고 재임베딩하지 않는다. fence 전 crash는 intent를 버리고, fence 뒤에는 전진만 한다.
  - 학습 런타임과 학습 상태는 따로 고른다. 런타임(`runtimes/laya`, 절대 인터프리터 경로가 inference proof에 봉인된 가상 환경)은 옮기지 않고 재프로비저닝하며, 사용할 수 있는 활성화 포인터(`active.json`: 소유자 전용 정규 파일, `choose_runtime`의 포인터 형식, 실제로 있는 실행 가능한 interpreter가 루트 안으로 resolve)가 있는 쪽을 따른다. 새 디렉터리가 우선이고, 다음이 이전 디렉터리(`.../qmd-auto-context`)다(`runtime_setup.runtime_base`). 학습 상태(`live-selection`의 selector·checkpoint·policy, `laya-inference` 서비스와 자원 lane)는 번들 업그레이드 worker가 한 번 옮긴다(`context_learning.state_move`: resident service drain·lease 보유, lane lock 전부 non-blocking 획득, 두 디렉터리 rename, `learning-state.json` 기록, checkpoint 포인터 재기준). 옮기기 전까지는 이전 디렉터리를 쓰고, 전환 기록이 있으면 새 디렉터리를 쓴다(`runtime_setup.learning_state_base`). 옮긴 뒤 selector heal(`context_learning.selector_heal`)이 어댑터 앵커 재연결·synthetic attestation·inference 준비를 다시 돌린다. 학습 registry는 schema(`user_version`)까지 초기화된 쪽을 따른다(`storage_layout.root`).
  - 위키 카드 소유 표시: 새 카드는 `createdBy: memvane`과 `> Auto-generated by MemVane` 상투구를 쓰고, 읽는 쪽은 `qmd-auto-context`도 같은 소유로 본다(`wiki_markers.CREATED_BY_NAMES`·`AUTO_DISCLAIMER_PREFIXES`).
  - 학습 adapter 정체성 anchor: 이전 plugin id 캐시(`qmd-auto-context-marketplace/qmd-auto-context/<ver>`)의 adapter도 anchor로 인정하고, 실행 대상은 현재 id 캐시뿐이다(`adapter_binding.CACHE_IDENTITIES`).
  - legacy cleanup 대상(`~/Library/Application Support/qmd-auto-context/{runtimes/qmd,shared-qmd,backend}`, `managed-by: qmd-auto-context` LaunchAgent)은 은퇴한 QMD 백엔드가 쓴 이름 그대로다.
- 플러그인 id가 바뀌어도 번들 업그레이드는 같은 규칙이다: 새 id 번들은 이전 id 번들에 묶인 route를 더 오래된 번들로 보고 `laya_bundle_upgrade`로 넘겨받는다. 이 릴리스가 쓰는 route는 `memvane-route-v3` 스키마(필드는 v2와 같음)라 v1/v2만 읽는 이전 번들은 그 route를 `blocked`로 읽고 넘겨받거나 되돌리지 못한다. `_not_older`는 실행 커밋이 바인딩 커밋의 조상이면 거절하고, 바인딩 커밋이 실행 커밋의 조상이면(전진) 허용한다. 갈라진 이력이나 clone이 바인딩 커밋을 모를 때(다른 id의 marketplace clone, shallow clone)는 번들 버전(SemVer 우선순위, `package.json` 또는 캐시 디렉터리 이름)이 엄격히 높아야 허용하고, 같거나 판정할 수 없으면 거절한다(fail-closed).

런타임 선택·partial clone 번들 증명의 개발 계약과 합성 검증 범위는 `docs/development-runtime-bundle-proof.md`를 따른다. 자동 번들 업그레이드는 ensure가 반환한 소유 generation을 모든 provider 재검토에 고정하며, source Git 증명은 lazy fetch와 transport를 금지한다.
