# 문서 작성 지원과 Relate 도입 검토

작성일은 2026-11-23이다.

## 결론

**권고는 1.1.0을 현재 계획과 검증 절차에 따라 진행하고, 사용 중에 검색과 문서 작성에서 어떤 정보가 빠지는지 확인한 뒤 Relate 도입을 결정하는 것이다.** 1.1.0이 이미 완료됐다는 뜻은 아니다. 출시 전 미해결 항목과 검증 상태는 [1.1.0 제3자 리뷰](2026-11-23-1.1.0-third-party-review.md)에서 관리한다.

문서 작성 지원은 별도 제품으로 탐색할 만하다. 작성자가 쓴 문장을 보고 관련 근거, 빠진 조건, 함께 설명할 내용을 찾아주는 방향이다. 이 기능의 가치는 실제 글이 더 정확하고 완전해지는지로 판단한다.

Relate는 문서 사이의 관계를 탐색하는 데 쓸 수 있다. **현재 단계에서는 기존 SQLite를 Relate로 전환할 이점이 입증되지 않았다.** 기존 검색으로 집필에 필요한 정보를 찾을 수 있는지 확인하고, 관계 탐색이 추가로 중요한 정보를 찾아주는지 비교한다.

## 만들고 싶은 경험

사용자가 팀원을 위한 설치 문서에 다음 문장을 쓴다고 가정한다.

> 새 worktree를 만들면 설치 관련 파일을 Git 추적에서 제외한다.

기존 검색은 어떤 파일을 제외하는지 찾는 데 유용하다. 집필 지원 기능은 **“이 설명만 따라 하면 새 팀원의 검색 기능이 실제로 활성화되는가?”**를 확인하도록 관련 자료를 보여준다.

이 프로젝트의 위키에서 worktree 카드의 관계를 두 단계 따라가면 온보딩 규칙과 설정 해석 문서에 도달한다. 설정 파일이 있어도 해당 설치에서 온보딩을 마쳐 검색 경로가 선택되어야 hook과 skill이 동작한다는 조건이 나온다. 팀원용 가이드라면 이 조건을 함께 설명할 수 있다. [worktree 안내](../../README.md#git-worktree) · [설정 해석](../../memvane/settings/README.md#설정-해석-우선순위)

작성자에게 다음 정보를 보여준다.

- **바로 쓸 근거** — 이 문장의 근거가 되는 원문과 위치.
- **함께 볼 조건** — 이 글의 독자에게 필요한 예외나 선행 작업.
- **확인할 질문** — 현재 자료만으로 답할 수 없는 내용.

자료를 채택하면 어떤 문단에 어떤 원문을 사용했는지 남긴다. 나중에 원문이 변경됐을 때 관련 문단을 찾아 다시 검토하는 데 활용할 수 있다. 이는 제안하는 기능이다.

## 지금 확인된 사실

| 항목 | 확인 결과 | 해석 |
|---|---|---|
| 위키의 관계 | 작업트리의 `verified` 카드 387장에 대상이 확인되는 `related` 연결 598개가 있다. | 연결을 이용한 집필 자료 탐색을 실험할 수 있다. |
| 다른 원문 발견 | 양방향으로 최대 두 단계 따라갔을 때 230장의 출발 카드에서 다른 원문 파일에 도달했다. | 다른 자료를 찾을 가능성이 있다. 발견된 자료가 실제 글에 도움이 되는지는 별도 평가가 필요하다. |
| DB 비교 | 동일한 관계를 Relate 1.2.0과 SQLite의 재귀 쿼리로 조회했을 때 결과 집합이 같았다. | 현재 규모의 탐색 가능 여부만으로 DB 전환을 결정하기 어렵다. |
| 원문 변경 | 과거 리비전의 발췌를 확인할 수 있었고 이후 파일이 바뀐 카드 83장 중 74장은 발췌가 동일하게 남았다. 9장은 하나 이상의 발췌를 그대로 찾지 못했다. | 실제 인용 구간을 우선 확인하는 기능을 검토할 수 있다. 주변 문맥이 바뀌었을 가능성은 따로 확인해야 한다. |

이 집계는 게시된 운영 색인의 전체 현황이 아니라 당시 로컬 작업트리와 두 Git 리비전을 대상으로 한 실험이다. 실제 작성자의 문서 품질이나 작업 시간은 측정하지 않았다.

## Relate를 도입하면 달라지는 점

[Relate 1.2.0](https://github.com/relatedb/relate/tree/v1.2.0)은 애플리케이션에 내장하는 그래프 DB다. 카드, 원문, 작성 문단을 연결하고 관계를 양방향으로 조회하기 좋다. 예를 들어 다음 두 질문을 같은 관계에서 다룰 수 있다.

1. 이 문단을 작성할 때 함께 살펴볼 결정과 원문은 무엇인가?
2. 이 원문이 바뀌면 어떤 문단을 다시 확인해야 하는가?

Relate는 SQLite 파일을 직접 사용하는 제품이 아니다. 자체 저장 엔진을 사용하고, 영속 그래프를 메모리에 적재한다. 기존 MemVane의 세대별 게시와 원문 검증을 옮기려면 별도의 설계와 검증이 필요하다. [Relate 저장 엔진](https://github.com/relatedb/relate/blob/v1.2.0/docs/guides/storage-engine.md) · [현재 view store](../../memvane/store/README.md)

도입을 검토한다면 **기존 SQLite를 유지하고 Relate를 별도의 관계 탐색용 저장소로 실험하는 방식**이 적절하다. 작성자가 채택한 근거 기록은 검색용 그래프를 다시 만들더라도 보존할 수 있어야 한다. 실제 운영 구조와 보관 방식은 실험 후 결정한다.

## 1.1.0 이후 확인할 것

1. **기존 검색의 한계** — 실제 문서 작성 중 필요한 예외나 결정 배경을 찾지 못한 사례를 모은다. 같은 자료를 검색어를 바꿔 찾을 수 있었는지도 확인한다.
2. **관계 탐색의 효과** — 같은 초안에 기존 검색과 관계 탐색을 각각 적용한다. 작성자가 빠뜨린 조건을 발견해 문장을 실제로 바꿨는지, 무관한 결과가 얼마나 섞이는지 비교한다.
3. **근거 추적의 효과** — 작성자가 채택한 원문이 바뀌었을 때 수정이 필요한 문단을 찾는 데 도움이 되는지 확인한다.
4. **운영 비용** — 관계 색인 생성·갱신 시간, 메모리 사용량, 여러 작업이 동시에 접근할 때의 동작을 측정한다.

관계 탐색이 유용해도 SQLite로 충분하면 그 방식으로 구현할 수 있다. 관계 종류와 탐색 요구가 늘고 Relate가 집필 품질이나 구현·운영 측면에서 실질적인 이점을 보이면 별도 도입을 검토한다. 기존 DB의 전면 교체는 데이터 이전과 기존 기능의 동등성까지 입증한 뒤 판단한다.

## 판단 범위

이 문서는 1.1.0의 출시 승인이나 일정 결정을 내리지 않는다. 문서 작성 지원과 Relate에 관한 조사 결과를 바탕으로 한 권고다. 검토 시 기준 코드는 로컬 `49e0d96d`이며, 당시 로컬 `origin/main`은 `f7293ec1`로 50커밋 앞서 있었다. 1.1.0의 현재 상태는 작업 중인 릴리스 자료와 실제 검증 결과를 다시 확인해야 한다.
