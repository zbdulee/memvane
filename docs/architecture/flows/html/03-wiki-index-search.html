03 위키 색인과 검색 주입

사용자가 호스트 에이전트에게 “이 모듈을 왜 이렇게 설계했지?”라고 묻으면, 답을 쓰기 전에 Laya가 관련 위키 카드만 찾아 검증한 뒤 컨텍스트로 붙여 줍니다.

질문 하나가 처리되는 순서

사용자 행동자동즉시큐 대기멈추면 실패
  1. 입력 / 행동
    사용자가 프롬프트를 보냅니다

    선택된 Laya v2 route(호스트에 연결된 Laya 경로)라면 호스트가 recall hook을 호출합니다.

    사용자 행동hook 호출은 자동즉시
  2. 처리 ①
    준비 확인 후 색인 세대 하나를 고정

    선택된 설치·provider와 임베딩 모델 소유 프로세스의 신원을 확인하고 새 질의의 자원 사용을 판정합니다. 모델이 차갑거나 교체 중이면 훅이 직접 로드하지 않고 laya-sync를 요청한 뒤 이번 질의는 보류합니다.

    자동즉시 판정준비 중·자원 보류는 검색 성공 아님
  3. 처리 ②
    위키 설정과 색인 세대 확인

    wiki role과 hierarchical 설정을 확인한 뒤 색인 세대 하나를 pin합니다. 이 세대에서 끝까지 읽으며 실패해도 다른 세대의 일부 결과로 바꾸지 않습니다.

    자동요청별조건 불충족 시 실패
  4. 처리 ③
    위키 카드만 검색

    요청별 Python 경로가 고정된 SQLite 세대의 wiki 컬렉션을 먼저 lexical로 찾고, 같은 사용자·설치·provider·모델 fingerprint에 결속된 비공개 소켓으로 질의 벡터를 받아 vector 결과와 합칩니다. 모델은 별도 소유 프로세스에 남아 있고 훅이 새로 로드하지 않습니다. 별도의 상주 Laya 검색 서버는 없으며 원문 파일 본문도 검색 대상이 아닙니다.

    자동즉시binding 없으면 실패
  5. 처리 ④
    빼고, 검증합니다

    index.md·log.md와 pending refresh(갱신 대기)가 남은 source의 카드를 뺍니다. 남은 행을 하나씩 검증합니다.

    대기 상태를 알 수 없거나 검증이 실패하면, 결과를 줄여 내보내지 않고 fail closed(전체 실패)합니다.

    자동즉시모르면 실패
  6. 결과
    검증된 위키 카드가 컨텍스트에 들어갑니다

    카드 안의 발췌와 원문 위치(source locator) 링크도 함께 갑니다. 빈 결과도 정상입니다. 끝나면 pin을 반드시 풉니다.

    자동즉시
  7. 다음 동작
    호스트가 답을 씁니다

    링크를 따라 원문 파일을 직접 열지는 호스트의 선택입니다. 플러그인 통과 조건이 아닙니다. 색인 갱신은 이 흐름과 별개로 백그라운드 큐에서 처리됩니다.

    호스트 선택갱신은 큐 대기

헷갈리기 쉬운 세 가지

원문 파일 (raw source)

색인 안 함 · 검색 안 함 · 주입 안 함

Laya는 path와 hash 기록(cursor)만 남깁니다. 신선도 판단과 위키 생성에만 씁니다.

위키 카드

검색·주입 대상

생성된 카드(.auto-context/wiki)입니다. 안의 발췌와 원문 위치 링크는 정상 출력입니다.

Laya 위키 전용 색인

위키 카드만 담음

membership·본문·FTS·vector 모두 위키 카드 기준입니다. 세대 단위로 게시되고 pin으로 읽습니다.

색인 갱신 (백그라운드)

  1. laya-sync wake를 요청합니다

    wake queue에 offer합니다. 결과는 queued·retained·dropped 중 하나입니다.

    자동큐 대기
  2. queued·retained만 큐에 남습니다

    dropped는 큐에 남지 않습니다. 성공한 job으로 보지 않습니다.

  3. sync worker가 wake를 소비합니다

    선택된 설치의 모델 소유 프로세스가 없으면 off-hook 경로에서 시작을 요청하고, 준비되기 전에는 durable wake를 보류합니다. 준비된 모델로 위키 카드 본문을 임베딩하고 새 wiki generation을 게시합니다. 원문은 path·hash만 다룹니다. sync가 끝나도 모델은 선택된 설치에서 유지됩니다.

    자동큐 처리 시점

활성화 직후 wake는 한 번만 요청하고 재시도하지 않습니다. dropped면 그 요청만으로 sync가 보장되지 않습니다. capacity store가 생긴 뒤 첫 세대가 게시되기 전까지 recall은 아무것도 주지 않습니다.

오류·구현 상태·근거

실패하는 경우 (fail closed)
  • wiki role이 없거나 hierarchical이 아님 → hook 오류
  • binding store가 있는데 pin된 세대에 binding 없음 → 실패
  • pending 상태 확인 불가 → wiki_pending_refresh_unknown
  • 반환 행 검증 실패 → 실패 (일부만 내보내지 않음)
  • wake offer가 dropped → job 없음. 활성화 시 요청은 자동 재시도 없음
  • 첫 bound generation 게시 전 → 빈 recall
  • 모델 cold start·신원 전환·정상 자원 압박 → 이번 질의를 명시적으로 보류. 정상 자원 압박만으로 준비된 모델을 내리지 않으며, 모델 준비·큐 등록만으로 검색 성공이 아님
  • 기동 실패 → 비공개 owner 상태에 사유를 기록하고 제한적으로 재시도. 영구 실패는 별도 실패 상태이며 무한 재시도하지 않음
구현됨 vs 미검증
  • 구현 경로: 기존 위키 전용 색인·wake 구분에 더해, 현재 후보에는 설치 결속 임베딩 모델 소유 프로세스와 요청별 SQLite 검색 경로가 있습니다.
  • 아직 미확정: 모델 소유 프로세스 변경은 최종 후보 검증 및 실제 호스트 QA 전입니다. 코드 경로의 존재를 검색 PASS로 취급하지 않습니다.
  • 미검증: synthetic QA 증거는 있으나, 실제 호스트의 route 선택·recall 주입 QA는 통과하지 않았습니다.
  • 일부만 확인: worker가 세대를 게시하는 내부 단계, 카드 변경 시 wake를 보내는 주체.
  • 이 문서는 큐 전체 비움, 실제 학습 완료, 운영 전환 완료를 주장하지 않습니다.

이 프로젝트의 용어

Laya
위키 카드를 색인·검색해 호스트에 컨텍스트로 주는 경로. SQLite 검색은 요청별 Python 실행이며 상주 검색 서버가 아님.
Laya v2 route
호스트가 선택한 Laya 연결 경로. 다중 source 정책을 가짐. laya_index_host_route.py
recall hook
프롬프트 시점에 동기로 도는 검색 단계. query_selected_v2
위키 카드
원문에서 생성된 카드. 유일한 검색·주입 대상. .auto-context/wiki
wiki role
컬렉션이 위키용임을 뜻하는 역할. 검색 루트를 정함. wiki_index_roots
hierarchical
wiki role에 요구되는 컬렉션 정책 값.
index generation
sync worker가 게시하는 색인 한 세대.
pin
검색 동안 한 세대만 읽도록 고정. 끝나면 release.
binding store
세대별 binding을 담는 저장소. pin된 세대에 binding이 없으면 실패.
pending refresh
source가 바뀌어 카드 갱신이 남은 상태. wiki freshness pending ledger에서 strict하게 읽음. wiki_pending_refresh_unknown
fail closed
확실하지 않으면 줄인 결과 대신 실패를 내는 원칙.
source locator
카드 속 원문 위치 링크. 검증된 span만 담김. source_locations
wake queue
sync 요청을 담는 런타임 큐. runtime-wakes.sqlite3, runtime_work.py
offer / queued·retained·dropped
큐에 wake를 넣는 시도와 그 결과. dropped는 큐에 남지 않음.
sync worker (laya-sync)
wake를 소비해 위키 세대를 게시하는 비동기 작업자.
임베딩 모델 소유 프로세스
선택된 설치에서 검증된 로컬 모델을 로드해 유지하는 별도 프로세스. 같은 사용자·설치·provider·모델 fingerprint가 맞을 때만 재사용. laya_embed_resident.py. OS 부팅 서비스로 등록되지 않음.
owner 소켓
비공개 Unix 소켓. 훅은 이미 준비된 모델에 질의 벡터를 요청하며, 모델을 직접 시작하지 않음.
질의 보류
새 질의가 자원 압박 또는 모델 준비 때문에 실행되지 않은 상태. 백그라운드에 프롬프트를 저장하지 않고 다음 질문에서 다시 판정. 검색 PASS가 아님.
capacity store
설치 후 생기는 저장소. 이후 첫 bound generation 전까지 recall은 비어 있음.
