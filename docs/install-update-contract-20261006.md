# Managed setup and preserving update contract (development)

## User entry

After installing the host plugin from its marketplace, ask the agent: “Show the auto-context setup plan for this project,” “Prepare the reviewed setup in isolation,” “Apply the prepared setup,” or “Roll back the last setup.” The exposed `setup` skill invokes `core/setup_entry.py`, which discovers project inputs and writes the strict coordinator request itself. The existing `update` skill remains the index refresh command; it does not install packages.

The ordinary preserving developer entry is `python3 core/setup_entry.py plan-install|install --project <absolute project path>`. The separate topical-card/shadow and runtime preparation CLI is `python3 core/setup_entry.py inspect|check-update|plan|prepare|status|activate|rollback --project <absolute project path>`. `inspect`, `check-update`, and `plan` are read-only. `prepare` accepts reviewed options, publishes an owner-private deterministic request and delegates to `install_update.py`; `activate` is a separate approved cutover. The lower-level `install_update.py prepare --request` remains an internal/debug interface. [Codex plugin hooks](https://developers.openai.com/plugins/build/plugins) and [Claude hooks](https://code.claude.com/docs/en/hooks) describe runtime events such as SessionStart, not a supported install callback for migration. Host marketplace installation and hook trust remain separate, explicit host actions. The one-time setup skill is therefore the installation entry; a later update starts with read-only `check-update` and requires a new prepare/apply approval. A short, local, one-time SessionStart notice points a project needing setup to this skill. The new code checks legacy settings and an unfinished setup journal before ordinary hook or queued work, retaining old jobs while setup is required. This internal inactive state does not disable the host plugin or change its trust record. A previously loaded host process can still run its older code until that host refreshes or reloads the plugin.

[Claude's plugin update documentation](https://code.claude.com/docs/en/discover-plugins) says a running session keeps its loaded plugin version until reload or a later session; custom marketplace auto-update settings may differ from official marketplaces. [Codex plugin packaging](https://developers.openai.com/plugins/build/plugins) treats marketplace refresh and changed hook trust as separate host steps. The source marketplace entry in this checkout uses a URL without a pinned revision, so these host update paths do not themselves attest this frozen development tree. Actual host plugin refresh, new hook trust, and an already running old process remain outside the synthetic upgrade tests.

### New machine readiness

1. Install and trust the host plugin, then inspect the project with the exposed `setup` skill.
2. Prepare the QMD runtime and its separately identified embedding model cache, then verify a local index, embedding, and search probe. Plugin source installation alone does not supply the QMD model files.
3. If local learning is wanted, provide an already available, reviewed Laya base model directory and prepare its isolated Python runtime. The current `--laya-model-dir` contract requires an existing absolute path and offline model loading; setup does not download base weights. A learned head artifact is stored locally in its owner-private cycle directory and is not copied to another machine by Git push or plugin installation. Moving such an artifact needs a separate model and data migration plan with source, license, integrity, and user authorization checks.

## Preserving common-file installation (isolated development candidate)

The exposed setup skill now uses `plan-install` and explicit `install` for an existing v1 file/wiki project or an empty opted-in project. This route preserves original/global DB, settings, wiki, model cache and private learning history; it copies legacy settings exclusively and reuses approved local QMD2.5.3/Node/GGUF inputs. New software/model preparation retains its separate approval gates and is not performed by this route. Laya may be absent: it remains deferred and does not activate learning.

A missing common store runs the existing isolated prepare/approved activate flow, then only approved collection roots are enrolled and queued. An existing common store is reused. Completion requires canonical common routing, a ready hook guard, actual typed vector-only/no-rerank scoped search, owned healthy endpoint and durable queue ACK. The private `shared-install-journal.json` binds the reviewed settings/collection/model/runtime inputs and records incomplete phases. Retry resumes that intent; a selected store or in-flight writer is preserved, never automatically rolled back. Busy/deadline conditions return75; unsafe inputs require review. The deadline bounds maintenance/readiness, while initializer probes retain their own existing bounded timeouts.

Plugin auto-update is code distribution, not completed setup or permission to install runtimes. With v1 paths, missing Laya/model/runtime, partial runtime or a stale pointer, normal host hooks remain harmless/setup-required and emit one local setup notice. They do not silently use the old global DB or download/build software. After successful installation the hint stops and compatible hooks use the common route. Completed installs permit harmless query preference edits; changed structural collection ownership remains closed for review. The older shadow coordinator validates production common routing even when revisiting a historical activated receipt; a project shadow alone is not a finished preserving install.

### Lock budget, source stability and lock identity

`core/install_deadline.py` (SSOT) gives the explicit installer and the shared-store CLI one in-process lock budget (`--deadline-seconds`, default 600, valid range 0–3600). Inside that context every nested blocking `flock` retries non-blocking until the shared budget expires; ordinary hook and worker locking outside the context is unchanged, and an existing holder is never signalled or terminated. A busy lock returns `status: "deferred"` and the setup entry exits **75**; the journal keeps its receipts for an identical approved retry, and an index writer that outlives the controller budget continues. Permission denial and unsafe state are errors, not busy. If cleanup of a partially selected activation finds its lock busy, the runtime pointer is retained and the journal enters `recovery_required` for explicit recovery.

Approved indexed Markdown collections are hashed before maintenance and again after readiness; inode, size, mtime and ctime also catch temporary A→B→A edits. Only changed collections publish a write-ahead queue intent, and resume checks the recorded snapshot even when no new host hook ran. `core/install_maintenance.py` `stable()` runs at most three maintenance/readiness passes; if sources keep changing it defers with exit 75 (`sources_changed_during_resume`) and keeps the queued work. This is a bounded stable-source proof, not a promise that authors stop editing after completion.

Bootstrap preparation records generation/probe identity and native step checkpoints. A native child inherits an exclusive lease, so controller exit cannot start another writer while that child survives; CPU bootstrap attests and directly executes the CLI so a launcher cannot drop the lease. Denied or unknown process identity is never treated as a dead owner. Lock reclaim and release share a stable sidecar lease and check owner and inodes; PID publication uses its original open file, so delayed cleanup cannot affect a new holder, and a storage-permission failure preserves the PID marker. Open host sessions alone are not a writer lease; the live-session flow uses a bounded writer/embed reservation and approved scope.

Regression suites (`shared-install`, `shared-install-resilience`, `shared-qmd-setup`, `shared-enrollment`, `setup-upgrade-guard`, `qmd-endpoint`, `qmd-native-policy`, `live-cutover`, durable queue/kick) use a disposable synthetic HOME, fake QMD/model markers and mocked endpoint identity. They never run paid APIs, user manuscripts, operating DB rollback or real model learning. Hardware power loss, an actual host upgrade and a Linux CI run of a committed integration are outside what these suites prove.

## Supported execution and requests

The bundled managed QMD/Laya installation lock and default runtime roots target macOS arm64. Managed QMD accepts Node 22 and 24 LTS, and Node 26 Current; Node 20 is rejected by installer preflight and runtime reuse. Node 22.23.3 and 26.10.0 each passed an isolated native SQLite/index/embed/vector probe with a newly prepared QMD 2.5.3 package, while CI covers Node 22/24 and the Node 26 fixture. Odd major versions are outside this support policy. Laya uses a separate Python 3.12.14 generation, and Python >=3.9 is required for the plugin hook. Other OS/architecture combinations remain supported only by the existing, explicitly installed global QMD hook path; managed setup reports `unsupported_managed_platform` with manual guidance and makes no changes. QMD runtime reuse requires an exact, proved 2.5.3 package; other globally installed QMD versions are inventoried but never overwritten. The normal backend accepts `>=2.5.3 <3`, which is a wider policy than the managed installer.

A strict JSON request is generated by the entrypoint and consumed by the coordinator. It chooses `qmd.mode` (`active`, `reuse`, or `install`), `laya.mode` (`defer`, `active`, `reuse`, or `install`), and `index.mode` (`none` or `shadow`). It names every external executable/model/cache explicitly and includes installation execution gates for new packages. QMD `reuse` validates the existing installation; QMD `install` uses the checked-in hash lock and creates an inactive generation. Laya `reuse` requires an explicit executable, adapter, and local model directory; Laya `install` requires the selected uv and pinned lock plus separate `--approve-laya-install`. It does not activate a teacher or select a private checkpoint. `shadow` stages a new project DB against the existing wiki and model cache. The request records a project root and explicit `runtimeRoots.qmd`/`runtimeRoots.laya` paths. `runtimeRoots.qmd` must equal the default managed root reported by `inspect`; the hook and daemon resolver use that same root. `inspect` reports default roots and Node/npm candidates without executing them. The coordinator refuses a different project or changed request on resume, except a reviewed wiki mapping submitted while `awaiting_legacy_review`; that transition rebuilds the shadow index before cutover. The CLI does not infer permission from the presence of a package or a model cache.

The separately requested topical-card `plan` requires a published, proved v2 wiki before `shadow` preparation. An explicit `--bootstrap-empty-wiki` mode is limited to a new modern opted-in project with an empty wiki, no legacy settings or project DB, no source index, and no selected pointer. It records the original index route and rechecks both that route and the current route at prepare and cutover, including a custom `INDEX_PATH` or a project-local default cache DB. A shared global DB is accepted only after read-only inspection shows no collection path covering this project; an unreadable or ambiguous shared DB blocks bootstrap. Its inactive shadow generation uses a temporary local synthetic collection to prove the embedding model and vector dimension, then removes the probe documents and vectors before cutover. The prepared proof retains that model fingerprint so the first real card cannot switch models silently. Activation selects an empty project DB; normal guarded hooks may then generate, verify, publish, and index the first card. This scope is `v2_empty_bootstrap`, not a migration of existing material. It discovers a project-local QMD config, model cache, optional source DB and the target embed model; it infers vector dimension from the source only when the model identity matches. Missing inputs are named blockers, not guessed settings. A separately reviewed owner-private v1 mapping list may be supplied; the coordinator rechecks every publication proof. `--index-mode none` is explicitly `runtime_only_no_v2_index`, so it never claims to have migrated search or wiki data. `check-update` compares the pinned QMD/runtime selection, modern settings, selected project index, v2 opt-in/publication and legacy review journal without writes. Its `up_to_date` status covers those selected routing/proof markers, not live model quality or a new package release feed.

## Request shape

### New-machine shared-store initialization

Read-only `inspect` and `check-update` inventory a missing shared store without authorizing global-QMD fallback. Explicit `plan-store` / `prepare-store` / `store-status` / `activate-store` reuse verified existing QMD 2.5.3 and a local GGUF; no package/Laya installation occurs. Backend selection is explicit (`--qmd-backend auto|cpu`, legacy `--qmd-cpu` alias). Auto uses a generation-local hash-attested Node entry that narrows the existing QMD `ensureLlama` API to `ensureLlama(false)`, retaining automatic GPU selection while forbidding native build/download. CLI/LLM and entry hashes are checked on every runtime selection, and daemon/CLI use the same entry. There is no new hook, test API injection or environment preload. With `--approve-index-execution`, a single synthetic local embedding and typed `vec:` search (`--no-rerank`) prove dimension/fingerprint and actual native backend receipts. All probe rows are removed before `prepared_inactive`; native failure or drift retains inactive state. CPU is an optional explicit choice. To change only a valid inactive preparation, `--replace-inactive-store-preparation` archives the old journal and preserves every old generation; selected pointers/interrupted/unproved state cannot use this transition.

Preparation is serialized and repeatable for the identical reviewed request. `activate-store --approve-store-activation --old-host-sessions-restarted` is a separate approval: it refuses existing shared pointers and non-quiescent/unproved dedicated daemon endpoints (new default scan starts at8584), never stops a daemon, and selects the runtime only if no competing selection appeared under its activation lock. Its failure cleanup uses that same lock and deletes only its exact new pointer. An interrupted activation reports `recovery_required` and preserves pointers for review. This is an empty plugin store initialization, **not** a migration of v1 wiki/index/history; modern opted-in projects can start routing to the new store after selection. Existing data, global QMD and model weights remain in place. Operational host update/trust, project preserving migration, other QMD models and Laya readiness remain separate gates.

For a fresh scoped store, `--store-scope <approved project>` binds source settings hashes into the request and an immutable `scope-policy.json` proof. `--allow-live-host-sessions` replaces a restart assertion with a real writer/embed reservation: activation waits up to `--writer-wait-seconds` (default30, maximum120) on the exact common worker locks, never signals holders, validates its reservation and rechecks inputs before/after pointer publication. Runtime publication remains serialized/atomic; the shared pointer is atomically/exclusively published from complete bytes. Project routing remains closed while the bootstrap journal is activating/recovery_required. After commit, only approved project roots enter this new store, so other live host sessions and schedulers may continue without triggering unapproved indexing. Existing reviewed unscoped store format remains compatible. Explicit later enrollment/migration of additional roots is a separate integration task, never inferred from an old indexing:true setting.

New production v2 dirty work uses the plugin-private `backend/dirty-queue`; the legacy `~/.config/qmd/dirty-queue` is retained for v1. Producer/worker/update paths resolve the same queue and refuse a production override aliasing the old default. Existing v1 binaries/config/DB are never redirected. Late v1 DB/queue writes therefore remain intact but do not automatically turn that already-loaded session into a v2 session. Source files remain authoritative; the explicit initial reindex verifies stable source snapshots with bounded retry. Ordinary host reload is needed to adopt new code, not to keep old isolated DB writes from corrupting the new store.

The reviewed JSON request uses `schema: "qmd-install-request-v1"` and an absolute `project`. It requires:

| Field | Choices and required inputs |
|---|---|
| `runtimeRoots` | Absolute owner-private roots. `qmd` must be `inspect.defaultRuntimeRoots.qmd`; `laya` is explicitly chosen. |
| `qmd` | `active`; `reuse` with absolute `qmd` and `node`; or `install` with absolute `node` and `npm`, boolean `allowExecution` and `allowLifecycleScripts`. |
| `laya` | `defer`; `active`; `reuse` with absolute `executable`, `adapter`, and `modelDir`; or `install` with absolute `uv`, `lock`, `adapter`, and `modelDir`, `uvSha256`, `lockSha256`, and boolean `allowExecution`. |
| `index` | `none`; or `shadow` with absolute `config`, `wikiDir`, and `modelCache`, `sourceIndex` as an absolute path or null, `expectedModel`, positive `expectedDimension`, and boolean `allowExecution`. Explicit empty bootstrap additionally requires `bootstrapEmptyWiki: true` and an absolute `bootstrapIndexRoute` recorded by the setup entrypoint. |
| `config` | `preserve` or `copy_legacy`. Copy retains the legacy source. |
| `wiki` | `preserve`; or `reviewed_v2` with a complete `mappings` array. Each row has `legacyPath`, `legacySha256`, `generationId`, and `cardId`. |

The `install` gates approve package execution only when explicitly set in a reviewed request. `shadow` builds a new DB in a private generation; `sourceIndex` is the original DB whose consistent SQLite backup snapshot, including committed WAL pages, is frozen for rollback proof. A main-file SHA alone is insufficient for live WAL and is not used as the source drift decision. The requested QMD config must bind the one enabled wiki collection to the exact `.auto-context/wiki` directory. Each wiki Markdown file must appear as an active document with the same SHA-256 and expected-model vector. Published v2 pages and source revisions must still pass proof. The entire corpus, DB and config are checked again immediately before cutover and after all pointer and daemon steps. Source fingerprint checks never issue a checkpoint or write to the original DB. During pointer selection or return to the original index, a short SQLite `BEGIN IMMEDIATE` reservation blocks concurrent SQLite writers; it is always rolled back without DML. If the reservation cannot be obtained or the source snapshot changes, cutover fails closed. SQLite may create WAL shared-memory sidecars when taking this reservation on a checkpointed WAL file; this is the database engine's lock state, not a content migration. The coordinator holds the same owner-private project lock as managed wiki publication and retirement through validation, pointer cutover, and journal commit. An uncoordinated manual edit detected after pointer selection triggers rollback rather than `activated`. Every legacy card requires a verified, published v2 mapping before cutover. The original card remains in place.

Source fingerprint backup staging is under the process temporary directory as `qmd-source-snapshots-v1-<uid>/job-<random-128-bit-token>/snapshot.sqlite`. The root and each job are owner-only mode 0700; the snapshot, owner stamp and advisory lock files are created mode 0600. SQLite may briefly create journal or WAL sidecars inside that private job. The job lock is held from before backup creation until the snapshot is hashed and removed. Normal completion removes the whole job. On the next fingerprint entry, unlocked jobs with a matching owner stamp, expected file names, regular single-link files and owner UID are removed immediately; no age-based deletion is used, so concurrent live jobs remain intact. Unrecognized files, symlinks, hard links, malformed jobs and unsafe staging roots are preserved for manual review. A crash can therefore leave a full private backup until the next entry; there is no background sweeper. An in-memory SQLite backup was considered, but would require memory proportional to the full index and an additional serialized copy for hashing. The private disk staging keeps peak memory bounded. These backups never intentionally write or checkpoint the source DB. The cutover reservation can still create source `-wal`/`-shm` sidecars, so source logical preservation is not a promise of zero filesystem writes.

## Phase and recovery rules

1. `inspect` reads current host/runtime/config/wiki/index inventory without writes. It reports unsupported platform and legacy wiki blockers; no “installed” status is inferred from plan-only code.
2. `prepare` creates an owner-private project journal, copies no user source and changes no active pointer. Each prepared generation is recorded only after the existing installer or shadow-index proof succeeds. A pending journal prevents the SessionStart legacy-config migration from moving the frozen `.auto-context.json` source. A failing step leaves the journal resumable. Repeating the same request reuses already prepared stages; changing it requires an explicit rollback/abandon review.
3. Before `activate`, the coordinator rechecks prepared proofs, original DB and settings hashes, pointer baselines, platform, and legacy wiki status. v1/missing/future wiki cards stay in their original location. Any such card blocks v2 cutover pending reviewed conversion; no automatic semantic migration or silent deletion occurs. Legacy `.auto-context.json` or `.agents/qmd-recall.json` can be copied to modern settings only after byte/normalization proof; the original stays intact. A write-ahead settings intent records the source and target hash before an atomic file link. Resume can adopt the exact completed bytes after a crash; rollback removes only a matching file.
4. `activate` selects QMD, confirms the hook/daemon resolver chooses that wrapper, then selects the project DB and Laya as separately journaled transitions. If a managed daemon process exists, including one whose health endpoint fails, it reloads through the backend manager and verifies health plus the new process entry and Node identity. A subprocess timeout enters the same structured rollback or recovery path as other activation failures. Rollback reloads the restored selection. A failed transition restores already changed pointers only if their bytes still equal what this transaction wrote. It reports `recovery_required` rather than claiming partial success if a concurrent writer prevents restoration.
5. `rollback` checks current pointer and settings hashes before restoring their pre-activation bytes, with each runtime's activation lock. It never deletes original DB, wiki, checkpoint, gold, history, or cached models. Prepared generations remain inactive for inspection; explicit cleanup is separate. Repeated `activate`/`rollback` is idempotent. Laya `reuse` records an attested external runtime without changing a managed pointer; Laya `active` keeps the existing selected pointer. Learning policy and checkpoint selection remain separate.

No actual operating pointer, global config, model cache, or user source is used by the development E2E; tests use owner-private synthetic projects and injected installer runners. This coordinator E2E made no package download or external model call and did not change user data. Package lifecycle scripts and operating project migration remain separate; actual host trust is handled by the official Codex UI.

The complete product wiki writer, lock-order, and post-cutover failure inventory is in [`install-update-writer-error-audit-20261006.md`](install-update-writer-error-audit-20261006.md). Ordinary SQLite and callback exceptions enter the same structured rollback path; interrupted processes retain write-ahead recovery state.

## Additional approved projects in a selected common store

The preserving `install` route audits actual physical vectors in its approved
indexed collections. Missing/malformed rows or inconsistent current
model/fingerprint chunk metadata prevent completion. Under the writer/embed
fence, repair journals intent, atomically invalidates only defective target
metadata, retains physical/healthy/foreign data, and uses normal queue/embed
maintenance. A defective hash shared with a foreign collection requires review.
Bootstrap generation/step checkpoints survive controller interruption; a
surviving native child retains a lease, deferring another writer. CPU bootstrap
uses an attested direct CLI entry to keep that lease on the actual process.
EPERM/unknown lock owners stay busy.

`enroll-store --project <approved root> --approve-project-enrollment --approve-index-execution` reuses the selected runtime/store. It holds the common writer/embed fence, rejects collection-name/path collisions, rechecks modern settings and records a generation/proof-bound owner-private `enrolled-projects.json`. It preserves the sealed initial scope policy, source/wiki, existing SQLite rows/vectors, model identity and active pointers. It queues normal update/embed without wiki regeneration or teacher/learning activation. Repeating a completed enrollment is unchanged. Interruption before enqueue retains approved intent with `queued:false`, so the same approved action resumes enqueue. Existing hooks maintain enrolled roots; marketplace reinstall retains their external runtime/DB/receipt paths. Legacy global DB/vector history is preserved rather than imported by enrollment.
