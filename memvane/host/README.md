# Host 응답과 route

SessionStart는 같은 호스트의 설치 메타데이터와 최근 1시간의 유계 이벤트를
읽는다. 현재 실행 번들이 그 호스트의 설치 버전보다 낮고 현재 세션의
최신 hook 기록도 옛 버전이면 세션을 다시 열도록 한 줄 안내한다.
최신 번들로 다시 연 세션·다른 호스트·종료한 세션의 기록은 안내하지 않는다.
hook에서 외부 CLI는 실행하지 않는다. 설치 버전이나 세션을 증명하지 못하면 안내를 생략한다.

편집 recall(`posttool`) 응답 뒤 capture는 기존 CPU share를 확보한 경우에만 supervisor를
시작한다. 프롬프트 recall은 학습 사례를 수집하지 않는다. share FD는 supervisor와 worker가 종료할 때까지 유지한다.

선택 프로젝트 레지스트리(`memvane/registry/memvane_registry.py`, `~/.local/state/memvane/v2/auto-context/registry/projects.sqlite`)는 선택된 main checkout과 연결 worktree 경로의 조회 색인이다. 행은 후보일 뿐이고 소비자는 기존 route 증명을 다시 한다. 활성화 성공 뒤 setup이 등록하고, restore·retire·abandon 성공 뒤 재관측으로 해제가 증명될 때만 `detached`로 바꾸며, 선택 route의 SessionStart와 `snapshot()`이 유계 reconcile을 한다. journal·route·ledger·store·intent를 쓰지 않고 새 lock·wake kind·hook action이 없다. resident service는 레지스트리를 다루지 않는다. 외부 편집 대상 탐색이 이 색인을 쓴다. 상태 규칙·예산·실패 방향은 `docs/project-registry.md`에 있다.

프로젝트 밖 원문 편집은 `memvane/wiki/intake/external_edits.py`가 소유 설치의 journal·route·provider attestation 메타데이터를 확인해 private blob 알림과 `laya-sync` wake를 전달한다. 외부 store는 훅에서 열지 않는다. 소유 sync 워커가 전체 write 증명·현재 blob·설정·compile 동의를 다시 확인한 뒤 기존 source 큐와 삭제 수명 주기로 넘긴다. recall과 로컬 compile 범위는 세션 프로젝트를 따른다. 범위·상한은 `docs/out-of-project-edit-routing.md`에 있다.

host route: `hooks/run-hook`은 `entry/run.py hook-classify`으로 action을 분류하고 선택된 route를 `memvane/host/host_response.py`에 전달한다. recall은 게시된 위키만 검색하고 질의 시점에 원문을 다시 읽지 않는다. 연결 worktree는 자기 view만 읽으며, 게시 head가 없으면 `view_preparing`, checkout이 읽는 동안 바뀌면 `checkout_changed`로 컨텍스트 없이 종료한다. SessionStart·성공한 편집·성공한 Bash는 main checkout에 `laya-sync` wake를 요청한다. `update`·`update-queued`·`file-change-event`처럼 sync와 함께 discovery grant를 기록하는 훅이 discovery lock 경합(`DiscoveryBusy`)을 만나면 `laya-sync` wake는 남기고 compile grant만 `busy_skipped`로 건너뛰어 exit 0으로 마친다(`compile`의 `owner_busy` 경로는 fail-closed를 유지한다). 미온보딩 프로젝트는 색인·recall·compile·학습을 하지 않으며 SessionStart에 setup 안내를 낸다. 연결 worktree의 wiki compile·수명 주기·학습 실행은 main checkout에서만 한다. 학습 사례 수집은 연결 worktree의 편집도 받는다. 선택 route의 거절은 fail-closed다. 선택된 설치에서 provider 파일을 일시적으로 읽지 못하면 recall은 빈 컨텍스트를 반환하고 main checkout의 gate는 편집 입력 검사를 통과하면 정상 종료한다. 이 경우 이벤트 사유는 `worker_attestation_unavailable` 또는 `production_attestation_unavailable`이다. 잘못된 편집 입력은 평소와 같은 사유로 거절한다.
- `host_response.py` — 선택된 Laya route의 hook 응답(`recall`·`update`·`update-queued`·`gate`·`posttool`·`index`·`compile` 등). 설치 journal의 선택 증명을 확인한 뒤 runtime을 연다. `wiki_card.py`는 선택 경로와 위키 worker가 공유하는 카드 읽기 헬퍼(frontmatter 파싱·source 해석·본문 추출)다. `event_log.py`는 설치 이벤트 로그(`<state root>/events.jsonl`) writer·reader이고, recall 진단은 `host_response._event_scope`가 hook 호출당 한 줄로 남긴다.
- `edit_recall.py` — `posttool`의 편집 recall 꼬리. 편집 증명과 route proof 재확인이 끝난 뒤 편집이 추가한 텍스트로 선택된 view를 검색하고, 세션에서 아직 주지 않은 카드를 최대 2장(본문 600토큰, selector가 답하지 못하면 기본 순위 1장) Claude·Codex PostToolUse `additionalContext`로 준다. hook 진입부터 10초 안에 끝나며, 예외·proof 변화·예산 초과는 `{}`·exit 0이고 sync·provider wake를 남기지 않는다. 세션 상태(이미 준 카드, 편집 recall 시각)는 install state root의 `edit-recall-sessions/`에 non-blocking flock으로 둔다. 이벤트는 `recall.edit` 한 줄이고, main checkout은 응답 뒤 `learning-capture` 자식에 후보 pool을 넘긴다. 끄는 스위치는 `MEMVANE_EDIT_RECALL=off`다.
- `session_cards.py` — 세션이 이미 받은 카드의 기록과 제외 규칙. 세션 파일(`edit-recall-sessions/<sha256(session id)>.json`, 24시간 단명 상태)은 주입한 `[path, blob sha]` 쌍과 함께 `seq`(카드를 주입하고 기록한 recall 수), `at`(주입 때의 `seq`), `by`(주입된 문맥: `p` 프롬프트, `e` 주 문맥의 편집, `e:<agent id 해시 8자>` subagent의 편집, `e?` 문맥을 모르는 편집)를 둔다. 프롬프트 recall(Claude·Codex)은 검색 전에 non-blocking shared lock으로 읽어 `p`·`e` 쌍을 검색에서 제외하고(`memvane.recall.api.set_session_exclusions`), 주입 뒤 exclusive lock을 50ms 간격 3회까지 시도해 기록한다. 편집 recall은 선택 뒤에 거르며 주 문맥은 `p`·`e`·`e?`, subagent는 자기 항목만 본 것으로 친다. 신호 없이 문맥에서 사라질 수 있는 항목(편집 주입 전부, compaction 신호가 없는 호스트의 전 항목)은 주입 뒤 recall 20회(`WINDOW`) 동안만 제외한다. SessionStart의 `source`가 `compact`·`clear`면 lock 없이 표식 `<세션 파일>.reset.<nonce>`를 쓴다. 표식이 있는 동안 읽는 쪽은 아무것도 제외하지 않고, 쓰는 쪽은 lock 안에서 본 표식의 쌍을 버린 뒤 기록하고 그 표식을 지운다. 24시간 지난 표식은 sweep이 지운다. 기록이 없거나 바쁘거나 깨졌으면 제외 없이 진행한다(그 recall 한 번의 중복). 이벤트: `recall`의 `sessionExcluded`·`sessionState`(`ok`·`none`·`busy`·`reset_pending`·`unavailable`·`write_skipped`)·`injectedBy`와 사유 `no_candidates_after_exclusion`(제외가 실제로 후보를 지운 빈 결과. 이때는 한 단어씩 묻는 폴백으로 넘어가지 않는다), `recall.edit`의 `agentScoped`·`injectedBy`, `update-queued`의 `sessionSource`·`sessionReset`. Hermes와 세션 id 없는 payload는 기록도 제외도 하지 않는다. 기록은 출력 전에 쓴다: 그 뒤 출력이 문맥에 닿지 않으면(제출 취소, 다른 hook의 차단, 연결 worktree 경로의 `selected_route_changed`) 그 카드는 본 적 없이 제외된다(누락 방향의 잔여, 창 20회나 세션 초기화가 푼다). 세션 파일은 64KB(`MAX_SESSION_BYTES`)를 넘지 않게 저장 때 오래된 쌍부터 버린다(긴 비ASCII 경로는 글자당 6바이트).
  main checkout 세션이 같은 저장소의 연결 worktree 파일을 편집하면 그 편집은 main 프로젝트의 편집이다(`edit_checkout`). 편집 경로의 가장 가까운 `.git`을 stat으로 찾고, worktree 모양의 `.git` 파일일 때만 그 worktree의 프로젝트 root를 `select_route`로 분류한다. 결과가 `worktree`이고 main route의 정체성이 세션 route와 같아야 받는다. git은 checkout당 `rev-parse` 2회이고 일반 checkout 편집에서는 실행하지 않는다. 증명은 길이·throttle 검사보다 먼저 돌며 자체 상한은 1초다. 검색과 후보 pool은 main view이고, 경로 규칙과 상대 경로는 worktree의 프로젝트 root 기준이며 worktree settings의 `skipPaths`를 main의 것에 더한다. main 경로가 하나라도 있으면 main 경로만 쓰고, 없으면 증명된 worktree 한 곳의 경로만 쓴다. 두 곳이면 `skip_mixed_checkout`, 증명 실패는 `skip_outside_project`, 증명 시간 초과는 `skip_checkout_proof_timeout`이다. 저장소 밖 폴더는 받지 않는다. 연결 worktree를 cwd로 연 세션의 편집 recall은 자기 view로 검색하고, 그 pool의 카드가 전부 main 게시 head와 같을 때만 main 프로젝트의 사례가 된다(다르면 `edit_view_diverged`로 저장하지 않는다). main root 안의 별도 clone과 submodule 경로는 main 경로로 다룬다. 카드의 자기 인용 제외는 상대 경로 일치로 판정하므로 branch가 옮기거나 이름을 바꾼 파일은 제외되지 않는다. `posttool` 행은 `editTarget`(`main`·`linked`·`linked_unproved`·`mixed`·`outside`)과, git을 실행한 경우 `checkoutProofMs`를 남긴다.
- `posttool.py` — 편집 hook payload의 경로 추출 helper. hook entrypoint가 아니고 `wiki_compile_enqueue`가 import한다.
- `compile` 액션(Claude/Codex)과 Hermes `index` 내부 편집 경로는 `sync_owner`·큐 락을 잡지 않고 `wiki_compile_enqueue.enqueue_payload(..., pending_only=True, selected_route=(decision, proof))`로 `record_pending_refresh(..., compact=False, lock_timeout=0.15)`로 `.memvane/compile/edit-inbox.jsonl`에 한 행만 덧붙인 뒤 `laya-compile` wake를 요청한다. 훅은 `wiki-pipeline.sqlite3`를 열지 않는다. `update`/`update-queued`는 compile이 켜진 선택 프로젝트에서 매번 `laya-compile` wake를 요청하고(wake 큐가 합치고 할 일 없는 pass는 원장 조회 한 번으로 끝난다), inbox 크기를 `editInbox` trace로 남긴다. 이 wake가 기록되지 않으면 `selected_compile_enqueue_failed`로 거절한다.
- hook 진입은 `hooks/run-hook`과 `entry/run.py`가 담당한다. `wiki_compile_enqueue`는 선택된 hook 응답이 호출하는 source 큐 함수다.
### hooks (`hooks/`) — 유일한 훅 진입점
> Claude/Codex/Gemini의 훅 진입점은 `hooks/run-hook` 단일 디스패처다. Hermes Agent는 별도 host protocol이므로 Python plugin adapter(`plugin.yaml`, `__init__.py`, `hermes_adapter/`)가 같은 core 스크립트를 호출한다. **도메인 로직은 여전히 core/가 SSOT**다.

- `run-hook` — 공통 디스패처(bash). 호출: `run-hook <action> <engine>` (engine: claude|codex|gemini). `hooks.json`·`hooks-codex.json`이 등록한 action은 `update-queued`(SessionStart), `recall`(UserPromptSubmit), `gate`(PreToolUse), `posttool`·`index`·`compile`(PostToolUse 편집 도구), Claude 전용 `file-change-event`(PostToolUse Bash)다. 처리 순서: sandbox/headless 가드 → 모든 action을 `entry/run.py hook-classify`으로 분류 → `candidate|preview|worktree`면 `entry/run.py hook-serve`으로 exec, `blocked`면 "request refused"로 exit 3, `legacy`면 무작업 exit 0. 분류 예외는 `error`를 출력한다. recall은 컨텍스트 없이 종료하고 SessionStart는 오류를 알리며 온보딩을 제안하지 않는다. `recallQuiet`가 붙은 `blocked`(멈춘 활성화·복원이 남긴 marker만 있는 프로젝트 `selection_route_missing`, 준비 중 설치의 preview 증명 실패)는 recall에 한해 `legacy`로 출력해 컨텍스트 없이 exit 0이다. `majorMismatch`가 붙은 `blocked`(다른 플러그인 메이저의 route·marker)는 모든 action에서 `legacy`로 출력하고, `update-queued`의 안내는 온보딩 대신 메이저 불일치 한 줄(`onboarding_notice.MAJOR_NOTICES`)이다. 포인터는 있으나 ledger·journal이 활성화·복원 도중인 설치는 선택 증명이 `selection_transition_pending`으로 거절하고, recall은 이것을 컨텍스트 없는 exit 0으로 답한다. `legacy`의 `update-queued`만 온보딩 안내 한 줄(`onboarding-notice`)을 출력한다. 플러그인 루트는 `run-hook`의 위치에서 정한다. 도메인 로직은 `memvane/`에 있다.
- `hooks.json` — Claude hooks (`${CLAUDE_PLUGIN_ROOT}`). `hooks-codex.json` — Codex hooks도 **`${CLAUDE_PLUGIN_ROOT}`**를 쓴다(형태: `"${CLAUDE_PLUGIN_ROOT}/hooks/run-hook" <action> codex`). Codex가 신뢰성 있게 주입하는 plugin-root 변수가 CLAUDE_PLUGIN_ROOT이고, 로컬 캐시의 OpenAI codex·zax·superpowers 등 **모든 codex 플러그인이 codex hooks에서 이 형태를 쓴다**(shell 확장이든 텍스트 템플릿 치환이든 양쪽 메커니즘에서 입증된 유일한 형태). `${PLUGIN_ROOT}`(codex 바이너리가 인식하는 alias지만 간헐적으로만 주입)를 단독으로 쓰면 비었을 때 command가 `/hooks/run-hook`으로 해석돼 **exit 127**(command not found)이 난다 — 실패 지점이 command 확장 단계라 run-hook 내부 dirname fallback으로는 못 막는다. **novel한 `${VAR:-fallback}` 파라미터 확장이나 `;`/`&&` 제어 연산자는 쓰지 않는다**: 어떤 codex 플러그인도 안 쓰는 문법이라, codex가 shell이 아니라 템플릿 치환을 하면 매칭/해석에 실패할 수 있다. run-hook 내부는 여전히 `CLAUDE_PLUGIN_ROOT→PLUGIN_ROOT→dirname` 순서로 방어한다(도달만 하면). CLAUDE_PLUGIN_ROOT 자체가 비면 여전히 127인데, 이는 codex-level 상태로 OpenAI 공식 포함 모든 codex 플러그인에 동일하게 영향한다(우리만의 문제 아님). PreToolUse `gate`도 이 경우 127로 죽어 deny를 못 내므로 pending 편집 차단이 fail-open된다(수용 가능한 트레이드오프). Codex 공식 문서상 same-event command hooks는 동시 실행될 수 있으므로 posttool/index/compile은 서로 순서 의존하면 안 된다.
- Antigravity(agy)는 공식 PostToolUse payload에 edited file path/tool input이 문서화되어 있지 않고 stdout contract도 `{}`라서, AGY 자동 hook은 설치하지 않는다. AGY 자동 posttool/index/compile은 전용 payload adapter가 생긴 뒤 재활성화한다.
- `hooks.json`은 **표준 구조** `{hooks:[{type:"command",command}]}`를 따라야 한다. 비표준 구조면 호스트(Claude/Codex)가 훅을 인식 못 함.
- 매니페스트: `.claude-plugin/plugin.json`, `.codex-plugin/plugin.json`(+`interface`, `hooks` 경로 명시).

### Hermes Agent plugin (`plugin.yaml`, `__init__.py`, `hermes_adapter/`)
- Hermes는 Claude/Codex hook JSON을 읽지 않고 Python plugin system을 쓴다. root `plugin.yaml` + `__init__.py`가 `hermes_adapter.plugin.register(ctx)`를 노출한다.
- Hook mapping: `pre_llm_call`→`recall`, `on_session_start`→`update-queued`, `pre_tool_call`→`gate`, `post_tool_call`→`posttool`+`index`. `hermes_adapter/core_bridge.py`가 route를 분류해 선택된 route에서만 `memvane.journal.api.select_route` → `host_response.serve_selected`로 넘긴다. `legacy`는 무작업이고, 그 밖의 상태는 경고만 남기며 QMD로 폴백하지 않는다(gate는 block).
- Hermes `post_tool_call` 반환값은 observer-only라 같은 턴 모델 컨텍스트에 posttool 힌트를 주입하지 않는다. 따라서 Hermes 경로의 편집 후 동작은 자동 인덱싱 중심이며, Claude/Codex posttool 컨텍스트 주입과 동일하다고 문서화하면 안 된다.
- Hermes `on_session_start`도 context 주입 채널이 없어(반환값 미사용) SessionStart 안내가 표면화되지 않는다. 미온보딩 프로젝트의 온보딩 안내도 Hermes에는 나가지 않는다.
