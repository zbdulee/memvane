# 설치 증명과 번들

- `ledger_common.py`는 선택 ledger의 비공개 JSON 읽기·쓰기, ledger lock, 프로젝트 단위 operation lock과 settings preflight를 제공한다.
- 설치 준비는 review digest와 provider attestation을 확인한다.

# 설치·정리와 내부 명명

임베딩 모델과 학습 추론은 사용자당 하나인 `memvane/resident/resident_service.py` 프로세스가 호스팅한다. 서비스는 설치별 socket과 owner lease를 통해 worker를 공유한다.
### 설치 / cleanup
Claude·Codex는 marketplace plugin install이 제품 경로다. 제품용 `install.sh`/`uninstall.sh`는 없다. AGY는 공식 PostToolUse payload adapter 전까지 자동 hook을 설치하지 않는다.

live `v1/`에 쓰는 setup·writer·wake 큐·sync owner lock·resident service는 실행 플러그인 루트가 Claude 또는 Codex의 `plugins/cache/<marketplace>/memvane/<version>`이나 Hermes의 `~/.hermes/plugins/memvane`일 때만 연다(`memvane/kernel/memvane_execution_guard.py`). `MEMVANE_TEST_ALLOW_UNINSTALLED_ROOT=1`은 격리 시험 전용이고 `MEMVANE_TEST_RUNTIME_ROOT`가 함께 있을 때만 인정한다.

설치 기록(provider attestation, journal, 프로젝트의 `route.json`·`selection.json`)은 옆 파일에 완성해 fsync한 뒤 덮어쓰지 않는 rename으로 게시한다. 중단된 생성은 기록을 남기지 않고, 같은 단계의 재실행이 남은 조각을 지우고 다시 만든다.

새 머신의 Laya embed runtime은 `setup_entry.py provision-index-runtime --approve-index-runtime-download`가 만든다(`memvane/provider/embed_runtime.py`). Node는 `PATH`를 먼저 보고 mise/fnm/nvm/volta/asdf/Homebrew/system 설치 순으로 찾되 메이저 22/24/26의 실제 바이너리만 받는다(버전 매니저 shim은 거절). `locks/laya-embed-runtime`(node-llama-cpp 3.18.1 + prebuilt `@node-llama-cpp/mac-arm64-metal`)를 `npm ci --ignore-scripts`로 설치하고, GGUF는 `https://huggingface.co/ggml-org/embeddinggemma-300M-GGUF/resolve/main/embeddinggemma-300M-Q8_0.gguf`에서 받아 sha256 `f470220f84b6235197541352d22f10bf00098a8242c18eaacea9c8a4add557bc`과 일치할 때만 채택한다(`--provider-model-file`로 같은 GGUF의 로컬 사본 지정). 결과는 `~/.local/state/memvane/v1/embed-runtime`의 세대 디렉터리와 `active.json`·`previous.json`이다. `gc-index-runtime`은 active·previous·`~/.local/state/memvane/v1/installs/*/provider-attestation.json`이 가리키지 않는 세대를 나열하고 `--approve-index-runtime-gc`가 있을 때만 지운다(attestation의 과거 `profileDependencyClosure` 행은 보지 않는다).


### 이름과 내부 명명
- 제품 이름은 MemVane, 플러그인 id는 `memvane`, marketplace는 `memvane-marketplace`, 저장소는 `zbdulee/memvane`이다. skill id는 `memvane:<skill>`, 색인 DB의 사용자용 이름은 memvane-db, hook·안내 메시지 태그는 `[memvane]`이다.
- 사용자별 루트는 `memvane/kernel/memvane_paths.py`가 정한다: 상태 `~/.local/state/memvane/v1`(설치별 state root, `embed-runtime`, `service`, `initial-builds`, `auto-context` 로그·scan state: 프로젝트 폴더와 별개인 사용자별 디렉터리라 이름이 그대로다), 지원 디렉터리 `~/Library/Application Support/memvane`(그 밖의 OS는 `~/.local/share/memvane`), 설정 `~/.config/memvane`, 캐시 `~/Library/Caches/memvane`·`~/.cache/memvane`. 새 설치·온보딩은 이 루트에만 쓴다.
- 내부 명명은 `core/laya_*.py` 모듈, Laya 엔진 용어, `configFormat` 값 `auto-context-dir`, `QMD_*` 환경 변수를 쓴다. 프로젝트 포인터는 `.memvane/route.json`과 `.memvane/selection.json`이다.
- 프로젝트 폴더는 `.memvane/`다. 설정, `wiki/`, route·selection·lock·`compile/` 런타임 파일을 이 폴더에 둔다(`memvane/settings/project_dir.py`).
- resident service는 사용자별 서비스 루트에서 동작한다. worker는 바인딩과 진행 중 요청이 없으면 `RECLAIM_SECONDS` 뒤 정지한다. 바인딩은 `OWNER_RECHECK_SECONDS` 간격으로 소유를 재증명하며, owner 잠금 경합이면 바인딩과 socket을 유지한다. `LAYA_SERVICE_TIME_SCALE`은 fixture 전용 내부 환경 변수다.
- wiki-dedup resolver는 프로젝트별 run-lock을 사용한다.
- 프로젝트 단위 lock 이름은 `laya-qmd-cutover-operation.lock`, `.topical-publish.lock`이다.
- 위키 카드 소유 표시: 새 카드는 `createdBy: memvane`과 `> Auto-generated by MemVane` 상투구를 쓰고, 읽는 쪽은 `qmd-auto-context`도 같은 소유로 본다(`wiki_markers.CREATED_BY_NAMES`·`AUTO_DISCLAIMER_PREFIXES`).

런타임 선택은 provider·worker 파일과 모델·런타임 정체성을 확인한다.

`runtime_wake_cancel.py`는 프로젝트의 `laya-sync` 빌드 wake 행을 읽기 전용으로 보여 준다(`build-wake-status`). 큐 읽기는 runtime api `wake_cancel_status`가 한다. 1.0에는 wake 행을 지우는 취소 명령이 없다.

## 온보딩 use case

plan·prepare·finalize·activate·recover·restore는 모두 `install.api`에 있다. 설치 ledger(`ledger.json`, `memvane-install-ledger-v1`)는 install만 쓴다(`application/onboarding_activation.py`의 finalize·activate, `application/onboarding_restore.py`의 restore). finalize는 원문 관측(`wiki.intake.api.schema3_wiki_cards`·`schema3_sources`)을 직접 부르고, 위 층의 sync dispatch 확인 하나만 `resolve_sync_target` keyword port로 받는다. `activate_origin_selection`·`recover_origin_selection`은 호출자가 state root의 `install_lock`을 쥔 채 부르고, `select_origin`은 route를 읽고 그 lock을 직접 잡는 CLI용 입구다.

## 온보딩 단계의 재실행

`application/onboarding_workflow.py`(plan·provider review·prepare·build status·rescan), `application/onboarding_restore.py`(restore·abandon·foreign pointer 교체)와 `application/onboarding_activation.py`(finalize·activate·recover)의 각 단계는 임의 지점에서 멈춘 뒤 같은 명령을 다시 실행하면 같은 결과로 수렴한다.

- `prepare`는 raw 원문을 sync와 같은 상한(4,096 파일·64 MB)으로 먼저 스캔하고, 넘으면 빌드 전에 `raw_scan_limit_exceeded`로 거절한다.
- 영속 기록(`route.json`의 `stateNode`·`storeNode`, reader 기록의 `*_node`)은 재실행에서 inode로 대조하고 기록된 `st_dev` 바이트를 유지한다. plan의 `scopeId` seed는 프로젝트 경로·inode·settings sha256이고 `st_dev`를 넣지 않으므로, 재부팅 뒤에도 같은 plan이 나오고 그 digest로 `prepare`를 다시 실행할 수 있다.
- `finalize`는 게시 head 뒤에 위키 카드나 raw 원문이 바뀌었으면 빌드를 `building`으로 되돌리고 wake를 요청한 뒤 `initial_build_pending`을 낸다. 빌드가 다시 `ready`가 되면 다음 `finalize`가 활성화 전 reader 기록을 새 head로 다시 봉인한다. `activate`가 `initial_build_out_of_date`·`initial_build_head_changed`로 거절하면 `finalize`부터 다시 실행한다.
- `activate`는 포인터를 쓰기 전이면 이전 활성화가 남긴 비활성 discovery snapshot을 새로 증명한 snapshot으로 바꾼다.
- `build-rescan`(`index-build-rescan`)은 journal이 `prepared`이고 프로젝트 포인터가 없을 때만 동작한다. 선택 뒤에는 `initial_build_already_selected`로 거절하고 갱신은 sync owner가 맡는다.
- `restore`는 활성화 전 설치를 버린다(abandon): journal을 `restored`로 바꾸고 build 포인터와 `build.json`을 지워 새 install id의 `prepare`가 시작되게 한다. 활성화 뒤에는 첫 선택 쓰기 전까지 포인터를 거둔다. 첫 쓰기 뒤에는 attestation의 provider·모델·런타임이 이 호스트와 다를 때만 선택을 해제하고(`released`), 그 밖에는 `rollback_forward_only`다. 어느 경우에도 state root·store·journal·ledger는 남고 정리는 사용자 runbook·gc가 맡는다. `build.json`은 마지막에 지우므로, 그 뒤의 재실행은 `restored` journal을 읽고 `changesApplied: 0`을 낸다. 프로젝트 포인터가 더 낮거나 모르는 메이저의 것이면(hook의 `majorMismatch` `other`) `restore`는 state root를 읽지 않고 그 포인터만 지운 뒤(불일치를 가진 파일을 마지막에) `released`를 내고, 다음 plan이 새 온보딩을 시작한다. 더 높은 메이저의 포인터는 지우지 않는다.
- `recover`(`recover-index-origin`)는 ledger가 있으면 멈춘 활성화나 restore를 끝낸다. ledger가 없으면(finalize 전) journal이 이미 `restored`인 abandon만 마무리하고, 그 밖에는 `initial_build_not_finalized`로 거절한다. 설치를 버리는 것은 승인된 `restore`만 한다.
- `plan-fresh-wiki`는 프로젝트에 `route.json`·`selection.json`이 있으면 `project_selection_already_exists`로 거절한다. 단 hook이 `legacy`/`foreign_install`로 분류하고 모든 포인터가 이 기계에 state root가 없는 한 1.x 설치를 가리키면, plan은 그 바이트의 sha256을 `replacesForeignPointers`에 담고 `prepare`가 빌드 등록이 성공한 뒤 route, marker 순으로 지우고 그다음 빌드 wake를 요청한다. 등록이 거절되면 포인터 파일은 그대로 남는다. 이 기계에 있는 설치나 다른 메이저를 가리키는 포인터는 지우지 않는다. 두 파일 사이에서 멈추면 다시 plan한 뒤 `prepare`한다.
