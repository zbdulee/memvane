# Wiki verify와 수명 주기

검수 행과 교체본이 기록한 원문 SHA-256이 현재 원문과 다르면 유료 검수를 생략한다. 카드 쓰기 잠금 안에서 원문·교체본·행의 정체성을 다시 확인하고 `verify-deleted.jsonl`과 검수 로그에 `pending_source_changed`를 기록한다. 파일 정리는 큐와 다른 claim의 참조, 파일의 inode·길이·변경 시각을 대조한다. 같은 대상의 서로 다른 원문 revision은 각각 판정하므로 뒤늦게 재생한 행이 현재 revision의 검수를 덮어쓰지 않는다.

혼합 버전에서 공용 backfill 집계와 카드 검수 결과는 별도로 확인한다. 구 worker의 E1 추출이 영구 실패하면 공용 cohort는 `complete_with_skips`를 표시한다. native가 private 기록에서 남은 형제 B를 재개해 게시·검수한 뒤에도 이 표시는 남는다. B의 검수 결과는 해당 카드의 marker·원문 revision·검수 본문 지문으로 확인한다.

기존 보이는 카드를 교체할 때 외부 편집을 배제할 근거가 없으면 writer는 원행과 후보를 프로젝트의 private 인계 기록에 보관한다. 구버전만 실행되는 동안 교체는 대기한다. native verifier는 교체 순간의 기존 파일을 원자적으로 보존할 수 있을 때만 승격한다. 편집기가 그 사이에 저장한 카드도 보관 경로에서 다시 열 수 있다. 대상별 이력에서 수기 삭제가 확인되면 그 삭제를 보존한다. 해당 이력이 전부 사라진 대상은 새로 만들 수 있어 사람이 지운 카드도 다시 생성될 수 있다. 온라인에서는 혼합 공용 원장의 inode와 기존 행을 보존한다. 무관한 카드를 만들면 `generated-manifest.jsonl` 끝에 그 생성 행을 덧붙인다. 첫 일반 검수 행도 private에 보관하므로 구버전만 실행될 때에는 첫 검수가 대기한다. native는 첫 stamp를 쓸 때도 그 순간의 기존 파일을 원자적으로 보존한다.

writer는 대상마다 검수할 교체본 한 건을 넘긴다. 파일 옆의 이름이 기존 후보와 충돌하면 해당 파일을 보존하고 다른 마커로 최신 후보를 등록한다. 숨김 교체본의 정리는 원문 revision이 낡았거나 후속 후보가 이를 대체한 근거, 해당 경로를 쓰는 다른 작업, 파일의 정체성을 확인한 뒤 진행한다. 참조나 소유 관계가 불분명하면 파일과 원행을 보존한다. 같은 원문을 인용하는 검수 claim이 있으면 compile worker는 추출을 미루고 원문 작업을 유지한다.

선택된 compile wake와 직접 실행한 worker는 source와 검수의 미완료 작업을 각각 확인한다. 검수 큐에 보류한 대상이 있어도 독립 source 작업을 회수할 수 있다. 한 대상에 서로 다른 후보가 있으면 현재 원문 SHA, pending의 마커·원문 기록, 게시 카드의 SHA를 대조해 지금 검수할 후보를 정한다. 큐 교체와 구 verifier의 claim은 같은 잠금을 쓴다. 삭제 감사는 큐 교체 성공 후 확정하며, 재시도는 같은 정리 작업의 감사 행을 재사용한다.

혼합 버전에서 보호가 시작되는 시점은 1.1.1 큐 소유자가 검수 큐 잠금을 획득해 해당 대상을 정규화한 때다. SessionStart는 wake를 예약한다. 이전 writer가 중복 행을 남긴 뒤 그 잠금을 1.0.22~1.1.0 verifier가 먼저 얻으면 그 claim 한 배치는 이전 규칙으로 처리될 수 있다. 그 구간에는 시간 상한이 없다. 이미 넘어간 claim은 소유자가 반환한 뒤 다음 pass에서 다시 확인한다.

한 번에 검사하는 범위는 live 큐와 claim을 합쳐 8 MiB, claim 64개다. 큰 단독 live 큐나, live가 비고 소유 프로세스가 종료된 단독 대형 claim은 원본 inode를 private에 보관하고 여러 pass에 나눠 읽는다. 줄 끝은 바이트 LF로 판정한다. 판독할 수 없는 원행과 잘린 끝부분도 보존한다. 구 writer가 열린 파일에 뒤늦게 나머지 바이트와 LF를 쓰면 같은 inode에서 완성된 행을 이어서 처리한다.

65번째 claim 때문에 숨김 경로의 모든 참조를 확인할 수 없으면 공용 행과 claim을 그대로 두고, 교체 원행과 후보 이미지를 private에 보관한다. 처음 생성할 경로도 구 claim의 대상일 수 있으면 최초 노출을 보류한다. claim이 끝나면 참조를 다시 확인해 후보를 검수·게시한다. 그동안에도 현재 원문 revision·marker·카드 본문이 확인되는 독립 일반 카드는 검수할 수 있다. 원래 행을 다시 만날 때는 같은 카드의 완료 근거를 대조해 중복 검수를 피한다.

프로젝트의 보류 사본 한도는 64 MiB다. 한도가 차면 사본이 필요한 교체는 기존 카드와 원문 작업을 유지하고 공간이 생긴 뒤 재시도한다. 원본 inode를 보유한 배치는 계속 읽을 수 있다. 첫 게시와 검수를 위한 제어 기록을 쓸 수 있으면 독립 카드는 새로 만들고 검수할 수 있다. 제어 기록을 쓸 공간이 없어도 이미 검수된 카드의 본문·마커와 현재 원문 revision이 일치하면 공용 큐의 단일 일반 행을 추가 모델 호출 없이 완료한다. 대조에 실패하면 원행을 유지한다.

- `wiki_verify_worker.py` — 기계 검수(auto-verify). writer는 generated 카드의 원행과 이미지를 private에 보관한다. compile worker가 종료할 때 verifier는 이 기록과 이전 버전이 남긴 검수 큐를 같은 예산으로 처리한다. **per-run 예산은 `max(verify.maxPerRun, min(그 run이 만든 카드 수, VERIFY_PRODUCED_HARD_CAP))`다** — 고정 상한이면 생산 속도가 배수 속도와 무관해 큐가 자라고, `recallVerifiedOnly` 기본값 아래에서 `generated`로 남은 카드는 recall에 나오지 않는다(문서 10개를 편집해 카드 20장이 생기면 배수 3에서 7 run이 필요하고, 그 사이 정확한 카드가 recall에 나오지 않는다 — 백필과 무관한 평상시 병목이다). `maxPerRun`을 그냥 크게 잡는 것은 상수라 같은 문제를 되풀이하므로 하한을 **그 run의 생산량**에 묶는다. **그러나 생산량은 모델 출력에서 유도된 값이므로(`len(candidates)`) 반드시 상한을 씌운다** — 안 씌우면 카드 40장을 낸 run이 verify 200회를 돌려 모델이 과금을 정한다. 사람이 적은 `maxPerRun`은 언제나 존중하고 모델 유도분만 `VERIFY_PRODUCED_HARD_CAP`(30)으로 자른다. **예산을 키우는 것만으로는 목표가 달성되지 않는다**: 큐가 FIFO라 `kept[:budget]`이 예산을 **가장 오래된 backlog**에 써 버려 그 run의 카드는 그대로 `generated`로 남았다(실측: backlog 4 + 신규 2, 예산 2 → backlog 2장만 검수). 그래서 worker는 개수가 아니라 **경로 목록**(`produced_targets`)을 넘기고 verify는 그 카드를 **먼저** 처리한 뒤 남은 예산으로 backlog를 드레인하며, backlog가 있으면 **1건은 항상 예약**해 대량 생산기 동안 기아가 생기지 않게 한다. 생산량은 `wiki_compile`이 verify 큐에 실제로 append했을 때만 결과 JSON에 넣는 `verifyQueued`/`targetPath`로 얻는다(카드 수 추정이나 큐 줄 수 재기는 판정 조건을 두 곳으로 갈라놓는다). 생산이 없는 run(기존 backlog 드레인)에서는 예산이 커지지 않는다 — 하한이지 대체가 아니다. **검증 근거의 권위는 큐가 갖는다**: `candidate.sources`는 모델 출력이고 `load_sources`는 목록 **앞에서** `MAX_SOURCES`(3)개만 읽으므로, 모델 목록이 앞에 오던 동안에는 모델이 decoy 3개를 내면 카드가 **실제 원문 없이** 검증돼 `verified`(= `recallVerifiedOnly` 기본값에서 인용 가능한 캐논)가 됐다 — 검증 전제 자체를 무력화하는 클래스다. 두 층으로 막는다: (1) `wiki_compile_worker`가 실제 소스를 목록 **맨 앞**에 두고 같은 경로의 모델 항목을 버린다(`is_same_file_source` — 경로만 본다. dict 완전 일치는 `collection`만 다른 중복을 남겼다), (2) 실제 소스를 `authoritativeSources`로 **별도 필드**에 못박아 `load_sources`가 `MAX_SOURCES`와 무관하게 반드시 읽게 한다(순서만으로 보장하면 그 계약이 암묵적이라 다음 편집에서 조용히 깨진다). 이 필드는 verify 잡에만 있고 frontmatter로는 나가지 않으며(`markdown_page`는 `sources`만 읽는다) `wiki_compile.authoritative_sources`가 닫힌 스키마로 재구성한다. 0.x 잡·수동 compile 경로엔 키가 없어 기존 동작 그대로다. **`engine`/`trigger`를 setdefault→대입으로 바꾼 것과 같은 원칙이다 — 사실은 큐가 정하고 모델은 의견만 낸다.** verifier는 extractor와 동일 adapter 풀을 payload `{"task":"verify"}`로 재사용해 카드 주장 vs 원문 소스를 적대 대조하되, **엔진은 카드를 만든 엔진과 분리한다**(`compile.verify.crossEngine` 기본 `prefer` — 다른 엔진을 먼저 시도하고 없으면 같은 엔진으로 검증). **`pass`는 근거를 요구한다** — `claims`가 비어 있거나 항목이 전부 퇴화한 값(`null`·`""`·`{}`)이면 `pass`로 처리하지 않고 `invalid_verdict`로 다룬다. `pass`가 `verified`의 유일한 입구이고 `verified`는 `wiki_card.is_auto_trusted_card`를 통과해 캐논급으로 주입되므로, 근거 0인 `pass`는 곧 "무관한 요약이 trusted 카드가 된다"다(원문과 정반대인 카드 요약 + `{"verdict":"pass","claims":[]}` → `verified` 로 재현). **`fail`/`inconclusive`로 강등하지 않는다** — 둘 다 기본 동작이 카드 삭제인데 근거 없는 pass 는 "원문과 모순"도 "판정 불가"도 아니고 **출력이 못 쓸 것**이다. `invalid_verdict` 경로는 카드를 지우지 않고 `generated`로 남긴다(= recall 비가시, 소스를 고치면 재검증이 열린다). 라이브 3프로젝트(ai-proxy·rccar·ktlo-check) `verify-log.jsonl`의 `pass` 319건이 전부 `claims > 0`이고 `pass + claims=0`은 0건이라 이 조건은 실제 verifier 출력을 하나도 거부하지 않는다. **`supported`/`quote` 값까지는 보지 않는다** — 그것은 프롬프트가 모델에 맡긴 verdict 규칙을 소비자에서 재구현하는 것이고, 모양 검사는 퇴화한 출력을 거부할 뿐 거짓말하는 adapter 를 막지 못한다(`[{}]`를 만들 수 있는 adapter 는 완전한 모양도 만든다). `lib.emit_verdict`에서 exit 1로 막지 않는 이유는 비127 종료가 transient 로 분류돼 잡이 영구 보존되고 cooldown 만료마다 재호출되는 과금 루프가 되기 때문이다 — worker 쪽이 유일하게 옳은 층이고 명시 argv/`backends` adapter 도 함께 덮인다. pass → `status: verified`+`verifiedBy`/`verifiedAt`/`verifiedMode` 패치(recall 검수급 대우, 단 `is_auto_writable_page` 보호 집합엔 불포함 — 소스 변경 시 자동 갱신되고 갱신 시 generated로 리셋·재검증), fail → `compile.verify.onFail` 기본 `delete`(카드 즉시 삭제, tombstone 없음 — 소스 수정 시 재생성 가능), **inconclusive → `compile.verify.onInconclusive` 기본 `delete`**(값 집합은 onFail과 동일하고 `none`이 0.x 하위호환 "generated 유지"), **쓰기 반환값을 삼키지 않는다**: `stamp_verification`이 실패하면(디렉터리 권한·ENOSPC) 카드는 `generated`인데 로그에 `verified`가 남고 큐에서도 사라져 재시도 없이 유료 호출만 소모되고 그 카드가 `recallVerifiedOnly` 아래 **영구 비가시**가 됐다 — 실패는 `stamp_failed`로 로그에 남기고 **잡을 보존**한다. `record_verify_deletion`(삭제 전용 감사 원장)이 실패하면 **삭제하지 않는다**(fail-closed) — 미검수 카드가 하루 더 남는 것과 설명 없이 사라진 카드는 등급이 다르고, 후자는 원장에 본문이 없어 복구도 사후 판단도 불가능하다. **inconclusive 억제 마커(`verify-skipped.jsonl`)도 같은 처방을 받는다**: 삭제 **전에** 쓰고 실패하면 지우지 않고(`delete_blocked`/`suppression_ledger_unwritable`) 잡을 보존한다 — 삭제·감사 기록 **뒤에** 쓰고 실패를 삼키면 카드는 사라지고 마커가 없어 unchanged source가 재컴파일→재검수→재삭제를 반복한다(매 반복이 유료 호출). 그래서 `record_verify_suppression`은 `(written, ok)`를 돌려준다 — 0건은 정당한 경우(소스 전멸)가 있어 개수만으로는 실패를 구분할 수 없다. 순서는 **감사 원장 → 억제 마커 → 삭제**다(억제를 먼저 쓰면 감사 실패 시 지워지지도 않은 카드의 소스가 영구 억제된다). 그리고 유료 호출 전 preflight는 **두 원장 모두**를 본다(`preflight_block_reason` — `onInconclusive`가 실제로 `delete`일 때만 억제 원장을 검사한다). 이 함수가 SSOT다. `verify_skipped_path`도 `verify_deleted_path`와 **같이 기본 경로로 폴백한다** — 오타 하나가 "마커가 한 줄도 안 남는" 상태를 만들면 그게 곧 과금 루프다. transient(CLI 부재 127/timeout) → 큐 보존+**후보 단위** cooldown(`verify-engine-cooldown.json` — compile cooldown과 분리). transient를 inconclusive로 오분류하면 verifier CLI 없는 머신에서 카드가 전멸하므로, verdict 분기는 반드시 유효 JSON verdict를 받은 뒤에만 도달해야 한다. 판정은 `verify-log.jsonl`에 기록되며 256KB 초과 시 최근 절반만 유지(트림) — pass까지 담는 운영 로그라 활성 프로젝트에서는 며칠치만 남는다(실측: service-engineering에서 3주치 이력이 이미 밀려나갔다). **기계 판정이 카드를 지우는 유일한 게이트이므로 삭제 사유는 트림하지 않는 `verify-deleted.jsonl`(`compile.verify.deletedPath`)에 별도 보존한다** — fail·inconclusive 공통, 삭제된 카드 1건당 1줄(targetPath/verdict/engine/reasons/sourcePaths/deletedAt, 원문 본문 미포함)이라 무제한 누적 위험이 없다. inconclusive는 추가로 `verify-skipped.jsonl`(source+bodyHash 키, 과금 루프 억제 겸용)에 남고, 두 verdict 모두 manifest에 `verify-deleted` action 행을 남긴다(compaction은 identity별 최신 행만 남기므로 카드가 재생성되면 대체된다 — 지속 감사 추적은 `verify-deleted.jsonl`이 SSOT).
  - **검수 엔진 규칙.** (1) 카드를 만든 엔진이 별도 호출로 검수한다(`plan_verify_attempts`, `verifiedMode: self`). argv 해석은 `resolve_extractor_argv` 한 벌이고 `compile.verify.builtins`는 해석용 이름만 더한다. 다른 설치된 CLI로 대신 검수하지 않는다(카드 한 장에 유료 호출이 둘이 되고, 생산 엔진이 특정되지 않으면 자기검증 여부를 증명할 수 없다). (2) 생산 엔진 라벨의 SSOT는 **큐 잡**이다: `candidate.engine`은 모델 출력이라 worker가 잡 값으로 **덮어쓴다**(`setdefault` 금지). sentinel `UNKNOWN_ENGINE`·해석 불가 라벨은 `producing_engine_unavailable`로 잡을 보존한다. (3) **유료 호출은 카드당·run당 1회.** 유료 실패(인증 안 된 CLI·verdict 미출력·timeout)는 `set_engine_cooldown`으로 그 엔진을 식히고 식힘 중이면 `engines_cooling`으로 보존한다. 어느 경로도 verdict를 만들지 않으므로 transient→inconclusive(=삭제) 오분류는 구조적으로 불가능하다. **식힘 기록의 False를 삼키면 안 된다**(`cooldownWriteFailed`로 표면화) — read-modify-write는 sidecar flock으로 직렬화하고 만료값은 24h 클램프다. `invalid_extractor_json`/`invalid_verdict`는 같은 입력에서 재현되는 오류라 폐기한다(보존하면 cooldown 만료마다 재과금). timeout·실행 실패는 항상 보존한다. 127/transient/식힘 경로도 로그 1줄을 남긴다(`result: "deferred"`). 로그 키는 `producedBy`(생성)/`engine`(검수)/`verifiedMode`(달성)로 의미가 고정이다. **recall은 `verifiedMode`를 읽지 않는다.** **기존 카드 자동 재검증은 없다**(카드 수만큼 host CLI 호출 = 사용자 계정 청구).
  - **`status: verified`/`contested`는 `verification_stamp.render_verification`이 만든 바이트 한 벌로만 쓴다**(`stamp_verification`은 렌더와 쓰기를 차례로 부르고, intent 경로는 같은 바이트를 `write_rendered_verification`으로 쓴다) — status와 증명 필드 4개(`verifiedBy`/`verifiedAt`/`verifiedMode`/`verifiedBodyHash`)가 한 쓰기로 나가야 status만 바뀌고 증명이 빠진 카드가 생기지 않는다(라이브 27장이 그 형태다: 코드가 쓰지 않는 `verifiedBy: agent-full-source` 수동 백필, 전부 `verifiedAt` 결측 — **소급 수정하지 않는다**. 결측은 거짓이 아니고 지금 채우면 없던 사실을 만든다). 반대로 카드 갱신으로 `generated`로 리셋될 때는 그 키들이 **키째 사라진다** — 값만 비운 `verifiedBy: ""`는 "한 번 검수를 통과한 카드"로 읽히는 잔재이기 때문이다(라이브 5장). **제거하는 주체는 `rewrite_generated_card`의 frontmatter merge다**(`VERIFY_PROOF_FIELDS`에 든 키를 옛 frontmatter에서 건너뛴다). 즉 이 튜플에 키를 더하면 리셋 경로가 자동으로 그 키를 지운다 — 새 필드를 추가할 때 리셋 코드를 따로 고칠 필요가 없고, 반대로 **튜플에 넣지 않으면 취소된 검증의 잔재가 남는다**(새 본문에 옛 지문이 붙어 영구 불일치가 된다).
  - **inconclusive 삭제는 억제 마커가 필수다.** fail("원문과 모순")은 판정이 결정적이지만 inconclusive("verifier가 판정 못함")는 같은 소스에서 재현될 확률이 높아, 마커 없이 삭제하면 소스 재큐잉마다 재컴파일→재삭제가 반복되고 매 반복이 host CLI 호출 = 사용자 계정 과금이다. 삭제 시 카드의 각 소스 `(sourcePath, sourceBodyHash)`(= extractor에 전달된 `maxSourceChars` 절단 본문 해시, `memvane.wiki.verify.api.source_body_hash`)를 `verify-skipped.jsonl`에 기록하고, `wiki_compile_worker.process_job`이 **extractor 스폰 전에** 현재 본문 해시와 비교해 일치하면 skip한다(`candidates.jsonl`에 `verify_inconclusive_suppressed`). 소스 본문이 바뀌면 해시가 달라져 자동 재시도. `dedup-skipped.jsonl`과 동일 패턴이며 같은 이유로 **트림 대상이 아니다**(한 줄 유실 = 삭제 감사 추적 유실 + 과금 루프 재개). 마커 로드 실패는 fail-open(컴파일 진행).
  - 검수기의 기계 삭제는 `generated-manifest.jsonl`에 `verify-deleted` 행을 남긴다. 보이는 카드가 사라졌는데 이 행이 없으면 verifier와 직접 writer가 삭제 감사 기록, 보관한 inode의 전체 SHA-256, 삭제 예정 행, 해당 대상의 manifest 세대를 대조한다. 일치하면 누락된 행을 한 번 기록하고 수정한 원문으로 재생성한다. 구 감사 기록만 있어 삭제 주체를 가릴 수 없으면 보류한다. 이후 생성된 카드의 수기 삭제가 확인되면 tombstone으로 보존한다. `--check`는 복구 결과만 판정한다.
  - **compile intent(DB 출처 기록).** 선택된 설치에서 검수 잡에 compile worker가 읽은 `sourceFingerprints`(view·checkout digest·`scanId`·`observedNs`와 원문마다 worktree·branch·path·sha·크기·HEAD·추적 상태)가 있으면, pass 분기는 `render_verification`으로 최종 바이트를 한 번 만들고(`verifiedAt`은 인자 `now`) `_provenance_gate`가 store `worktrees` 기록으로 checkout을 새로 capture해 view와 (worktree, branch)가 지문과 같을 때만 intent를 `<install state root>/provenance-intents/compile-<id>.json`에 쓴다(fsync, 0700, `id` = kind·view·카드 경로·stamp 후 카드 SHA·`scanId`의 digest). 그다음 같은 바이트를 stamp로 쓰고 pending이면 rename한다. HEAD가 바뀐 것은 막지 않는다(원문 sha는 검수가 다시 대조한다). intent에는 경로·카드 SHA·`expectedTargetHash`·지문·`lines-v1` span·verdict/result digest·`verifiedMode`·검수 엔진·생산 엔진이 들고 원문과 본문은 없다. stamp 실패, stale pending, replay에서 view가 바뀐 경우 그 intent를 `.superseded`로 바꾼다. checkout capture가 실패하면 intent 없이 검수·stamp를 진행하고 `provenance_checkout_unavailable`을, compile과 verify 사이에 branch가 바뀌었으면 `provenance_checkout_changed`를, digest 입력이 틀리면 `provenance_value_invalid`를 `verify-log.jsonl`에 남긴다. intent 쓰기가 실패하면 그 잡은 `provenance_intent_write_failed`로 deferred다. sync가 intent를 소비해 compiled attestation을 기록한다([sync](../../sync/README.md)). 수명 주기는 이 기록을 읽지 않는다.
- `verification_stamp.py` — 검수 결과 status와 증명 필드를 한 번의 원자적 쓰기로 남기는 유일한 writer(`stamp_verification`·`render_verification`·`write_rendered_verification`). 프런트매터 렌더 규칙은 card의 `render_frontmatter_fields`가 소유한다.
- `verify_ledger.py` — 유료 검수 전 원장 쓰기 가능성 preflight(`ledger_writable`)와 억제 마커의 본문 해시(`source_body_hash`). compile worker는 verify api로 같은 해시를 읽는다.
- `wiki_lifecycle.py` — **wiki 수명 주기.** 선택된 candidate route(wiki collection 있음)의 SessionStart·프로젝트 안 편집(`index`)·성공한 agent Bash(`file-change-event`)가 `wiki_lifecycle_request`로 프로젝트당 요청 하나를 sync state 디렉터리(`<key>-wiki-lifecycle-request.json`, 소비 기록은 `-served.json`)에 남기고 그 프로젝트의 `laya-compile` wake를 offer한다(`_request_selected_sync` 안, 실패해도 hook 응답은 그대로). sealed bundle의 compile pass(`memvane.wiki.compile.api.run`)가 대기 요청을 먼저 소비해 이 모듈을 `LIFECYCLE_SECONDS` 제한 자식으로 돌리고, 그 run이 넣은 재생성 행을 같은 pass의 compile worker가 처리한다(넣은 것이 없으면 worker를 건너뛰고 drained). 대기 중인 요청이 있으면 다음 trigger는 쓰지도 깨우지도 않는다(묶음 처리). run 도중 들어온 요청은 실행 중 행의 revision을 올려 후속 pass 하나가 처리한다. 전용 wake kind를 두지 않는 이유: UID wake 큐는 모든 설치 번들의 worker가 공유하고, 표에 없는 kind를 만난 구버전 worker는 `next_row`의 KeyError로 죽은 뒤 자기 rewake로 다시 뜬다. 연결 워크트리 route·bundle 불일치 route·미온보딩 프로젝트는 요청을 남기지 않는다. plugin 소유 카드(`wiki_compile.auto_writable_text`: `createdBy`가 `wiki_markers.CREATED_BY_NAMES`(`memvane`, 이전 플러그인 이름 `qmd-auto-context`) + auto 블록, `superseded` 제외)만 컴파일러 소유 `sourceRevisions`(path·collection·sha256)로 판정한다: 기록된 원문이 없으면 `wiki_source_retire.retire_deleted_source`로 퇴역시키고(옛 바이트를 `.memvane/compile/retired-wiki/`에 보관 → unlink → index 줄 제거 → `laya-sync` wake. memvane-db full scan이 다음 세대에서 없는 wiki 파일을 뺀다), 해시가 바뀌면 `wiki_compile_enqueue.enqueue_changed_sources(session_start=True)`로 재생성을 넣고(legacy settings는 `session_start_source` trigger 동의를 따르고, `settingsModel:"minimal"`은 동의 없이 넣는다 — `regeneration_config`), 같으면 둔다. `sourceRevisions`가 없는 카드는 `sources`를 판정한다: 파일 원문이 모두 있으면 지문을 채우고 카드를 유지하며(schema3 선택 설치는 카드 변경 없이 유지), 모두 없거나 파일 항목이 없으면 퇴역시킨다. session 원문만 있으면 유지하고 파일 원문이 일부만 없거나 판정할 수 없으면 보류한다. 살아 있는 원문이 남은 공유 카드는 바로 지우지 않고 `sourceDelete` 행으로 compile worker에 넘긴다(생존 원문 재생성 뒤 퇴역). 판정 불가(형식이 틀린 provenance, allow-root 밖 원문, 읽기 실패)는 남기고 로그만 쓴다. **git 브랜치 안전**(`git_branch_safety`): 연결 워크트리와 rebase·merge·cherry-pick·revert·bisect 진행 중에는 run 전체를 건너뛰고, 원문 소실은 HEAD 계보의 삭제로 증명될 때만 조치한다. 원문이 HEAD·index에 추적 중이거나 HEAD에 병합되지 않은 로컬 브랜치 끝에 있거나, 카드와 원문이 모두 커밋된 적 없거나, git이 답하지 못하면 `HOLD`로 남긴다. git 저장소 밖 프로젝트는 기존 판정 그대로다. `retire_deleted_source`도 같은 판정을 거쳐 `held_branch`를 돌려주고, compile worker는 그 `sourceDelete` 행을 정리한다. 존재 판정은 `wiki_card.resolve_existing_source` 하나다. **선택된 memvane-db route에서만 조치한다** — 선택된 route가 없으면 `ineligible`만 센다. 유계: 해시 대조는 `compile.sourceScan.maxCardsPerScan` 순환 커서 창, 퇴역은 run당 `MAX_RETIRE_PER_RUN`, enqueue는 compile per-wake 상한이고 상한에 걸리면 커서가 그 카드에 멈춰 다음 run이 이어 간다. 카드 수·바이트 상한은 `wiki_source_retire`와 같은 값이다. **대량 삭제 가드**: 증명된 카드 중 원문 소실 카드가 `MASS_DELETE_MIN`보다 많고 `MASS_DELETE_FRACTION`을 넘으면 그 run은 아무것도 지우거나 넣지 않고 로그만 남긴다(디스크 미마운트·브랜치 전환·checkout 이동). 지문 없음은 카드 자체의 성질이라 비율 계산에서 빠지고 run당 상한을 받으며, 가드가 발동한 run은 그것도 보류한다. 멱등성: 퇴역한 카드는 다음 run에 없고, 보관은 같은 내용을 재사용하며, live 큐 키가 중복 enqueue를 접고, 같은 원문 해시의 재생성은 `REFRESH_RETRY_SECONDS` 안에 다시 넣지 않는다(상태는 `~/.local/state/memvane/v1/auto-context/scan-state/<key>-wiki-lifecycle.json`(`QMD_SYNC_STATE_DIR`). 같은 원문의 신선한 카드가 있어도 이 상태를 지우지 않는다 — 지우면 낡은 형제 카드가 매 run 다시 들어간다). 로그는 `~/.local/state/memvane/v1/auto-context/logs/wiki-lifecycle.log`(`QMD_WIKI_LIFECYCLE_LOG`). `compile.sourceScan.enabled:false`는 조치만 끄고 `ineligible` 집계는 유지한다. PostToolUse와 raw discovery(`wiki_discovery`)는 편집된 원문 자체를 enqueue하고 삭제 원문을 `sourceDelete`로 넣으며, 편집 뒤 lifecycle run은 그 원문을 인용한 다른 카드를 맡는다. `wiki_source_missing.py`는 카드 소스 분류와 wiki root 격리(`wiki_root_of`) helper만 둔다.
