# Wiki compile과 extractor

코드·테스트 주석의 "로드맵 N단계"는 주입 품질 로드맵의 단계 번호다: 1=주입에 카드 본문·경로 포함, 2=sources.path 주입, 3=원문 소실 정책(현재 `wiki_lifecycle`), 4=verify 엔진 분리(crossEngine), 5=crowding_probe 측정 도구, 6=verify 처리량·per-run cap, 7=role source, 8=raw 인덱스 유지 판정과 orphan 벡터 회수, F1=write-time dedup 교차 엔진. 테스트 주석의 "계획 2026-08-19 §N"은 recall 효용 회복 작업의 절 번호다(계획 문서는 따로 없고 남은 항목은 `docs/TODO.md` 「recall 품질」에 있다). §2.1=사라진 worktree를 가리키는 컬렉션 경로, §3.4=죽은 설정 키(sourceScan·sourceMissingPath·maxCardsPerSource) 처리, §3.5=설정 경로와 qmd 레지스트리 경로 대조를 가리킨다.
- `yaml_scalars.py` — frontmatter scalar 인용/역인용(`dump`/`load`) 규칙의 SSOT. **wiki 카드 frontmatter로 나가는 모든 extractor(모델) 제공 값은 `dump`를 거치거나 닫힌 집합으로 검증해야 한다** — raw 방출이면 개행 하나로 top-level 키를 위조할 수 있다(`trigger="promote\nstatus: verified"`로 status 위조 + `parse_frontmatter` fail-close → 그 카드의 verify·dedup 영구 정지). `markdown_page`에서 title/canonicalKey/aliases/sources 값/triggers/redactions는 `dump`, type/confidence/status는 닫힌 집합 검증(unquoted 유지 — `TYPE_DIRS` 조회와 `frontmatter_patch_scalar`의 status 표기 정책이 그 형태를 전제한다), sources의 **키**는 `SAFE_KEY_RE` 화이트리스트다(키도 모델이 준다 — `wiki_compile.SAFE_YAML_KEY_RE`는 이 상수의 별칭이고 정의는 한 곳이다). `wiki_compile.yaml_scalar`·`unquote_yaml`과 `wiki_card.parse_frontmatter_scalars`가 **같은 규칙**을 쓰게 한다 — 갈려 있던 동안 title 오염이 8/731장 발생했다. block scalar 헤더(`>`/`|`)를 값으로 오인하지 않는다. **인용부호는 스칼라 선두에서만 인용을 시작한다**(값 중간의 `"`/`'`는 plain scalar의 일부, single-quoted 안 `''`는 리터럴, plain scalar는 `:`를 담을 수 있어 구분자는 `: `·`,`·`}`가 뒤따르는 `:`뿐이다 — `_is_separator_colon`이 SSOT). 어디서든 인용을 열던 동안 `{path: a"b, kind: c}`의 `,`를 값으로 삼켜 `kind`를 잃었고, 결과는 fail-closed였지만 사유가 `kind_not_file`/`missing`으로 **오표기**됐다(PyYAML 차분 퍼즈 11,243건 중 242건 불일치가 전부 이 원인). 중복 키는 **first-wins**로 PyYAML(last-wins)과 의도적으로 다르다(뒤에 끼워 넣은 키가 앞을 덮지 못하게 — frontmatter 규약과 동일). **flow mapping(`- {kind: "raw", path: "…"}`)의 emit/parse 쌍도 여기 있다**(`dump_flow_mapping` ↔ `load_flow_mapping`, 쓰기 `wiki_compile.markdown_page` ↔ 읽기 `wiki_card.frontmatter_source_entries`) — 같은 이유로 갈리면 조용히 깨진다. 값 분리는 인용부호 밖의 `,`만 보는 스캐너다(`,`를 담은 경로가 반으로 잘리면 다른 파일을 가리킨다). 왕복은 테스트로 못박고 PyYAML 대조는 **테스트에서만** 한다.
- `wiki_markers.py` — wiki 카드 `qmd:auto` 마커 리터럴의 SSOT. **쓰는 쪽(`wiki_compile`)과 읽는 쪽(`recall`)이 같은 문자열을 쓰게** 한다(각자 정규식을 들면 형식이 바뀔 때 읽는 쪽만 조용히 깨져 주입 본문이 빈다). 엄격도는 의도적으로 다르다 — 쓰기는 sourceHash까지 정확 매칭(잘못된 블록 덮어쓰기 방지), 읽기는 접두만 보는 선형 스캔(fail-open).
- `wiki_compile_defaults.py` — compile 설정 블록 생성 헬퍼(제품 코드 호출부는 없고 테스트가 쓴다). generated config에는 절대 adapter 경로를 쓰지 않고 `compile.extractor.builtins`에 `claude`/`codex`/`hermes` 같은 symbolic engine만 저장한다.
- `wiki_compile_enqueue.py` / `wiki_compile_worker.py` — 자동 compile source는 `raw`/`session`/`source` Markdown만 허용하며(role `source`는 qmd에 등록되지 않는 compile 전용 입력이다 — `config.COMPILE_SOURCE_ROLES`가 SSOT이고 enqueue·worker 양쪽이 같은 판정을 쓴다), dot segment는 skip/reject한다(`.agents/skills`, `.claude`, `.codex`, `.github` 같은 agent/tooling metadata를 wiki로 승격하지 않기 위한 안전장치). **단 dot 검사 범위는 "명시적으로 등록된 collectionPath 루트 아래"로 한정한다** — 루트 자체의 dot segment(novel의 `.nova/06_Sessions`)는 사용자가 `collectionPaths`에 직접 적은 소스라 면제하고, 그 아래에서 새로 나타나는 dot segment(`.drafts/`, `.hidden.md`)는 그대로 배제한다. 이 좁히기가 완화 범위를 자동으로 봉쇄한다: `collectionPaths`가 `.`(저장소 전체)이면 면제 접두부가 비어 rel path 전체가 여전히 dot 검사를 받으므로 dot 디렉터리가 하나도 열리지 않는다. 여기에 더해 `.memvane`·`.auto-context`·`.git`·`node_modules` segment는 role 게이트와 무관하게 항상 deny다(`DENIED_SOURCE_SEGMENTS`) — wiki 카드/compile 큐가 자기 자신의 소스가 되면 무한 증식한다. **worker의 per-run 상한은 `compile.batch.maxPerRun`(기본 10)이고 `batch.maxItems`(기본 5)와 다른 것이다** — maxItems는 "이만큼 모이면 지금 시작"(시작 조건)이고 maxPerRun이 없으면 큐에 든 **전량**을 한 프로세스가 순차 실행한다(큐 1,000건 = 유료 CLI 1,000회 직렬). 초과분은 requeue되어 다음 kick이 집으므로 조용히 유실되지 않는다(sync의 `QMD_SYNC_COMPILE_MAX`와 같은 성질). `--json`의 `deferred`가 미룬 개수다. **이 값이 보장하는 것은 extractor 호출 수뿐이다** — 한 run의 유료 호출은 extractor(≤ maxPerRun) + dedup judge(≤ 쓰인 카드 수) + verify(예산)이고, 그래서 **`candidates` 순회에도 상한이 필요하다**(`compile.maxCardsPerSource` 기본 10): 길이는 모델 출력이라 슬라이스가 없으면 큐 5건에 모델이 카드 40장을 낼 때 한 run 유료 호출이 205회가 된다(모델이 과금 규모를 정하는 구조). 초과분은 `skipped`/`cards_per_source_cap` 레코드로 남기되 **잡을 requeue하지 않는다** — 재처리는 extractor 재호출이고 그것은 같은 소스에 대한 이중 과금이다(올바른 해법은 소스 분할). 유료 호출 수를 정하는 값은 전부 config 상수로 클램프한다(`MAX_COMPILE_PER_RUN`·`MAX_CARDS_PER_SOURCE`·`MAX_VERIFY_PER_RUN`) — `"100"`·`99999999`가 그대로 통과하던 자리다. **단 어떤 클램프도 두 값의 곱을 막지 않는다**: 한 run의 카드 수는 `batch.maxPerRun × maxCardsPerSource`이고 judge는 카드당 1회이므로 기본값(10×10)에서 최악 140회, 상한까지 올리면 2,581회가 가능하다. 곱에 상한을 두지 않는 이유는 **두 값을 함께 올리는 것이 사용자의 명시적 선택**이고 `docs/settings.md`에 그 셈이 경고로 적혀 있어서다(예상 밖의 비용이 아니다). 총량 상한을 새로 두면 "설정대로 동작하지 않는다"는 다른 종류의 놀라움이 생기고, "모델 출력에서 유도된 값만 코드가 자른다"는 원칙과도 어긋난다. **고아 `*.claimed.*` 회수는 `claim_queue` 안에서 같은 flock 아래 일어난다.** selected durable wake(`wiki_selected_laya._compile_idle`)도 drained를 판정하기 전에 compile run lock을 잡고(잡혀 있으면 worker 실행 중이라 idle 아님) source·verify 큐마다 그 큐 lock 아래에서 고아 claim 회수, 남은 claim, 큐 내용을 함께 판정한다. 생존 판정은 파일명에 박힌 claimer pid다. `os.replace`는 mtime을 보존하므로 claim 직후 `os.utime`으로 claim 시각을 찍는다. pid 검사가 1차, mtime backstop 이 pid 재사용 대비 2차다. 예외 시 claimed 파일을 지우지 않는다 — 남기는 것이 복구 경로다(리퍼가 회수한다). `requeue_lines`가 ENOSPC로 실패한 뒤 지우면 잡이 영구 유실된다. 회수는 at-least-once이고 중복은 `MAX_REQUEUE_COUNT`로 유계다. 초과분은 폐기 + 원장 + SessionStart 알림이 종점이다.
- **`memvane/wiki/compile/wiki_extract.py`의 수동 경로에는 `maxCardsPerSource`가 걸리지 않는다**(candidates 슬라이스 없음, 카드당 judge 1회). 사용자가 `wiki-compile` skill로 직접 요청하는 경로라 자동 경로와 같은 상한을 강제하지 않았다 — 자동 훅이 사용자 모르게 쓰는 것과 사용자가 명시적으로 요청한 것은 다르다. 대량 candidate JSON을 넣으면 호출 수가 그만큼 난다는 것만 알아 두면 된다.
- **카드는 frontmatter `sourceRevisions`를 계속 쓴다.** 선택된 설치에서는 검수를 통과한 카드의 같은 원문 지문을 sync가 compiled attestation으로 index에도 기록한다(compile intent, [verify](../verify/README.md)). 소비 조건이 frontmatter `sourceRevisions`·`sourceSpans`와 intent의 일치라서 두 기록은 같은 내용이다. recall의 member trust와 수명 주기 판정은 frontmatter 기록에서 온다.
- **`sourceRevisions`는 두 경로 모두 컴파일러가 소유한다 — caller/모델 값은 채택되지 않는다.** 자동 경로는 `wiki_compile_worker`가 `snapshot_bytes` **단일 읽기**로 잡은 파일 스냅샷을 candidate 에 **대입**하고(`setdefault` 금지 — `engine`/`trigger`·`authoritativeSources`와 같은 규칙), 수동 경로는 `wiki_extract.attach_compiler_provenance`가 compile 직전에 같은 일을 한다. 이 필드가 비면 그 카드는 `wiki_card.is_auto_trusted_card`(status + createdBy + **비어 있지 않은** `sourceRevisions`)를 영구히 통과하지 못해 **검수를 받아도 recall 에 나오지 않는다** — 즉 모델이 값을 안 주거나 형식을 틀리는 것만으로 카드가 조용히 무용해진다(라이브 census: service-engineering 2026-08 카드 중 128장이 provenance 없음, 08-11 이후 결측 0). **해시는 절단 여부와 무관하게 파일 전체다**(extractor 에는 `maxSourceChars` 로 자른 본문을 주지만 수명 주기가 호출하는 `wiki_freshness.compare_revision`도 전체 파일로 대조한다 — 절단을 해시에 섞으면 편집 없이 영구 stale 이 된다). 수동 경로에서 caller 가 정하는 것은 **어느 파일인가**뿐이고(큐가 없어 불가피하다) 스냅샷은 컴파일러가 직접 읽어 만든다. **전부 아니면 전무**다 — 파일 소스 하나라도 스냅샷 못 하면(미존재·root 밖·`MAX_PROVENANCE_FILE_SOURCES` 초과) 아무것도 내지 않는다(부분 목록이 완결된 근거처럼 보이면 안 된다. `dump_source_revisions`의 형제 기각과 같은 규칙). `authoritativeSources`와 `sourceRevisions`는 **같은 읽기**에서 함께 나온다 — 소스 집합을 두 벌로 만들면 "검증은 A 를 보는데 provenance 는 B 를 가리킨다"가 된다. 수동 경로의 파일 소스 상한은 `wiki_verify_worker.MAX_SOURCES`와 같아야 한다(권위 항목은 verifier 에서 잘리지 않으므로 여기서 내는 목록 길이가 곧 유료 검수의 읽기 폭이다). **그 상한은 중복 제거 뒤 서로 다른 파일 수에 걸린다 — 항목 수에 먼저 걸면 안 된다.** 판정은 `(st_dev, st_ino)` 동치이고 그것은 `os.path.samestat`(= `os.path.samefile`)이 보는 값과 같다. 문자열 정규화로 흉내내지 말 것 — 대소문자 무시 여부는 마운트마다 다르고 한글은 NFC↔NFD 로 갈리며 하드링크는 어느 정규화로도 같아지지 않는다. rel 문자열로 판정하면 같은 파일의 별칭 2개가 같은 파일을 두 번 세어 검수 읽기 폭을 헛되게 쓰고, 별칭 4개는 상한에 먼저 걸려 provenance 가 통째로 사라진다(= 그 카드는 영구히 recall 에 나오지 않는다). 겹치면 먼저 나온 rel 이 남고(frontmatter 중복 키의 first-wins 와 같은 규약), 조사할 **항목** 수는 별도로 `MAX_PROVENANCE_SOURCE_SCAN`(상한의 2배)으로 유계다 — 중복 제거는 항목을 다 열어 본 뒤에야 확정되므로 상한을 항목 수에 걸 수 없고, 무한히 조사하면 caller 목록 길이가 곧 syscall 수가 된다(`wiki_card.collect_source_paths`의 조사 예산과 같은 규칙). 창을 넘기면 기존 ">상한" 과 같이 전무다. **기존 카드 소급 백필은 하지 않는다** — 대부분 건전하게 증명할 수 없다.
- **`post_session_summary` 트리거는 자동 발화 경로가 없다(설계상 불가, 죽은 설정 아님).** 이 트리거는 host가 *compact session summary*를 hook에 넘겨줄 때 발화하도록 의도됐지만 그런 host가 없다 — Claude Code의 SessionEnd/PreCompact/Stop은 `transcript_path`(raw JSONL)만 주고, Codex hooks·Hermes plugin hooks에는 session-end 채널 자체가 없다. raw transcript를 소스로 삼는 것은 금지돼 있고(`raw`/`session`/`source` Markdown만), enqueue는 LLM을 호출하지 않으므로 hook-side 요약도 불가하다. 대신 이 값은 **수동 경로의 레코드 라벨**로 실제 소비된다(`wiki_extract.py`가 payload `trigger`를 그대로 기록 → `skills/wiki-compile`). 따라서 `COMPILE_TRIGGERS`에서 제거하지 말 것. 세션 결론의 **자동** 수집은 `post_tool_source`가 담당한다 — 세션 노트를 `raw`/`session`/`source` collection의 `.md`로 쓰면 편집 훅이 큐잉한다.
- - **`targetPath`는 모델 출력이고 `resolve_target`이 identity 조회보다 그것을 우선한다** — 그래서 무관한 후보가 남의 카드 경로를 지정할 수 있다. 그 경로에 카드가 이미 있으면 `explicit_target_agrees`로 identity(canonicalKey·alias·title) 또는 `sources[].path` 공유를 확인하고, 하나도 겹치지 않으면 `updated`가 아니라 `merge-needed`로 보낸다. `merge-needed.jsonl`은 passive, non-trusted collision diagnostic이며 자동 merge·trust 승격·SessionStart resolver 입력이 아니다. 덮어쓰면 두 갈래로 갈리고 둘 다 나쁘다: verify가 `inconclusive`면 카드가 삭제되고 `auto:end` 밖 보존 섹션이 **영구 소실**되며(원장에 본문이 없다), `pass`면 본문은 새 소스인데 `sources:`·`title`이 옛 카드로 남아 provenance가 조용히 틀리고 2단계 `↳` 경로가 엉뚱한 파일을 가리킨다. 동일 문서 재추출(같은 canonicalKey/소스)은 그대로 `updated`다 — 갱신 경로가 존재하는 이유다. `source_paths_of`는 dict(candidate)와 raw flow 문자열(카드 frontmatter) **두 표기를 모두** 받아야 한다(한쪽만 보면 카드 쪽이 늘 빈 집합이라 판정이 조용히 죽는다).
- **`updated` 경로의 status 리셋(`patch_frontmatter_fields`) 반환값을 확인한다** — 실패하면 본문은 새 내용인데 status가 `verified`로 남아 정확히 그 코드가 막으려던 stale 검증이 되고, verify enqueue는 `status == "generated"`만 보므로 재검증도 일어나지 않는다. 실패 시 `statusResetFailed`를 남기고 **status와 무관하게 verify 큐에 넣어** 다음 run이 다시 대조하게 한다.

`wiki_compile.py`의 secret 방어는 **`secret_matches()`/`has_secret_like()`/`redact()`를 거친다**(`SECRET_PATTERNS`를 직접 `search`하지 말 것). `sk-…` 리터럴 패턴은 그대로이고, `(api_key|secret|token)\s*[:=]\s*\S+` 키워드 패턴만 값이 `_NON_SECRET_VALUE_RE`(플레이스홀더 `<…>`/`{{…}}`, env 참조 `$FOO`/`${FOO}`, `[REDACTED]`, `***`/`...`, 타입명 `string`/`bool`, `true`/`false`/`null`)에 해당할 때 무시한다. 축자 보존 강화로 기술 카드가 설정 키를 **이름만** 인용해도 `secret_like` reject되던 오탐만 제거한 것이며 불투명한 값은 여전히 전부 걸린다. 프롬프트에도 "secrets 규칙이 VERBATIM RULES보다 우선"을 명시해 두 층이 같은 방향을 가리킨다.
- 프로젝트 wiki에는 카드만 있다. 카드 작성 규칙은 번들의 `memvane/wiki/card/rules/default.md`·`novel.md`가 단일 원천이다(compile 워커가 extractor payload `wiki.schema`로 넘긴다. 프로젝트 루트에 `^\d+_Manuscript$` 디렉터리(`04_Manuscript/` 등)가 있으면 `novel`이고, 보조 신호로 wiki의 `characters`·`world`·`timeline`·`plot`·`style` 디렉터리나 `-manuscript`/`-plot` legacy collection도 `novel`로 본다. 판정은 루트 항목 읽기뿐이고 settings 키는 없다). 새로 쓰거나 고쳐 쓰는 카드는 로컬 selector 예산(본문 700토큰, `memvane/learning/wiki_card_budget.py`가 selector의 `derive` 경로로 잰다)을 목표로 한다. 넘으면 compile 워커가 분할을 한 번 요청하고, 그래도 넘는 카드는 쓰고 `wiki.card over_budget_written`으로 남긴다(selector는 앞부분으로 채점한다). 기존 긴 카드를 소급해 나누지는 않는다(일반 갱신은 같은 규칙, 검증 stamp·퇴역은 그대로 적용된다). 카드 목록은 memvane-db 색인이고, 카드 생성·갱신·삭제·은퇴 기록은 `memvane/wiki/workspace/wiki_activity_log.py`가 설치 이벤트 로그 `<state root>/events.jsonl`(`memvane/diagnostics/event_log.py`, 4 MiB 넘으면 `.1`·`.2`로 회전)에 `wiki` 이벤트로 남긴다. state root는 `/`부터 구성요소마다 `O_NOFOLLOW`로 열어 심볼릭 링크·남의 소유·쓰기 가능 상위 디렉터리를 거부하고, 실패해도 카드 쓰기는 막지 않는다. 선택 route가 없는 프로젝트는 state root가 없으니 기록하지 않는다(사용자별 디렉터리에도 쓰지 않는다). 카드 identity·explicit `targetPath`도 wiki root 메타 페이지를 대상으로 삼지 않는다. 워커는 최근 `wiki` 이벤트만 `- <ts> <action> <path> - <title>` 줄로 렌더해 `wiki.logTail`로 넘긴다(recall 등 다른 이벤트는 프롬프트에 들어가지 않는다). 플러그인은 wiki root의 `SCHEMA.md`·`index.md`·`log.md`를 만들지도 읽지도 않는다. 이전 릴리스가 남긴 파일은 지우지 않고, `source_text.is_wiki_meta_page`(wiki root 바로 아래 파일만, 하위 디렉터리의 같은 이름은 일반 카드)로 recall·compile grounding·수명 주기·dedup·퇴역·compile 증명에서 거른다. 색인 단계는 생성 헤더가 있는 root `log.md`만 빼고 나머지는 그대로 색인하므로 기존 설치의 generation digest는 바뀌지 않는다.
- `extractors/` — host-CLI wiki extractor adapters (`claude_adapter.py`, `codex_adapter.py`, `hermes_adapter.py`) + `lib.py`. Pure `payload→{candidates}` functions run in an isolated temp cwd with tools/custom context disabled. Worker는 `compile.extractor.argv`(legacy explicit) → `compile.extractor.backends[engine]`(explicit) → `compile.extractor.builtins`(runtime-resolved adapter) → `extractor.default` 순서로 선택한다. minimal settings는 host builtin auto-wiki compile을 켠 모양으로 펼쳐진다(`config.expand_minimal_settings`). Exit 127 = host CLI absent (worker then tries `extractor.default`). 격리: `lib.run_isolated`가 자식 env에 `QMD_SANDBOX=1`을 넣어 nested CLI의 qmd 훅을 즉시 무력화(재귀 차단)하고, claude는 `--safe-mode`·`--tools ""`·`--no-session-persistence`, codex는 `--ephemeral`·`--ignore-user-config`·`--ignore-rules`, hermes는 `--safe-mode`·`--ignore-user-config`·`--ignore-rules`·`-t ""`로 MCP/skills/plugins/rules/tool context를 최소화한다(hermes는 동등 persistence-off 플래그 없어 ~/.hermes에 1회성 기록이 남을 수 있음).
  - **`lib._PROMPT_TEMPLATE`의 VERBATIM RULES는 lex 검색 기반이다.** 카드 본문은 "이 토큰이 문서에 있는가"의 대상이라 토큰이 많을수록 매칭 기회가 늘어난다 — 쿼리 쪽(term이 늘면 AND가 좁아져 0건 위험)과 정반대로 축자 보존은 순수 이득이다. 백틱 코드스팬·**전체 경로**(basename으로 줄이지 말 것: FTS5가 `/`·`.`을 분해하므로 쿼리의 basename stem과 어차피 매칭된다)·시그니처·설정 키·단위 붙은 수치·에러/exit code·대괄호 태그를 축자 유지시킨다. "compact"/"short" 지시는 제거했고 대신 payload `maxLines`(worker가 `compile.maxAutoPageLines`를 그대로 전달)로 lint `too_many_lines`와 상한을 일치시킨다. 코퍼스별 프롬프트 분기는 하지 않는다 — 규칙이 조건부("source가 X를 포함하면")라 코드스팬 없는 서사 소스는 트리거되지 않고, 인명·EP 태그·인용 대사가 같은 목록에 있어 novel에는 additive다. 대신 "NOT a scene-by-scene retelling"으로 재화 방지를 명시한다.
  - **`suggestedType`의 SSOT는 `lib.TYPE_GUIDE`(정의 dict)이고 `ALLOWED_TYPES = tuple(TYPE_GUIDE)`다.** 프롬프트가 타입 이름만 나열하고 정의를 주지 않으면 모델이 가장 무난한 두 개(concept·decision)로 수렴한다. 같은 소스(`docs/resource.md` = AWS 리소스 인벤토리)가 이름만 주면 `concept`, 정의를 붙이면 `entity` ×2(confidence high)로 분류된다. 목록과 정의를 **한 dict에서 유도**하는 이유는 따로 두면 타입 추가 시 한쪽만 고쳐져 "정의 없는 선택지"가 재발하기 때문이다. **이 집합을 넓히는 것은 `memvane/wiki/compile/wiki_init.py`의 `base_dirs`를 넓히는 것과 같은 변경이다** — scaffold는 이 집합을 `wiki_compile.TYPE_DIRS`로 매핑한 값이어야 한다. `session`/`query`를 이 집합에 넣지 말 것: extractor 입력은 **문서 파일 하나**라 세션 기록을 만들 수 없고(그건 수동 `wiki-compile` 경로다) `query`는 어디에도 정의가 없다. 반대로 `wiki_compile.ALLOWED_TYPES`/`TYPE_DIRS`의 session·query 항목은 **그대로 둔다** — scaffold에서 뺀 것은 **미리 만드는 것**이지 타입 지원이 아니고, 카드를 쓸 때 `target.parent.mkdir(parents=True)`가 디렉터리를 만든다(실측: 수동 `suggestedType:"session"` → `sessions/`가 그 자리에서 생성). 빈 디렉터리를 미리 만들지 않는 이유는 미관이 아니라 **"여기에 뭔가 쌓여야 하는데 안 쌓인다"는 오진**을 막기 위해서다.
  - **`compile.maxSourceChars`는 12,000자 유지.** 상한을 올리면 extractor+verifier 두 번의 host CLI 호출이 모두 커져 편집당 토큰 비용(사용자 계정 청구)이 선형 증가한다. 대신 절단 사실을 payload `source.truncated`로 전달해 프롬프트가 "보이는 범위만 요약, 부재를 단정하지 말라"로 동작하게 한다(verify는 이전부터 truncated 소스를 `inconclusive`로 처리). 문서 후반부 커버리지는 bulk 재컴파일(P6)이나 소스 분할로 해결할 문제다.
