# Sync 게시

`sync.profile` 이벤트는 선택된 schema3 sync의 scan·plan·coverage·provider·storage·publish별 누적 밀리초와 호출 수를 한 줄에 기록한다. 본문과 경로는 기록하지 않는다. scan은 위키 목록·카드 읽기·원문 관측, plan은 fill 계획 생성(상태·fill 내부 호출 포함), coverage는 대상의 embedding set 확인, provider는 embedding 호출, storage는 `fill_view`, publish는 세대 준비·게시를 잰다. storage 시간에는 그 안의 provider 호출과 내부 계획 확인이 포함되므로 단계 시간은 합산하지 않는다. 이벤트의 `ms`는 schema3 실행 전체이며 후속 discovery는 포함하지 않는다.

- schema3 sync 게시(`product_sync_worker._run_schema3`) — `laya-sync` pass는 선택된 view store에 게시한다. sync owner와 worker writer scope 아래 main view를 먼저, 그다음 연결 워크트리 view를 게시한다. 연결 워크트리 view의 collection root는 그 워크트리의 프로젝트 폴더를 가리킨다. store가 그 view의 decision을 거절하면(`attestation_decision_mismatch`) 그 view만 held로 남고 pass와 main 게시·reader 재봉인은 이어진다. 바뀐 카드와 원문 관측에 따라 신뢰 상태가 달라진 카드를 `ingest_attested_card`로 넣는다(pass당 64장·45초). 완료된 raw 관측과 카드의 `sourceRevisions`를 비교해 현재 바이트와 맞는 revision을 attestation에 남기고, 관측된 원문에 맞는 revision이 없으면 카드를 untrusted로 넣는다. 관측 상한을 초과하거나 원문이 관측 밖이면 그 원문을 판정하지 않으며, 재생성은 `wiki_lifecycle`이 맡는다. 다른 worktree·branch view의 trust는 빌리지 않는다. 게시 head가 없는 cold view는 완료 전까지 게시하지 않는다. 모든 view 게시 성공 뒤 같은 sync owner와 writer scope 안에서 게시한 view의 오래된 행을 유계 batch로 정리한다. 바쁜 reader나 기한 때문에 미완료된 정리는 다음 게시에서 다시 시도한다. view binding은 settings 정체성과 wiki root dev/ino이고, `skipPaths`는 binding 밖이라 pass마다 현재 settings에서 읽는다. 삭제된 카드는 디스크 상태에 따라 색인에서 제거하며 카드 파일은 건드리지 않는다. manifest의 `sources`는 같은 pass의 유계 raw 관측(4,096 파일·64 MB, 넘으면 빈 목록)이고 wiki discovery가 그 관측을 재사용한다. vector spec으로 봉인된 head는 바뀐 적격 카드의 content를 먼저 fill하고 완료되면 vector 세대 하나를 게시한다. 예산·provider 사유로 fill을 마치지 못하면 lexical 세대를 게시하고 다음 pass에서 cursor로 재개한다. 초기 lexical-ready 경로는 그대로다. pass의 첫 cold target(chunk set 없음)은 chunk set이 있는 target처럼 resume 예산(`SCHEMA3_RESUME_SECONDS`)을 한 번 받고, 앞 작업이 pass 예산을 다 써도 그 target은 시도한다. main view에 ingest할 카드·원문 변경이 없는 pass는 vector fill과 그 뒤 vector 세대 게시에 240초 창(`SCHEMA3_VECTOR_SECONDS`, publish reserve 포함)을 쓰고, 창 안에서 자기 deadline에 걸린 fill 호출이 embedding set을 남겼으면 다음 호출로 이어 간다(아무것도 남기지 못한 호출은 pass를 끝낸다). 카드를 ingest한 pass와 연결 view는 pass 예산 그대로다. 첫 미완 target 앞 cache hit 구간이 `MAX_FILES`를 넘으면 한 호출로 넘기고, provider 호출마다 그 앞에서 owner를 기다리는 다른 프로젝트의 초기 빌드(`_initial_build_waiting`)에 양보하고(`laya_sync_yield_priority`), main view vector가 그 pass에 embedding set을 늘리고 끝나지 않으면(이 양보·provider 실패로 멈춘 경우 포함) 결과를 ACK하고 같은 `laya-sync` wake를 30초 뒤로 다시 offer한다(진척이 없으면 pending으로 남아 backoff하고, 연속 144회면 wake 정책의 `retry_cap`으로 지워져 다음 편집·SessionStart wake를 기다린다). main view가 게시된 pass(`indexed`·`unchanged`)는 연결 view가 무엇을 기다리든 성공이고, 실패 횟수는 main view가 게시되지 않았거나 main view vector가 진척 없이 남은 pass에만 쌓인다. 현재 세대가 없는 연결 view는 결과의 `linkedWaiting`(`waiting`: view나 그 vector가 `pending`·`deferred`, `held`: checkout이 바뀔 때까지 멈춘 view, `reasons`: 사유별 수)에 담기고 게시된 pass의 `wake.sync` 이벤트의 `linked` 필드로 남는다(main vector가 진척 없이 남아 실패로 끝난 pass의 이벤트에는 싣지 않는다). 대기 중인 연결 view가 이 pass에서 닿지 못한 것(`schema3_pass_budget`)이거나 처음 관측됐거나 남은 수(ingest할 카드, 채울 vector target)가 앞 pass보다 줄었으면 같은 30초 재offer를 받는다(`linked_reoffer.decide`). main이나 다른 view의 움직임, 남은 양을 줄이지 못한 작업은 재offer 사유가 아니고, 그런 pass는 재offer 없이 끝나 다음 sync 요청(SessionStart, 편집, 수동 update)이 연결 view에 다시 닿는다. 어느 view의 남은 수도, 대기 view 수도 최저치를 갱신하지 못한 재offer가 연속 20회를 넘으면 그 pass는 `pending`·`schema3_linked_pending`으로 끝나 wake 정책의 backoff와 retry cap을 따른다. 판정에 쓰는 앞 pass의 값은 install state root의 `linked-reoffer.json`(지금 대기 중인 view의 남은 수, view별 최저치와 대기 view 수의 최저치, 연속 수, 무엇이 움직였든 이어진 재offer 수: 200회를 넘으면 한 pass를 실패로 세고 다시 센다)에 둔다. 이 파일은 1.x 영속 계약 밖의 캐시다: 대기가 없는 pass가 지우고, 없거나 깨졌으면 이력 없음으로 읽고 원자적으로 바꿔 쓰며, 쓸 수 없으면 재offer하지 않는다. 그런 pass도 외부 편집 drain과 wiki discovery를 돈다. 마지막 fill 호출이 pass deadline을 넘기면 그 pass의 세대 게시는 새 publish reserve를 받는다. `wake.sync` detail은 main view vector 상태(`vec_<state>_<사유>`·`rem`·`ord`·`pms`·`pub`·`res_`)를 담는다. main view의 첫 vector 세대 뒤 owner가 `resettle_selection`으로 endpoint에 vector spec을 봉인해야 recall이 query vector를 요청한다. provider가 token window로 다시 쪼갠 카드는 view recipe가 그 chunk 위치를 재현할 수 없어 recipe의 fallback 창(`store.types.FALLBACK_CHARS`, 600/90/135 UTF-16 단위)으로 chunk set을 만들고 창마다 따로 embed한다(`_schema3_chunker`). 그 카드의 vector도 같은 vector 세대에 게시된다. provider 정체성을 증명할 수 없으면 wake가 `blocked`(`provider_blocked`)로 끝나고 일시적 거절은 `deferred`다. 같은 설치의 외부 편집 drain·wiki discovery·dedup retrieval·학습 corpus는 view head를 읽고, retroactive dedup scan은 view vector가 없으면 고정 사유로 건너뛴다.
- 선택 sync와 초기 빌드는 사용자당 하나인 sync owner 잠금을 함께 쓴다. 대기 중인 초기 빌드가 있으면 선택 sync가 양보한다.
- 선택 sync가 `indexed`·`unchanged`로 게시를 끝내면 같은 owner 아래 학습 유지보수 요청을 확인한다. 요청 하한·실패 backoff가 지난 설치만 worker를 시작하며 학습 요청 실패는 sync 게시 결과를 바꾸지 않는다.
- 초기 빌드는 완전한 lexical head를 게시하면 ready다. 선택 후 sync wake가 벡터를 채우며, 첫 벡터 세대 전에는 lexical recall을 제공한다.
- `sync.api.run(project, *, coordinator=None, report=None, start_service=None)`은 embed 서비스 시작 함수를 받는다. 없으면 설치된 warm 서비스를 쓰고, 시험 runtime root에 fixture port가 있으면 그 port의 서비스를 쓴다.
- compile intent 소비(`compile_intents.consume`) — verify worker가 검증을 통과한 카드마다 `<install state root>/provenance-intents/compile-<id>.json`(0700 디렉터리, canonical JSON, 이름 = 내용의 id)을 남긴다. view pass는 카드 ingest 뒤 `prepare_generation` 전에, 그리고 바뀐 것이 없는 pass에서도 그 view의 intent를 소비한다. intent 지문의 (worktree, branch)가 이 view와 같고, 그 경로의 이번 pass member와 디스크 바이트가 intent 카드 SHA와 같고, 카드 frontmatter의 `sourceRevisions` (path, sha256, size) 집합과 `sourceSpans`가 intent와 같으면 observed 지문·`lines-v1` span·`memvane-card-evidence-v2` receipt를 compiled attestation으로 `card_attestations`·`attestation_sources`에 쓴다. member trust는 바꾸지 않는다. 결과는 rename(`.consumed`·`.rejected`·`.superseded`)이고 rename 직전에 읽은 fd와 경로의 정체성을 대조한다. 카드가 아직 그 바이트가 아니면 waiting으로 남긴다. 거절 사유는 `provenance_parity_mismatch`(frontmatter와 불일치), `provenance_conflict`(같은 id에 다른 지문·attestation), `provenance_value_invalid`(손상·이름 불일치·값 검증 실패)다. 같은 view·경로에서 더 나중이거나 같은 관측의 intent가 consumed되면 그보다 앞서 기다리던 다른 카드 SHA의 intent는 superseded가 된다. 이번 pass member나 디스크의 현재 카드 바이트와 SHA가 같은 intent는 ingest가 늦어져도 남긴다. pass마다 view당 파일 512개를 열고 store 쓰기는 64건까지 시도하며, view별 위치를 `provenance-intents.cursor`에 남겨 다음 pass가 이어 간다. 첫 store 쓰기 앞에서 journal fence를 한 번 세우고, 소비할 intent가 없으면 store·journal을 쓰지 않는다. fence·writer 증명 실패와 store의 binding·일시 사유는 intent를 거절하지 않고 pass를 끝낸다. pass 결과의 `provenance`는 `{consumed, rejected: {사유: 개수}, waiting, superseded}`(연결 view는 `worktrees` 항목마다)이고, 게시를 끝낸 pass에서 consumed·rejected·superseded가 하나라도 있으면 그 합계가 `wake.sync` 이벤트의 `provenance`로 남는다(`app/runtime_dispatch._provenance`). intent 파일은 지우지 않는다. 아직 settle되지 않은 링크(nlink 2)나 열 수 없는 intent 파일은 건드리지 않고 (이름, inode)마다 한 번만 `unsafe`로 센다(view의 cursor 항목이 그 이름이 남아 있는 동안 기억한다).
- vector arena 관리(`vector_cache.py`) — sync pass는 store 옆 `vector-cache/`의 arena(`memvane/vectorcache`)를 store의 살아 있는 embedding set(어느 view의 head 또는 직전 세대의 적격 카드)과 맞춘다. pass 시작에 자가 대조·compaction·catch-up(pass당 4,096 vector·2초)을 하고, 세대를 게시하기 직전에 그 세대 member의 set을 append한다. 결과는 `vector.cache` 이벤트(`rebuild`·`compact`·`repair`·`catchup`·`append`·`skipped`·`failed`, 필드 `rows`·`sets`·`remaining`·`deadRows`·`bytes`)로 남기고 아무 일도 없던 pass는 남기지 않는다. 그 pass가 한 행 이상 append했고(catch-up 또는 게시 전 append) 남은 set이 있고 main view가 대기 중이 아닐 때만 같은 wake를 30초 뒤 다시 건다. 이벤트의 `ms`는 arena 작업(대조·compaction·append)에 든 시간이다. 진행하지 못하는 arena(`skipped`)는 다시 걸지 않는다. arena 쪽의 어떤 실패도 pass를 실패시키지 않는다.
