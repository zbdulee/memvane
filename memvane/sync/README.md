# Sync 게시

- schema3 sync 게시(`product_sync_worker._run_schema3`) — `laya-sync` pass는 선택된 view store에 게시한다. sync owner와 worker writer scope 아래 main view를 먼저, 그다음 연결 워크트리 view를 게시한다. 연결 워크트리 view의 collection root는 그 워크트리의 프로젝트 폴더를 가리킨다. store가 그 view의 decision을 거절하면(`attestation_decision_mismatch`) 그 view만 held로 남고 pass와 main 게시·reader 재봉인은 이어진다. 바뀐 카드만 `ingest_attested_card`로 넣고(pass당 64장·45초) 같은 바이트의 member는 trust를 유지하며, 카드의 `sourceRevisions`가 한 원문 경로를 서로 다른 (sha256, 크기)로 두 번 이상 인용하면 같은 pass의 raw 관측이 완료된 경우에만 현재 바이트와 맞는 revision 하나를 attestation에 남기고 맞는 것이 없으면 카드를 untrusted로 넣는다(`blob_store.current_revision_evidence`, 관측 상한 초과나 관측 밖 경로는 판정하지 않고 재생성은 `wiki_lifecycle`이 맡는다), 다른 worktree·branch view의 trust는 빌리지 않는다. 게시 head가 없는 cold view는 완료 전까지 게시하지 않는다. view binding은 settings 정체성과 wiki root dev/ino이고, `skipPaths`는 binding 밖이라 pass마다 현재 settings에서 읽는다. 대량 삭제는 `schema3_mass_removal_held`로 보류한다. manifest의 `sources`는 같은 pass의 유계 raw 관측(4,096 파일·64 MB, 넘으면 빈 목록)이고 wiki discovery가 그 관측을 재사용한다. vector는 lexical 세대를 먼저 게시한 뒤 설치 provider spec으로 fill하고(cursor 재개), 완료되면 vector 세대를 게시한다. pass의 첫 cold target(chunk set 없음)은 chunk set이 있는 target처럼 resume 예산(`SCHEMA3_RESUME_SECONDS`)을 한 번 받고, 앞 작업이 pass 예산을 다 써도 그 target은 시도한다. main view에 ingest할 카드·원문 변경이 없는 pass는 vector fill과 그 뒤 vector 세대 게시에 240초 창(`SCHEMA3_VECTOR_SECONDS`, publish reserve 포함)을 쓰고, 창 안에서 자기 deadline에 걸린 fill 호출이 embedding set을 남겼으면 다음 호출로 이어 간다(아무것도 남기지 못한 호출은 pass를 끝낸다). 카드를 ingest한 pass와 연결 view는 pass 예산 그대로다. 첫 미완 target 앞 cache hit 구간이 `MAX_FILES`를 넘으면 한 호출로 넘기고, provider 호출마다 그 앞에서 owner를 기다리는 다른 프로젝트의 초기 빌드(`_initial_build_waiting`)에 양보하고(`laya_sync_yield_priority`), main view vector가 그 pass에 embedding set을 늘리고 끝나지 않으면(이 양보·provider 실패로 멈춘 경우 포함) 결과를 ACK하고 같은 `laya-sync` wake를 30초 뒤로 다시 offer한다(진척이 없으면 pending으로 남아 backoff하고, 연속 144회면 wake 정책의 `retry_cap`으로 지워져 다음 편집·SessionStart wake를 기다린다). main이 진척했거나 vector 세대를 게시한 pass에서 pass 예산으로만 남은 연결 view(`schema3_pass_budget`)는 결과를 pending으로 만들지 않고 같은 30초 재offer를 받는다. 마지막 fill 호출이 pass deadline을 넘기면 그 pass의 세대 게시는 새 publish reserve를 받는다. `wake.sync` detail은 main view vector 상태(`vec_<state>_<사유>`·`rem`·`ord`·`pms`·`pub`·`res_`)를 담는다. main view의 첫 vector 세대 뒤 owner가 `resettle_selection`으로 endpoint에 vector spec을 봉인해야 recall이 query vector를 요청한다. provider가 token window로 다시 쪼갠 카드는 view recipe가 그 chunk 위치를 재현할 수 없어 recipe의 fallback 창(`store.types.FALLBACK_CHARS`, 600/90/135 UTF-16 단위)으로 chunk set을 만들고 창마다 따로 embed한다(`_schema3_chunker`). 그 카드의 vector도 같은 vector 세대에 게시된다. provider 정체성을 증명할 수 없으면 wake가 `blocked`(`provider_blocked`)로 끝나고 일시적 거절은 `deferred`다. 같은 설치의 외부 편집 drain·wiki discovery·dedup retrieval·학습 corpus는 view head를 읽고, retroactive dedup scan은 view vector가 없으면 고정 사유로 건너뛴다.
- 선택 sync와 초기 빌드는 사용자당 하나인 sync owner 잠금을 함께 쓴다. 대기 중인 초기 빌드가 있으면 선택 sync가 양보한다.
- `sync.api.run(project, *, coordinator=None, report=None, start_service=None)`은 embed 서비스 시작 함수를 받는다. 없으면 설치된 warm 서비스를 쓰고, 시험 runtime root에 fixture port가 있으면 그 port의 서비스를 쓴다.
- compile intent 소비(`compile_intents.consume`) — verify worker가 검증을 통과한 카드마다 `<install state root>/provenance-intents/compile-<id>.json`(0700 디렉터리, canonical JSON, 이름 = 내용의 id)을 남긴다. view pass는 카드 ingest 뒤 `prepare_generation` 전에, 그리고 바뀐 것이 없는 pass에서도 그 view의 intent를 소비한다. intent 지문의 (worktree, branch)가 이 view와 같고, 그 경로의 이번 pass member와 디스크 바이트가 intent 카드 SHA와 같고, 카드 frontmatter의 `sourceRevisions` (path, sha256, size) 집합과 `sourceSpans`가 intent와 같으면 observed 지문·`lines-v1` span·`memvane-card-evidence-v2` receipt를 compiled attestation으로 `card_attestations`·`attestation_sources`에 쓴다. member trust는 바꾸지 않는다. 결과는 rename(`.consumed`·`.rejected`·`.superseded`)이고 rename 직전에 읽은 fd와 경로의 정체성을 대조한다. 카드가 아직 그 바이트가 아니면 waiting으로 남긴다. 거절 사유는 `provenance_parity_mismatch`(frontmatter와 불일치), `provenance_conflict`(같은 id에 다른 지문·attestation), `provenance_value_invalid`(손상·이름 불일치·값 검증 실패)다. 같은 view·경로에서 더 나중이거나 같은 관측의 intent가 consumed되면 그보다 앞서 기다리던 다른 카드 SHA의 intent는 superseded가 된다. 이번 pass member나 디스크의 현재 카드 바이트와 SHA가 같은 intent는 ingest가 늦어져도 남긴다. pass마다 view당 파일 512개를 열고 store 쓰기는 64건까지 시도하며, view별 위치를 `provenance-intents.cursor`에 남겨 다음 pass가 이어 간다. 첫 store 쓰기 앞에서 journal fence를 한 번 세우고, 소비할 intent가 없으면 store·journal을 쓰지 않는다. fence·writer 증명 실패와 store의 binding·일시 사유는 intent를 거절하지 않고 pass를 끝낸다. pass 결과의 `provenance`는 `{consumed, rejected: {사유: 개수}, waiting, superseded}`(연결 view는 `worktrees` 항목마다)이고, 게시를 끝낸 pass에서 consumed·rejected·superseded가 하나라도 있으면 그 합계가 `wake.sync` 이벤트의 `provenance`로 남는다(`app/runtime_dispatch._provenance`). intent 파일은 지우지 않는다. 아직 settle되지 않은 링크(nlink 2)나 열 수 없는 intent 파일은 건드리지 않고 (이름, inode)마다 한 번만 `unsafe`로 센다(view의 cursor 항목이 그 이름이 남아 있는 동안 기억한다).
